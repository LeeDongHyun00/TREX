# 격차 페이지(디자인 v2) — 서버에서 구현이 필요한 부분 (§131, 2026-11-07)

대상: 디자인 캔버스 "TREX 격차 페이지 디자인" v2(P1~P18 + 빈 상태)의 앱 구현(`feature/exercise-expansion-46`, 스펙 §131). 서버는 사용자 담당이다(`docs/SERVER_SYNC_HANDOFF.md`).
이 문서는 **앱이 이미 한 것(서버 변경 없이 도는 것)** 과 **서버가 해야 할 것** 을 가른다. 서버 쪽 결정이 나면 §131 의 '서버 대기' 항목을 닫는다.

## 1. 서버 변경 없이 도는 것(지금 앱)

현재 동기화는 키-블롭 백업(`PUT /api/sync/{key}`, 나중에 바꾼 쪽이 이김, 키 `^[a-z0-9_]{1,64}$`, 페이로드 ≤ 2,097,152자)이라 **새 항목은 키만 늘리면 된다**. `sync/SyncRules.KEYS` 에 추가한 키:

| 키 | 내용 | 크기 |
|---|---|---|
| `body_weight` | 체중 기록(P7) 배열 | 건당 ~90자 |
| `xp` | XP 장부(P5·P6) — 세션·수동 기록·가이드 열람·루틴 공유 | 건당 ~100자 |
| `custom_exercises` | 직접 추가한 종목(P9) | 건당 ~200자 |
| `weekly_routine` | 요일 → 루틴 참조(P11) | 수백 자 |
| `record_retention` | 보관 기간(P14) — 기기끼리 같아야 한 기기의 삭제가 다른 기기 기록을 덮지 않는다 | 수 자 |
| `streak_pause` | 연속 멈춤(P6) | 수십 자 |

옛 앱은 모르는 키를 무시한다(`SyncRules.toApply`). `history` 항목에는 세트별 `sets`(kg·회·카메라 횟수·RPE·메모)와 `source` 가 늘었다 — 옛 앱은 그 칸을 읽지 않고 **저장할 때 버린다**(`TrexStore.saveHistory` 가 아는 칸만 쓴다). 옛 앱과 새 앱을 같은 계정에서 섞어 쓰면 옛 앱이 올린 `history` 가 새 칸을 지운다 → 아래 §2-1.

알림(P16)은 기기 안에서만 예약한다(Android `AlarmManager`) — **서버 푸시 없음**(디자인 안내문 그대로). 내보내기(P15)는 기기에서 CSV/JSON 을 만들어 공유 창으로 넘긴다 — 서버 없음.

## 2. 서버가 해야 할 것

### 2-1. 기록 보관 기간 vs 2 MB 페이로드 (결정 필요)

보관 기간 기본값이 **제한 없음** 이 됐다(예전 7일). `history` 가 한 블롭이라 하루 3종목 × 3세트 × ~400자 ≈ 하루 1.2 KB → 2 MB 는 약 4~5년치다. 당장은 넘지 않지만 사진·메모가 늘면 빨라진다.

- 선택 A(서버 변경 없음): 앱이 `history` 를 월별 키로 나눈다(`history_2026_11`). 키 규칙은 맞고 서버는 그대로이나, **옛 앱은 그 키를 몰라 그 달 기록을 못 본다**(무시하므로 깨지진 않는다).
- 선택 B(서버): 페이로드 상한을 올리거나(예 16 MB), `history` 만 압축(gzip base64)을 받는다.
- 선택 C(서버): 운동 기록을 행 단위 API(`/api/exercise-logs` 가 이미 레거시로 있다)로 옮긴다 — 항목별 충돌 해결·부분 동기화가 되지만 앱의 동기화 모델이 바뀐다.

권장: 당장은 A 도 B 도 하지 않고 상한을 지켜본다(앱이 `history` 크기를 계정 화면에 표시하지는 않는다 — 1.5 MB 를 넘으면 앱이 "보관 기간을 줄이거나 내보내기" 를 권하는 안내를 다음 단계로). 서버 쪽에서 B 가 쉬우면 B.

**옛 앱 섞어 쓰기**: 옛 버전이 `history` 를 올리면 새 칸(`sets`)이 사라진다. 서버에서 막을 방법은 없다(블롭). 앱 배포 뒤 체험판 사용자에게 업데이트를 강제하는 것(`AppUpdate.kt` 최소 버전)이 현실적 대책 — 서버 작업은 아니지만 릴리스 결정이다.

### 2-2. XP·배지·연속 — 권위(authority)

지금은 전부 **기기 계산**(`RecordModels.kt` `Rewards`·`badges`·`targetDayStreak`)이고 XP 장부(`xp`)가 블롭으로 백업된다. 사용자가 블롭을 손대면 XP 를 조작할 수 있지만, XP 는 커뮤니티 순위·보상 교환에 쓰이지 않으므로 **지금은 서버 검증이 필요 없다**. 다음 중 하나를 하려면 서버가 권위를 가져야 한다:

- 커뮤니티에 레벨·배지 표시(리더보드) → 서버가 `history` 블롭에서 XP 를 **재계산**하거나(규칙을 서버에 복제), 세션 완료 이벤트 API(`POST /api/sessions`)를 받아 서버가 적립. 후자가 정석이나 오프라인 세션의 뒤늦은 전송·중복(세션 id 로 멱등) 처리가 필요하다.
- '루틴 공유' 배지: 공유 링크 생성은 이미 서버(`POST /api/routines/share`)라 서버가 **공유 횟수를 계정에 기록**하면 기기 장부 없이 확정할 수 있다. 지금은 앱이 성공 응답 뒤 장부에 적는다.

### 2-3. 알림 푸시(선택)

디자인은 "서버가 보내는 푸시가 아니다" 라고 못박았다. 기기 알림의 한계: 재부팅 뒤 재예약 없음(다음 앱 실행에서 다시 건다), iPhone 미구현(설정만 저장). 서버 푸시(FCM/APNs)로 가려면 토큰 등록 API·스케줄러·요일/시각 저장이 필요하다 — **디자인 결정을 먼저 바꿔야 한다**.

### 2-4. 받은 루틴(P10 '받은 루틴' 탭)

이미 서버에 있다(`GET /api/routines/shared/{code}`, D14). 앱은 받은 루틴을 보관함(`routines`)에 넣는다 — 루틴 화면의 '보관함' 탭이 그것이다. 추가 서버 작업 없음.

### 2-5. 커뮤니티 '오운완 올리기'(P5)

이미 있다(완료 화면 → 커뮤니티 글쓰기). 보상 띠의 PR·XP 를 글 카드에 넣으려면 카드 데이터(`WorkoutCardData`)에 칸을 늘리고 **서버 게시글 스키마**에 선택 칸(`pr`, `xp`)을 더해야 한다 — 지금은 넣지 않았다.

### 2-6. 추천 루틴 프리셋 배포(선택)

프리셋 60개는 앱에 묶여 있다(`routines/RoutinePresets.kt`, 정본 `research/routines/routine_presets.json`). 앱 업데이트 없이 바꾸려면 `GET /api/routines/presets`(버전 붙여 캐시) 가 필요하다. 지금 필요하지 않다.

## 3. 앱이 아직 안 한 것(서버 무관, 다음 단계)

- 외부 중량·RIR 을 근육 부하 모델에 반영(§130 §3 의 '입력 추가') — 지금은 기록만 한다.
- Android 재부팅 뒤 알림 재예약(`RECEIVE_BOOT_COMPLETED`), iPhone 알림(`UNUserNotificationCenter`).
- 46종 운동 가이드(자료집 '수행 포인트').
- 운동 탭 행 편집에서 세트별 kg 목표(디자인 P11 "60 kg") — 지금은 '지난번' kg 을 보여 준다.
