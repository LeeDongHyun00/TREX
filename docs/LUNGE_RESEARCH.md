- 폰 세트 1개(첫 시도, 13:54)와 음성 로그(두 번째 시도, 13:56)
- 모집단 재생: AIHub 013 스텝 포워드 GT·MP, MM-Fit 런지 62세트 626걸음, REHAB24-6 Ex5 346창
- 다중 에이전트 분석: 분석 4, 설계 3, 심사 3, 종합, 반박 검토 2

분석 스크립트는 세션 scratchpad `lunge/` 에 있다. REHAB 파생물은 CC BY-NC 라 저장소에는 집계 수치만 둔다.

## 0. 결론

**이번 테스트에서 자세 판정은 0건이었다.** 원인은 넷이고, 넷 다 런지 자세 규칙 자체와는 무관하다.
1. **두 번째 시도는 앱이 죽어서 기록이 사라졌다.** 13:57:10.170 에 MediaPipe 안에서 SIGSEGV 가 났다(§1-3). 어제 20:06 에도 같은 크래시가 있었다.
2. **첫 시도는 몸이 옆으로 돌아가 있었다.** 준비 확인은 38~44°(B)로 통과했다. 그런데 걷는 동안 어깨 요가 54~84° 로 돌아가 **모든 규칙이 '옆 방향'으로 유보**됐다.
3. **숙임을 잡는 규칙이 없었다.** 런지 ship 규칙 '상체 숙임/젖힘'(`torso_pitch__min < −3.97`)은 **뒤로 젖힘** 검출기다.
4. **어깨 기울기 규칙은 흔들림을 잰다.** 규칙은 `shoulder_asym__std` 라 기울인 채 유지하면 std ≈ 0 이 된다. 게다가 MediaPipe 정상 오탐률이 15.8 %(n=19)다.

**재설계의 뼈대는 넷이다.**
- **(a) 1회 = 왼발 앞 걸음 + 오른발 앞 걸음.** 쪽은 무릎 신호에서 나오지 않는다. 걸음 **바닥 순간 어느 발목이 앞인가**라는, 걸음에 붙은 속성이다.
- **(b) 자세는 걸음마다 바닥에서 한 번 잰다.** 판정 단위가 걸음이다.
- **(c) 검사마다 볼 수 있는 촬영 방향이 다르다.** 방향은 걸음마다 **어깨선으로만** 정한다. 골반선은 앞다리에 따라 ±35° 흔들린다.
- **(d) 음성 오탐 예산은 세트 단위로 잡는다.** 걸음당 2 % 라도 20걸음 세트의 33 % 가 헛교정을 한 번 이상 듣는다.

## 2. 제1원리

### 2-1. 1회와 쪽

- **1회는 왼발 앞 걸음 1개와 오른발 앞 걸음 1개**다(사용자 결정 2026-09-24, 이번 요청에서 재확인).
- **'더 굽은 무릎 = 앞다리' 는 쓸 수 없다.** 두 무릎이 매 걸음 다 굽는다(바닥에서 앞 65–89°, 뒤 62–119°). 이 단서의 정확도는 AIHub GT 0.51, MM-Fit 0.25 다.
- **컬의 팔별 코어도 쓸 수 없다.** 두 무릎 자식 사이클이 겹쳐 한 걸음이 '동시 1회' 가 된다.
- **쪽은 바닥 순간 어느 발목이 앞인가로 정한다.**
  - 월드 3D 발목 전후 차 ÷ 다리 길이. 폰 걸음에서 0.46~0.84, 스쿼트에서 0.00~0.21 이다.
  - 2D 앞뒤 순서를 함께 본다.
- **세기에는 이름이 필요 없다.** 사선·옆에서는 '앞발이 카메라 쪽 다리인가 먼 쪽 다리인가' 로 두 무리로 나뉜다.
  - MediaPipe 가 좌우 이름을 통째로 뒤바꿔도 무리 나누기는 그대로라, 셈이 틀리지 않는다.
  - '왼/오른' 이름은 화면 표시에만 쓴다. 분석 프레임은 반전되지 않는다(`PostureAnalyzer` 는 뒤집지 않고 오버레이만 미러링 — `PostureLive.kt:1209·1383`).

### 2-2. 촬영 방향별로 보이는 것

| 검사 | 옆(60~90°) | 사선 45°(B/D) | 정면(C) |
|---|---|---|---|
| 앞발 쪽(셈) | ◎ 가려짐·앞뒤가 뚜렷 | ○ | ✕ 앞뒤가 깊이축 |
| 앞무릎 깊이 | ◎ 가까운 다리 2D r 0.93–0.96 | ○ 3D MAE 9.9° | △ 3D MAE ~14°, 2D 는 +37° 오차 |
| 뒷무릎 높이 | ◎ | ◎ | ◎ 수직 성분 |
| 상체 숙임(pitch) | ◎ | ○ | △ 깊이축(MAE 8.8°) |
| 정강이 기울기(무릎 앞으로) | ◎ | △ 요 보정 필요 | ✕ |
| 어깨 기울기 | ✕ 먼 어깨 가림·깊이축 | ○ | ◎ |
| 무릎 안쪽 모임 | ✕ | △ | ◎ |

- 사용자가 실제로 선 방향은 **옆에 가깝다**(54~84°). 요청한 다섯 중 넷(쪽·깊이·숙임·무릎 앞으로)은 옆에서 가장 잘 보인다. 어깨 기울기만 옆에서 못 본다.
- 저장소 규약상 옆(SIDE)은 미검증 등급이라 모든 규칙이 유보된다. AIHub 에 옆 카메라가 없으니(최대 45°) **옆은 폰 지정 오류 세트로만 검증할 수 있다**(원칙 #2 — 근거는 AIHub 에 한정하지 않는다).

### 2-3. 음성 예산

- 한 세트(10쌍 = 20걸음)에서 헛교정을 한 번이라도 들을 확률 = 1 − (1 − p)^20. p=5 % → 64 %, 2 % → 33 %, 0.5 % → 10 %.
- 음성 교정은 **같은 검사 2걸음 연속 위반**일 때만 한다. 오탐이 독립이면 대략 p² 가 된다. 음성은 세트당 상한 2회를 두고, 그 뒤는 화면 표시와 짧은 신호음으로만 알린다.
- 게이트(COACH 에서 걸음 제외)는 기존 입장 조건(모집단 정상 오탐 ≤ 2 %)을 그대로 따른다.

- **걸음 방향**
  - 직전 선 자세 프레임의 어깨선 요로 정한다.
  - 사선 띠는 ≤ 55°(`REP_OBLIQUE_MAX_DEG`)다.
  - `RepFormEvaluator` 에 방향 피처 이름 인자(`viewFeatures`)를 추가한다.
- **카운터**
  - 레거시가 화면을 계속 구동한다.
  - 새 코어는 그림자로 돌려 로그만 남긴다. 저장 세트에서 새 코어는 13/15, 레거시는 10/15 걸음을 잡는다.
  - MM-Fit(MediaPipe) 세트 정확도는 새 코어 0.97, 레거시 0.18 이다.
  - 새 코어의 시작 확정은 진폭 비 0.5~2.0 밖의 사이클을 보류하거나 버린다(`RepHysteresis.kt:239-257`). 깊은 걸음 뒤의 얕은 한 걸음이 말없이 사라진다. **런지에서는 이 비 조건을 완화한 채로 그림자를 돌린다.**
  - 화면 구동을 새 코어로 전환하는 것은 Gate A 와 폰 라벨 세트를 통과한 뒤다(`RepCounter.kt:789`).

### 3-1. 왼 + 오 = 1회 (문제 1)

**해결**
- **걸음마다 쪽을 정한다.**
  - 무리: 방향이 B/D/SIDE 이고 `|lunge_fwd_d| ≥ 0.25`(3D)이면, 앞발이 카메라 쪽 다리인지(가시도 차와 2D 앞뒤 순서) 보고 **가까운/먼** 무리로 나눈다.
  - 정면(C)이나 기준 미달이면 `?` 다.
  - 3D 가 확실하면(≥ 0.25) 2D 무릎 높이 여유가 모자라도 3D 로 정한다. 얕은 걸음은 뒷무릎이 높아 2D 단서가 약하다.
- **짝 수 규칙: 보수형.**
  - 쪽이 확실한 걸음들 사이에서만 짝을 강제하고, `?` 는 `?` 끼리만 짝짓는다.
  - 짝 수 = min(n가까운, n먼) + ⌊n?/2⌋. 걸음이 전부 `?` 이면 지금의 floor(N/2)와 같다.
  - `?` 를 만능 짝으로 쓰면, 덜 보일수록 수가 오른다(원칙 #1 위반). 그래서 쓰지 않는다.
  - 걸음마다 +0 또는 +1 이라 발표한 수가 되돌아가지 않는다.
- **COACH 와 TRACK.** 두 무리 풀을 따로 둔다.
  - TRACK: 동작 판별을 통과한 걸음 전부.
  - COACH: ship 차단 위반이 없는 걸음.
  - 짝을 풀에서 다시 계산하므로, 나쁜 걸음 하나가 1회를 통째로 지우던 '쌍 − 사이클' 빼기(`PostureLive.kt:402·999-1001`)가 사라진다.
- **화면**
  - 큰 숫자 = 짝.
  - 아랫줄은 처음에는 이름 없는 표시("한쪽 3 · 반대쪽 1", "반대쪽 차례")다.
  - 좌우 이름 점검(§5 단계 3)이 통과하면 "왼 3 · 오 1" 로 바꾼다.
  - `?` 걸음이 있으면 "좌우 미확인 n걸음" 을 밝힌다.
- **음성**
  - 숫자는 짝이 완성될 때만 말한다.
  - 짝 없이 인정된 걸음에는 짧은 확인음(`repTone`)을 낸다. 한쪽씩 몰아서 하면 첫 블록이 침묵이 되고, 침묵은 고장으로 읽힌다.
  - 같은 쪽 확신 걸음이 3연속이면 세트당 1회 말한다. "반대쪽 다리까지 해야 횟수가 올라가요." 왼2·오2 방식에서는 나오지 않는다.
  - 쪽 이름은 음성에 넣지 않는다.
- **동작 판별(무릎 들기 차단)**
  - `lunge_foot_lift`(두 발목 높이 차 ÷ 정강이, **바닥 프레임 중앙값**) > 0.75 → `reps.rejected`.
  - MM-Fit(MP, 626걸음): 중앙값 기준 0.8 % 기각, 최댓값 기준이면 3.2 % 라 입장 조건 위반이다.
  - **그림자로 먼저** 돌리고, REHAB·AIHub 오탐을 잰 뒤 켠다.

**예시(보수형 규칙, 전부 확신)**

| 순서 | 표시 |
|---|---|
| 말씀하신 프로토콜 L L R R Lb Lb Rb Rb Lt Lt Rt Rt | 0 0 1 2 2 2 3 4 4 4 5 6. TRACK 6, 숙임이 ship 되면 COACH 4 |
| 한쪽만 10걸음 | 0 (지금은 5) |
| 저장 세트 순서 R×4 L×5 R×5(얕은 R 3걸음이 `?` 면) | 확신 R4·L5 → 4, `?` 3 → +1, 합 5 |

**증거와 위험**
- 사선 AIHub-MP B·D 에서 쪽 정확도는 0.989 다.
- REHAB(앞다리 고정 영상)의 확신 걸음 정확도는 0.972 다.
- 정면 MM-Fit 에서는 쪽 짝짓기 50/62 세트, floor 62/62 세트다. 그래서 **정면은 `?`(floor) 로 둔다.**
- 20걸음 교대 세트에서 걸음 오판 p 하나가 짝 하나를 지운다. 1회 이상 잃을 확률은 p=2.8 % 면 43 %, 1 % 면 18 % 다.

**상태 제안**
- 쪽 판정과 짝 계산은 첫 빌드부터 **로그와 화면 보조줄**에 나온다.
- **큰 숫자를 쪽 기준으로 바꾸는 것은 안내형 세트 1회 뒤**다. 조건: B·SIDE 각 교대 블록에서 걸음 쪽 정확 ≥ 99 %, 세트 짝 수가 floor 이상 정확.
- 안내형 세트는 하루면 모인다(§5 단계 3). 사용자가 원하면 조건 없이 바로 전환할 수도 있다(§6 질문 1).

### 3-2. 허리 말림 → 상체 숙임 (문제 2)

**정직하게 말할 점: 허리 말림(척추 굽힘) 자체는 관측할 수 없다.**
- MediaPipe 33점에는 척추 점이 없다.
- AIHub 이 종목의 '척추의 중립' 위반 1015클립(전체 1618)에 굽힘 연기가 0건이다. 옆 기울임 556, 경추 407, 미상 52 다.
- 귀-어깨-골반 각은 숙이면 오히려 '곧게'(151 → 176°) 읽혔다.

보이는 것은 **상체 숙임**이다. 이번 세트에서 숙인 4걸음은 pitch +28.4~36.6°(두 번째로 곧은 걸음 대비), 나머지 걸음은 ≤ +6.3° 로 뚜렷하게 갈렸다.

**해결: 걸음 검사 '상체 숙임(걸음)'**
- 피처는 `torso_pitch`, 창은 BOTTOM, 통계는 MEDIAN 이다.
- 기준은 `SET_LOW_DELTA`(지금까지 두 번째로 곧은 바닥)이고, 첫 2걸음은 기준만 모은다.
  - `SET_MIN_DELTA` 는 쓰지 않는다. 앞쪽 반구 상단 프레임으로만 갱신돼 SIDE 에서는 기준이 서지 않는다.
  - `torso_incl` 대신 pitch 를 쓴다. incl 은 옆 뷰에서 roll 편향(~−8°)을 섞어 숙인 걸음을 2/4 만 잡았고, pitch 는 4/4 를 잡았다. 다만 근거는 폰 1세트다.
- 코칭 +20°, 차단 +25°.
- **처음부터 숙인 경우**
  - `absHi`: 바닥 `torso_incl` > 40° 면 기준과 무관하게 위반. 다른 피처를 보므로 새 필드 `absFeature` 가 필요하다.
  - `refCap`: 방향별 MediaPipe 정상 바닥 pitch 의 p95. 중앙값(≈ +10°)으로 자르면 보통 사람의 기준까지 잘린다.
  - `refNotice` 는 세트에서 1회 알린다.
- 문구: "상체가 많이 숙여졌어요. 가슴을 들고 몸통을 세우세요." '허리가 말렸어요' 는 쓰지 않는다.
- PostureScope 에 "허리 말림(척추 굽힘)은 보지 못해요 — 상체가 숙여지는 정도로만 봐요" 를 추가한다.
- **유지 자세(liveEvent)**: 선 채로 숙여 4 s 이상 멈추면 알리는 기능이다. 이 기준으로는 작동하지 않는다(`RepForm.kt:394-398` 은 SET_MIN·START 기준만 받는다). 선 자세 전용 기준을 따로 세워야 하고, 쉬는 동작(HUD 보기·폰 만지기) 오탐을 잰 뒤에 켠다.
- **런지 창 규칙 '상체 숙임/젖힘'(5345, MP 정상 오탐 16.2 %)** 은 걸음 검사가 생기면 `supersedes` 로 beta 로 내린다. 뒤로 젖힘은 걸음 단위 절대 하한으로 beta 재도입하고, 그전까지 PostureScope 에 '젖힘은 참고로만' 을 밝힌다.

**정상 오탐(걸음 바닥, 같은 규칙)**
- MM-Fit(MediaPipe, 연속 300 ms, 502걸음, 정면): > 20° 1.0 %, > 25° 1.0 %. 꼬리 1 % 는 랜드마크가 튄 걸음이라 임계를 올려도 줄지 않는다.
- AIHub-MP 키프레임(방향당 약 40걸음), > 25°: B 0.8 %, C 0 %, D 0.8 %.
- 옆(SIDE)은 모집단이 없다. **폰 세트로만** 잴 수 있다.

**방향과 상태**
- B/D: ship 후보.
- SIDE: 같은 검사를 beta 로 둔다. 사용자가 실제로 서는 방향이라 **폰 SIDE 세트 검증을 1순위**로 둔다.
- C: beta.
- ship 전까지 숙인 걸음도 센다(원칙 #2). ship 뒤 COACH 는 차단 걸음을 빼고 그 자리에서 이유를 말한다.

### 3-3. 깊이 80~90° (문제 3)

**제1원리: '90°' 는 합격선이 아니라 안내 문구다.**
- 정상 앞무릎 최소값(걸음별): AIHub GT 081 p50 91°, p75 107°, p95 127°. MM-Fit 정상 걸음의 33 % 가 90° 보다 얕다.
- 사용자의 곧은 정상 걸음은 65~84° 로 이미 90° 보다 깊다.
- 그래서 검사는 '덜 굽힘' 한 방향으로만 둔다.
- REHAB 치료사 라벨 '올바름' 런지는 앞무릎 p50 110°, p75 123° 로 얕다. 깊이 차단 하나로 한 집단의 올바른 런지를 틀렸다고 할 수 있다(원칙 #3·#4). 그래서 **차단은 '거의 편 다리' 만** 한다.

**해결**
- **앞다리 고르기**: 셈용 이름이 아니라 **3D 앞뒤(`lunge_fwd_d`)로만** 고른다. 이름이 뒤바뀌어도 무릎·발목 라벨이 함께 뒤집혀 영향이 없다.
- **방향별 측정**
  - 옆: 가까운 다리면 2D 각.
  - 사선·정면: 3D 각.
  - 3D/2D 차 > 15° 인 걸음은 유보한다.
- **걸음 검사 '앞무릎 깊이(걸음)'**
  - 코칭(beta): 본인 깊은 걸음 대비 +30° 이상 얕다. 기준은 `SET_LOW`, 첫 2걸음은 기준용이다.
    - 절대 110° 는 걸음별 오탐이 AIHub GT 7~22 %, MM-Fit 3.0 % 라 주 기준으로 쓰지 않는다.
    - 상대 기준 오탐은 MM-Fit 0.8 %, REHAB 0 %, AIHub-MP D 1.7 %·B 5.1 % 다.
  - 차단(ship 후보): 앞무릎 > 140°(AIHub 오류 연기 '앞다리 다 펴고' 수준) **그리고** 뒷무릎 높이 > 0.5.
    - 두 조건을 함께 보려면 새 필드 `gateAlso` 가 필요하다.
    - 뒷무릎 높이의 모집단 분포는 **미측정**이다. MM-Fit·AIHub 로 먼저 잰다.
- **놓친 얕은 걸음**
  - 레거시는 얕은 7걸음 중 2걸음만 사이클로 만든다. 사이클이 없으면 깊이 피드백도 없다.
  - 그래서 **세지 않는 분할 자세 검출기**를 따로 둔다: `lunge_fwd_d` ≥ 0.25 이고 앞무릎이 15° 이상 굽었다 펴짐.
  - 이 검출기는 깊이 안내("더 내려가 주세요")만 하고 횟수에는 손대지 않는다(원칙 #7).
- **문구**: "덜 내려갔어요. 뒷무릎을 바닥 가까이 내려 주세요." 뒷무릎 높이는 보이고, 각도와 무관한 말이다.
  - 음성은 같은 검사 2걸음 연속일 때만, 세트당 2회 상한.
  - COACH 차단 걸음은 "이 걸음은 세지 않았어요" 를 붙인다.
- **리포트**: 쪽별 평균 깊이를 '참고' 로 보인다("한쪽 약 80° · 반대쪽 약 110°").

**재평가된 저장 세트 결과**(검토에서 고침): 얕은 5걸음 중 **코칭 2 · 차단 0 · 유보 3** 이다(3D/2D 차 > 15°). '코칭 5/5 · 차단 3/5' 는 이 설계의 규칙을 적용하지 않은 숫자였다.

### 3-4. 어깨 기울기: 처음만 잡힘 (문제 4)

**원인 다섯**
1. **흔들림 검출기다.** 규칙은 `shoulder_asym__std`(8프레임 = 2.4 s)다. 기울인 채 유지하면 std ≈ 0 이다. 첫 시도 B3 는 평균 −0.10~−0.125 로 기울었는데 std ≤ 0.049 였다. 반대로 숙이는 동작만으로 std 가 0.103 이 되어 임계(0.102)를 넘었다.
2. **이 규칙 자체의 MediaPipe 정상 오탐이 15.8 %(n=19)다.** 2.3 % 는 GT 3D 수치였다.
3. **쿨다운(12 s)이 한 쌍(9~10 s)보다 길다.**
4. **옆에 가까우면 옆 기울기는 깊이축이다.** 먼 어깨가 가려진다.
5. **'처음부터' 는 초반 창이 유보여도 붙는다.** `PostureCoach.kt:305`(발화)와 `:386`(세트 리포트)이 초반 창 ABSTAIN 을 HABIT 으로 분류한다. **모든 종목**의 버그다(원칙 #1). 두 번째 시도의 13:56:54 발화가 이 경로였는지는 로그가 없어 **추정**이다.

**해결**
- **HABIT 수정(두 곳, 전 종목).** 초반 창이 판정(OK/VIOLATION)됐을 때만 '처음부터' 를 쓴다. 아니면 중립 문구 "몸통이 옆으로 기울어 있어요. 양 어깨 높이를 맞추세요." 로 말한다. 낡은 주석도 고친다.
- **std 규칙은 런지에서 beta 로 강등**한다. 5345 와 같은 근거(MP 정상 오탐 ~16 %)라 같은 대우를 한다.
- **걸음 검사 '어깨 기울기(유지)' beta**
  - `sh_level2d`, 바닥 중앙값.
  - 기준은 본인이 **같은 무리(앞발 가까운/먼)** 로 한 처음 2걸음이다. 앞다리에 따라 원근 오프셋이 뒤집히기 때문이다(오 앞 +0.013~+0.019, 왼 앞 −0.058~−0.061). 새 필드 `refBySide`, `refN`=2 가 필요하다.
  - 정면(C)에서는 무리를 모르므로 합친 기준을 쓴다.
  - 숙임 차단 걸음은 기준에서 빼고(`refExcludedBy`) 그 걸음의 기울기 판정은 무효로 둔다(`invalidatedBy`). 숙임만으로 2D 어깨 높이차가 +0.10 몸통 움직인다.
  - |Δ| > 0.12(≈ 9°) 에서 위반이다.
  - 절대 기준은 쓰지 않는다. MM-Fit 연속 데이터에서 |기울기| > 10° 오탐이 21 % 다. 자기 기준 오탐은 **미측정**이라 MM-Fit 으로 먼저 잰다.
- **발화 주기**
  - 걸음마다 화면에 칠한다.
  - 음성은 2걸음 연속 위반일 때 한다.
  - 창 규칙과 걸음 검사가 부위별 쿨다운 키 하나를 공유해 같은 기울기를 두 번 말하지 않는다.
  - 쿨다운 안에서 반복된 기울기는 음성 1회, 화면은 걸음마다 표시한다. 이 한계를 사용자에게 밝힌다.
- **못 볼 때 밝힌다.** 걸음 방향이 55° 를 넘으면 화면에 "옆으로 많이 돌아서 어깨 기울기는 못 봤어요" 칩을 띄운다. 리포트에는 "어깨 기울기: 15걸음 중 15 판정 못 함" 처럼 남긴다.
  - 컬의 `turnedTooFar` 문장("이 회는 자세를 못 봤어요")은 쓰지 않는다. SIDE 에서도 숙임·깊이는 보므로 거짓이 된다.

### 3-5. 무릎이 발끝을 넘음 (문제 5)

**제1원리: 그 자체는 오류가 아니다.**
- 무릎이 못 나가게 막으면 엉덩이 토크와 몸통 숙임이 는다(Fry 2003).
- 넘으면 무릎 부하(슬개건 +11 %, 대퇴사두 +13 %)가 는다(Zellmer 2019). 즉 부하를 어디에 둘지와 보폭의 문제다.
- 실제 결함은 **앞꿈치로 체중이 쏠리는 것(앞발 뒤꿈치 들림)**이다.
- **데이터가 금지 규칙을 뒤집는다.** 사용자의 곧은 정상 걸음은 정강이의 +0.14~+0.41 넘었고, 숙인 걸음은 덜 넘었다.
- 발끝 랜드마크의 2D 오차는 5~9 cm 이고 바닥에서 미끄러진다. AIHub 에는 이 조건도, 발끝 관절도 없다('Foot' 은 발목 앞 약 6 cm).

**해결 (사용자 결정 필요, §6)**
- **beta '앞 정강이 기울기' 는 숫자만 보인다.** "정강이 기울기 41°" 처럼 결함 문구 없이 표시한다.
  - 옆(SIDE)에서만 잰다. 사선의 요 보정(tan(참) = tan(2D) ÷ sin|요|)은 MediaPipe 요가 작게 읽혀(45° → ~33°) 과보정한다. 참 35° 가 ~42° 로 읽힌다.
- 음성 후보는 '정강이 > 45° **그리고** 앞발 뒤꿈치 들림' 이다. `heel_lift` 는 같은 발 랜드마크를 쓰므로 폰 세트 검증 뒤에만 쓴다.
- 게이트·점수에서는 제외한다. 숙여서 무릎이 뒤에 머문 걸음을 칭찬하지 않도록 숙임과 나란히 보인다.
- 발끝 기준 cm 는 로그에만 둔다. 사용자에게 cm 를 말하지 않는다.

1. **[P0] 크래시·기록 유실**
   - landmarker 를 **분석 실행기에서** 닫는다. 진행 중인 `detect` 가 끝난 뒤 `close` 를 같은 실행기에 제출한다. 또는 `detect`/`close` 를 한 락으로 묶고, 닫힌 뒤 `detect` 는 빈 샘플을 돌려준다.
   - 세트 로그는 앱 수명의 단일 쓰기 스레드로 쓴다. `posture_logs/inprogress/<set_id>.jsonl` 저널을 약 5 s 단위로 남기고, 재시작 때 `end_reason: recovered` 로 복구한다. 실패는 feedback 로그 `set_log_failed` 로 남긴다.
   - `finalized` 는 '취소' 때 리셋한다(`PostureLive.kt:568·916` — 지금은 ✕ → 취소 뒤 기록과 카운트가 조용히 멈춘다).
2. **세트 중 방향 확인.** 준비 확인은 선 자세에서만 한다(`CapturePreparation.kt:40-49`). 사용자는 38~44° 로 통과한 뒤 걷는 동안 54~84° 로 돌았다. 선 자세 프레임의 어깨선 요가 3걸음 연속 55° 를 넘으면 세트당 1회 "조금 덜 돌아 주세요" 를 말한다.
3. **자동 진행 보류.** 목표를 채운 뒤 마지막 걸음 판정 발화를 최대 2 s 기다린다(지금은 "6" 뒤 0.7 s).
4. **누락된 AIHub 조건.** '앞다리 무릎 각도 90도'(GT AUC 0.92)가 `rules_mp_v0.json` 에 exclude 로도 없어 PostureScope 가 밝히지 못한다.
   - 스텝 백워드는 같은 조건을 ship 하고 있다(`knee_maxside__mean > 160.6`, MP 오탐 4.9 %).
   - 걸음 검사가 생기면 `supersedes` 로 연결해 한 조건이 '못 봄' 과 '검증 중' 에 겹쳐 나오지 않게 한다.
   - JSON 헤더 counts 는 `rule_confidence.py --apply` 로 다시 만든다.
5. **주석 오류.** `RepCounter.kt:864-866` 의 "런지류는 knee_minside" 는 이 종목(knee_mean)에 대해 틀렸다.
6. **세트 로그에 코치 사건 타임라인**(`coach_events`)을 남긴다. 이번에는 음성 시각만으로 역추적해야 했다.

1. **쪽 기준 횟수로 전환하는 시점.**
   - (가) 안내형 세트 1회로 검증한 뒤 전환(권장). 예상 하루.
   - (나) 첫 빌드부터 바로 전환. 오판 1건이 짝 1개를 지우는 위험을 받아들인다.
2. **촬영 방향.** 45° 를 유지하고 세트 중 '덜 돌아 주세요' 로 붙잡을까요(어깨 기울기까지 봄)? 아니면 런지만 옆 90° 로 바꿀까요(깊이·숙임·정강이가 더 정확하지만 어깨 기울기는 못 봄)? 실제로는 54~84° 에 서 계셨습니다.

## 7. 한계 (못 보는 것)

- **허리 말림(척추 굽힘)은 끝까지 못 본다.** 숙임 없이 허리만 마는 것은 잡지 못한다. 척추 점을 주는 모델(SpinePose)은 CC BY-NC 라 제품에 쓸 수 없다.
- **방향마다 못 보는 것이 있다.**
  - 무릎 안쪽 모임: 사선·옆에서 못 본다.
  - 어깨 기울기: 옆에서 못 본다.
  - 숙임·정강이: 정면에서 약하다.
  - 골반 떨어짐: 신호 대 잡음이 약 1 이라 기록만 한다.
- **카운터는 beta(±1)다.** 레거시는 마지막 걸음을 구조적으로 늦게 센다. 쪽 확신 오판 1건은 짝 1개를 지운다.
- **모든 임계는 잠정이다.**
  - 폰 근거는 라벨 없는 1인 1세트(말씀하신 프로토콜과 다른 세트)다.
  - AIHub-MP 는 키프레임이라 비관적이다.
  - 앞 숙임·무릎-발끝·유지 기울기의 양성 라벨은 어느 모집단에도 없다. 검출률은 폰 지정 오류 세트에서만 나온다.
  - 옆(≥ 60°)은 모집단 데이터가 없다(AIHub 최대 45°).
- **처음부터 30° 로 숙인 채 시작하면** 상대 기준이 오염된다. `absHi` 40° 아래는 `refCap` 에 기대는데, 그 값(방향별 p95)도 아직 미측정이다.
