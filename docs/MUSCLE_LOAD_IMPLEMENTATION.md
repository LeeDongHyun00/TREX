작성: 2026-09-28. 대상: 현재 TREX 로컬 앱. 모델 버전 1.

## 1. 범위와 조사 결과

현재 `Sheets.kt` 카탈로그는 **26종목 전체**다. 앞서 조사한 기본 스쿼트·런지·덤벨 컬을 빼면 추가 대상은 23종목이다. 카탈로그와 연구 매핑의 집합 일치를 테스트한다. 자세 평가 가능 여부나 ship/beta/exclude 상태는 변경하지 않는다.

자료는 PubMed에 연결된 원연구의 초록과 공개 원문, 기존 해부학 자료를 대조했다. 유료 원문 전체를 읽었다고 주장하지 않는다. 아래 ‘직접’은 유사한 이름의 동작을 실험했다는 뜻이며, 앱 사용자의 수행 자세·중량까지 동일하다는 뜻이 아니다. **직접 관측한 근육 목록, 해부학적 보조 역할 추론, 제품의 수치 가중치는 서로 다르다.** 모든 근육을 EMG로 동시에 검증한 표가 아니다.

### 해석과 묶음

- 표면 EMG 크기는 개인의 근육 피로 %, 근손상, 회복 완료 시각이 아니다. 다른 실험의 정규화 EMG를 서로 더하지 않는다.
- ‘팔 앞쪽’은 이두근+상완근, 전완은 상완요골근을 포함한다. 중·소둔근은 ‘옆 엉덩이’, 비복근·가자미근은 ‘종아리’로 묶는다.
- Y 레이즈의 하부 승모근과 업라이트로우의 상부 승모근, 레이즈 방향별 삼각근 차이는 연구 설명에 남긴다. 현재는 하나의 표시 그룹으로 합산하므로 근두별 선택적 피로를 보여 주는 정밀 모델은 아니다.
- 장요근 전체는 현재 표면 모델에 없다. 고관절 굽힘근의 숫자는 근육군 추정이며 색은 모델에 있는 봉공근만 연결한다. 이 한계를 해당 부위 선택 시 표시한다.
- 늑간근·목 근육 등은 모델에는 있어도 이번 26종의 독립 부하 근거가 부족해 임의의 피로값을 부여하지 않는다.

## 2. 피로 추정식

기존 [§80 설계](MUSCLE_SESSION_FATIGUE_DESIGN.md)를 구현한다. 아래 상수 전부는 **제품 초기값**이며 논문에서 검증된 범용 수치가 아니다.

```
반복 운동의 기준량 = 수행 횟수 / 12
시간 운동의 기준량 = 실제 가동 초 / 45
맨몸 체격 보정 B = clamp(((체중/70) × (키/170))^0.25, 0.85, 1.15)
기구 운동 B = 1 (중량을 모르는 상태에서 키·체중으로 덤벨 무게를 지어내지 않음)
근육별 세트 부하 D = 기준량 × B × 종목별 역할 가중치
남는 부하 K(h) = 0.35 × 2^(-h/6) + 0.65 × 2^(-h/24)
현재 잠재 부하 L = Σ(D × K)
화면 점수 = 100 × (1 - exp(-L/6))
```

역할 가중치의 정확한 정본은 `trainingload/MuscleLoad.kt`다. 합계가 1이 아니며 에너지 비율이 아니다. 70kg/170cm의 기본 스쿼트 12회 × 3세트에서 앞 허벅지 즉시 지수는 약 39.35점, 24시간 뒤 약 15.92점이다. 다른 체형·종목과 실제 피로를 비교하는 검증값으로 쓰지 않는다.

회복 방향성은 [실패까지 수행한 저항운동의 회복 연구](https://pubmed.ncbi.nlm.nih.gov/28965198/), [서로 다른 저항훈련 프로토콜의 급성 피로 연구](https://pubmed.ncbi.nlm.nih.gov/30036284/), [RIR와 회복 연구](https://pubmed.ncbi.nlm.nih.gov/36752989/)를 참고했다. 운동량뿐 아니라 실패 접근도·프로토콜에 따라 회복 반응이 다르므로 현재 입력만으로 개인 회복 상수를 식별할 수 없다. 정식 3CC/3CCr 생리모델을 재현했다고 부르지 않는다.

### 단위·정확도 정책

1. 런지 4종: 표시 1회는 좌우 한 번씩. 12쌍을 양쪽 각각 24회로 중복 계산하지 않는다.
2. `repSides.track`이 있으면 좌우 원본을 사용한다. COACH의 차단 걸음도 실제 움직임의 부하이므로 COACH 성공 횟수로 낮추지 않는다.
3. `unknown`은 이미 좌/우 풀에 포함된 수다. **다시 더하지 않는다.** `extra`는 목표를 채운 쪽의 추가 걸음이며 보고서에 좌우별 수가 없으므로 균등 배분하고 출처를 표시한다.
4. 한쪽만 수행해서 화면이 0쌍이어도 TRACK 걸음 또는 미완성 반쪽이 있으면 부분 세트로 기록한다.
5. 스탠딩 사이드 크런치·니업·시저 크로스의 카운터는 단일 사이클이며 좌우를 보증하지 않는다. 제품 초기 가정은 교대 동작으로 보고 양쪽에 절반씩 배분한다. 양쪽 동시 동작과 구분하지 못하는 불확실성을 안내한다. 카운터 자체 단위를 변경하지 않는다.
6. 플랭크: 준비·휴식·일시정지 제외 `workMillis`로 계산. 부분 수행도 반영. 목표 45초를 실제 수행으로 대체하지 않는다.
7. 사용자가 완료/기록 화면에서 수정한 `actualReps`가 우선. 해당 수정이 있으면 이전 좌우 관측과 섞지 않고 그 단위로 재분배한다. 수정 해제 시 원 관측으로 돌아간다.
8. ship 자세 정확도·판정 수·유보 수는 원본 메타데이터로 보존하지만 **피로 배율로 사용하지 않는다**. TRACK/null/ABSTAIN을 100점으로 치환하지 않는다.

## 3. DB 설계와 선택 이유

현재 앱은 SharedPreferences JSON에 날짜별 최근 7일 기록을 저장한다. 같은 날 세션이 교체되고 오래된 날은 삭제되므로 이 저장소만 피로의 정본으로 쓰면 누적이 끊긴다.

**기기 내 SQLiteOpenHelper, DB `muscle_load.db` v1**을 추가했다. 네트워크·계정·새 ORM 의존성 없이 Android 기본 트랜잭션/외래키/WAL을 사용한다. 현재 규모와 오프라인 요구에는 충분하다. 기존 식단·프로필 저장소를 교체하지 않는다.

| 테이블 | 키/인덱스 | 내용과 이유 |
|---|---|---|
| `load_sets` | PK `id`, 시각 인덱스 `ended_at`, 라벨 인덱스 `posture_set_id` | `session_id`, `exercise_id`, `model_version`과 세트 원본 JSON. 횟수/초/좌우/추정 출처/완료 시각/시간 오차/당시 키·체중/수정 횟수/자세 메타데이터를 보존. 조회 키는 타입 컬럼, 앞으로 늘어날 원본 필드는 JSON |
| `muscle_doses` | PK `(set_id,muscle_id,side)`, FK `set_id` 삭제 연쇄 | 세트 → 근육군·좌우 기본 부하. 같은 ID 갱신 때 원본과 함께 원자적으로 재생성. 계산된 현재 색은 저장하지 않음 |
| `load_meta` | PK `key` | `legacy_v1` 이관 완료 마커. 매 시작마다 이전 기록을 다시 추가하지 않음 |

운동별 근육 연결/근거/가중치는 버전이 있는 Kotlin 카탈로그로 배포한다. 사용자마다 동일 연구 자료와 3D 메시를 DB에 복제하지 않는다. 메시·Three.js는 APK 자산이며 근육 ID로만 연결한다.

### 기록 흐름

```
세트 마감 → 실제 횟수/시간/좌우 + 완료 시각
→ 사용자가 기록 저장 / 정상 세션 완료
→ SharedPreferences 기록에 stable LoadSet 원본을 함께 저장(재전송 가능)
→ IO 큐 + Mutex → SQLite 원본/근육별 부하를 같은 트랜잭션에 upsert
→ 메모리에 원본/파생 부하 캐시
→ Default 스레드에서 경과 시간만 재계산
→ 홈 요약 · 3D 색 · 부위별 목록 · 추천 후보
```

- 세션 진입마다 UUID, 세트 단계의 Workout ID와 합쳐 세트 PK를 만든다. 회전/복원은 `rememberSaveable`에 같은 UUID와 마감 시각을 보존한다.
- 같은 세트 재저장: 교체. 다른 세션: 추가. 미완료 세트를 종료했다가 다시 시작하면 새 수행으로 기록하며 기존 부분 수행의 시간을 새 수행에 다시 더하지 않는다.
- 이전에 완료한 계획 항목은 새 세션에서 직접 마감한 token이 아니면 원장에 재전송하지 않는다.
- 날짜별 운동 기록도 `mergeSession`으로 누적하도록 고쳤다. 동일 LoadSet ID만 갱신한다. 운동 기록 화면의 7일 보관 정책은 그대로, 부하 원장은 90일 보관한다.
- 앱 복귀/30초 주기에는 DB를 매번 갱신하지 않고 메모리의 부하와 현재 시각만 계산한다. 화면 재계산은 Default, 저장/읽기는 IO에서 실행한다.
- DB 오류 시 기록 원본은 기존 저장소에 남으며 재시도 버튼/재시작으로 같은 ID를 재전송한다. SQLite 오류를 0점으로 표시하지 않는다. 다만 기존 7일 저장소의 재전송 보존 기간을 넘겨 장기간 DB 쓰기가 실패하면 해당 입력을 복구할 수 없는 제한이 있다.
- 원본 프로필이 없는 구기록은 이관 당시 프로필로만 추정한다. 시각은 해당 날짜의 시작~끝(오늘이면 현재까지) 범위와 중앙값을 보존하고 ‘이전 기록 추정’으로 표시한다. 시간 수행량이 없으면 목표 시간을 대입하지 않는다. 이미 삭제된 7일 이전 기록은 복원하지 못한다.
- 구기록 이관과 마커는 같은 트랜잭션. 라벨 수정은 `posture_set_id`로 현재/이전 원장과 부하를 갱신한다. 실패 뒤 재시작에도 보존된 라벨로 재시도한다.
- 향후 가중치/모델 버전 변경 시 원본 보존 후 `muscle_doses`를 재생성하는 명시적 마이그레이션을 추가한다. 현재 `onUpgrade`에는 무조건 삭제/재생성 경로가 없다.

### 규모와 다음 확장

하루 20세트 × 90일이면 원본 1,800건, 세트당 평균 5근육 × 2좌우로 부하 약 18,000건이다. 현재는 두 번의 순차 조회로 원장과 부하를 읽고 메모리 캐시를 쓴다. 현재 색을 매분 DB에 쓰는 구조보다 쓰기 횟수·DB 팽창이 적다. 이 수치는 용량 추정이며 기기 성능 벤치마크 결과가 아니다.

여러 사용자 계정·서버 동기화가 생기면 `owner_id`, 삭제 tombstone, 이벤트 revision, 세션 타임존, 독립적인 영속 outbox와 동기화 충돌 규칙을 먼저 추가한다. 현재 앱 로그인은 실제 계정 분리 저장소가 아니며 기존과 같이 기기 프로필 하나를 사용한다.

## 8. 완료 화면 사용 근육도 (§83, 2026-09-28)

§82의 완료 화면 점수 카드를 사용 부위 근육도로 대체했다. 카드 제목·설명·점수·펼치기·피로도 보기 버튼을 제거한다. 화면에는 모델만 표시하며 정상 상태의 추가 안내 문구를 넣지 않는다.

`sessionUsedMuscles`는 저장된 현재 세션 UUID만 대상으로 세트 ID 중복을 정리하고, 실제 수행량에 의한 양의 부하가 있는 근육/좌우 키를 추출한다. 양의 수행량이 있는 모든 관련 부위를 동일한 최대 강조색으로 표시한다. **100은 표시 농도일 뿐 피로 점수나 근활성 측정이 아니다.** 누적 피로·감쇠·다른 세션을 사용 부위 표시와 섞지 않으며, 수행량 0이나 횟수 0으로 수정한 기록은 강조하지 않는다. 한쪽 수행과 부분 시간 기록을 처리한다.

완료 화면의 `mode=session`은 한 모델만 표시하며 앞/뒤 버튼을 숨긴다. 수평 드래그는 360도 회전, 수직 드래그는 제한된 고도 변경이다. 포인터 캡처/취소를 처리하며 방향키와 Home 정면 복귀도 지원한다. Android WebView는 안쪽 드래그 시 부모 스크롤 가로채기를 제한하고 손을 떼면 해제한다. 밖의 영역은 페이지 스크롤을 유지한다. 재계산 시 WebView를 재생성하지 않아 회전 각도가 유지된다.

피로도 페이지의 색·앞뒤 보기·계산은 유지한다. 완료 전용 `setUsedMuscles`와 피로도용 `setFatigue` 입력을 분리한다. 동일 오프라인 자산과 기존 모델을 사용한다.

검증: JVM 476건(신규 3) 전부 통과, APK 빌드 통과. 실제 HTML/JS를 PC Chromium에서 표시해 강조/해제·피로 입력 무시·버튼/문구 숨김·마우스/터치 회전·정면 복귀·320px 넘침을 검사했고 정면/후면/사선 캡처를 확인했다. 별도 피로도 뷰어 회귀 검사도 통과했다. PC 검증 사진의 강조 값은 테스트용이며 앱에 저장하지 않는다. Android WebView/Compose 제스처 상호작용과 실휴대폰 화면은 검증하지 않았다. `outputs/session-muscle-map/verification.json` 및 `deployment.json`이 검증/설치 정본이다.


## 9. 완료 WebView 빈 화면 재현·수정 (§84, 2026-09-28)

- 사용자 관측: 마무리 화면에 근육도 대신 배경만 표시된다. PC 브라우저의 §83 검증으로는 Android WebView 결함을 검출하지 못했다.
- **PC Android 에뮬레이터에서 수정 전 현상을 재현했다.** 실제 `SessionCompleteScreen`의 스크롤 안에 `SessionMuscleMap`을 배치한 테스트에서 WebView `innerHeight=400`이지만 CSS `100vh`의 `stageH=0`이었다. 캔버스 생성/ready만으로는 렌더 성공을 보장하지 못한다.
- 완료 모드의 높이를 400 CSS px 폴백 + 실제 `innerHeight`에 따른 픽셀 높이로 지정한다. 0 크기에서는 카메라 투영/버퍼 갱신을 하지 않는다. 창 크기/다시 표시 이벤트에서 크기를 동기화한다.
- 완료 모드의 불필요한 후면 복제 메시를 생성하지 않는다. 정점 변환의 중간 일반 배열을 없애고, 픽셀 비율을 최대 1.5로 제한하며, 한 프레임에 여러 번 들어오는 렌더 요청을 하나로 모은다. 연속 애니메이션 루프는 두지 않는다. `outputColorSpace`를 사용한다.
- 완료 요약의 ‘참고만 하세요’ 문장을 제거했다. REFERENCE는 교정 헤드라인 대신 ‘운동별 자세 기록을 저장했어요’를 사용한다. 펼친 참고 항목은 ‘검증 중’ 표기로 유지한다. ship/ABSTAIN/정확도 판정과 라이브 엔진은 변경하지 않는다.
- **요청 범위만 검증:** 완료 문구 2건 + 현재 세션 사용 근육 3건의 JVM 테스트 통과. Android 에뮬레이터 검사 1건에서 stage 높이 400, 인체/강조 픽셀, 실제 터치 드래그 후 회전 및 부모 페이지 위치 불변을 확인했다. 일반 APK 빌드 통과. 전체 앱 회귀/운동 검증은 실행하지 않았다.
- 증빙: `outputs/session-muscle-fix/verification.json`, 수정 전후 `before.png`/`after.png`, 회전 `after-drag.png`, 설치 `deployment.json`. 초기 테스트 호스트가 원래 메인 콘텐츠를 보여 주던 문제를 수정해 ComponentActivity의 독립 완료 화면으로 한정한 뒤 위 재현/검증을 수행했다.
- 실휴대폰은 기존 관련 로그만 읽었으며 앱 실행·화면 조작은 하지 않는다. 업데이트 설치만 수행한다. 검증용 에뮬레이터에 설치한 replay 앱/테스트와 임시 저장 공간 설정은 제거/복원했다.

## 11. (§86) 완료 카드 내부 제목 · 조건부 스크롤 · 양옆 입력 여백 (2026-09-28)

완료 3D 제목은 ‘사용 근육’으로 변경해 어두운 카드 내부 상단에 배치하고,

입력을 가로채지 않는다. 제목 영역 역시 WebView 밖이다.
