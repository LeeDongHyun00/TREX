- **상태:** 제안. 구현·앱 생성·빌드·설치·테스트 실행 전이다.
- **작성 범위:** Mac 담당의 실행·검증 계획. [ADR-056](../IOS_POSTURE_KMP_DESIGN.md)을 구체화하는 검토 문서이며 정본 설계/API를 독자 변경하지 않는다.

- **앱 소스 기준:** `5237ba9d07662849fc2b23853672049ff2a950af`. 공통 API 커밋은 아직 없다.
- **관련 상태:** [Mac](MAC_STATUS.md), [Windows](WINDOWS_STATUS.md), [협업 규약](../IOS_KMP_COLLABORATION.md)

## 1. 만들 결과와 순서

자세 계산·반복·개인 비교·세트 상태·음성 자격은 **KMP 엔진 한 개**로 공유한다. Android는 기존 Compose 화면을 유지하고 iOS는 자세 기능만 담은 SwiftUI 검증 앱부터 만든다. 양쪽 카메라/MediaPipe/중력 센서는 동일한 입력 계약을 만들고, UI·TTS·파일 저장은 엔진이 반환한 결과와 효과를 실행한다.

진행 순서는 **개발 경로 확인 + 기존 Android 기준 확보 → 공통 계산 추출 → 공통 세션 추출 → iOS 카메라 연결 → 두 플랫폼 회귀 검증**이다. 실제 기기 연결은 첫 조건 하나를 충족한 것이며 빌드·계산 동등성·촬영 정확도를 대신하지 않는다.

첫 iOS 범위는 준비/운동/휴식/완료, COACH/TRACK, 일시정지·건너뛰기·수동 횟수 수정, 로컬 세트 기록이다. 로그인·식단·클라우드 동기화·앱 전체 UI 이전·규칙/모델 교체·beta 승격·스토어 출시는 이번 확장의 범위에 넣지 않는다. iOS 16+는 기존 개발 deployment target 제안으로 유지한다. 연결 기기가 iOS 27이라는 이유로 최소 지원 OS를 27로 바꾸지 않는다.

## 2. 연결된 장비와 개발 환경의 역할

| 장비 | 확인한 상태 | 구현에서 맡길 역할 | 아직 확인하지 않은 것 |
|---|---|---|---|
| 현재 Intel Mac | macOS 14.8.4, Xcode 16.2, SDK 18.2, Java 21, Gradle 8.13, CocoaPods 1.16.2 | 문서/API 검토, 두 USB 기기의 로컬 실행·결과 회수, 현재 환경의 빌드 가능성 확인 | Kotlin/Native 및 새 iOS 앱 빌드·서명·실행 |
| iPhone 16 Plus | 유선 `connected`, `paired`, `available`, Developer Mode `enabled`, DDI 서비스 사용 가능. 실제 조회 iOS **27.0 Beta**, build `24A5424a` | iOS 어댑터, 카메라·센서·TTS·중단·장시간 검증 | TREX 빌드/설치/디버깅 성공 및 안정 OS에서의 동작 |
| Galaxy Note10+ 5G (`SM-N976N`) | USB ADB `device`, Android **12**, API **31**, 셸 응답 정상 | 같은 단말에서 기존/공통 엔진의 Android 기준·회귀·성능 비교 | 설치 앱과 소스의 일치, 기존 데이터 백업, 이번 빌드 테스트 |
| Windows 작업 환경 | 원격 상태 문서에는 아직 P0/P1 구현 없음 | Android·공통 코드·테스트·Gradle·정본 자산 담당 | 현재 Windows 실행 환경/기기 원격 접근은 이 세션에서 확인하지 않음 |

**두 휴대폰은 현재 Mac에 연결돼 있다.** Windows가 이 단말에 직접 `adb`를 실행할 수 있다고 가정하지 않는다. Windows는 정확한 소스 SHA와 재현 명령을 공유하고, Mac이 같은 소스를 빌드하거나 전달받은 테스트 산출물을 검증한 뒤 기기에서 실행한다. Android 테스트 코드/계측 추가는 Windows가 담당한다. Mac의 Android 역할은 실행과 결과 보고이며 `app/` 소유권을 가져오지 않는다.

### 구현 착수 후 첫 검사: 개발 경로를 작은 단위로 입증

1. **현재 장비부터 검사한다.** 엔진 없는 별도 iOS 진단 앱으로 arm64 빌드 → 서명 → iPhone 설치 → 실행/로그 회수를 순서대로 확인한다. 각 단계의 성공/실패를 따로 남기고 기존 앱을 덮어쓰지 않는다. 계정/서명 설정이 없으면 빌드 결과와 서명 대기를 분리한다. 이 진단 앱은 공통 엔진이나 자세 판정을 포함하지 않는다.
2. **KMP/Pod 검증은 독립 조건이다.** P1에서 Windows가 공유한 최소 계산 모듈을 받은 뒤 Native framework 생성, Swift에서 실제 API 호출, 같은 입력의 반환값 확인을 수행한다. MediaPipe Pod 해석/링크/모델 초기화는 이 검사와 따로 기록한다. 순수 Swift 앱 실행 성공만으로 KMP·MediaPipe도 된다고 판단하지 않는다.
3. **도구 조합이 막히면 원인을 한정한다.** 현재 Kotlin **2.3.21**의 공식 Xcode 호환 기준은 **26.0**이다. iOS 27 SDK를 포함한 Apple의 최신 표는 **Xcode 27 RC / macOS Tahoe 26.6 이상**을 기재한다. Xcode 16.2에서 기기 연결이 가능하다는 사실은 이 두 조합의 빌드 호환성을 입증하지 않는다. 실패 로그를 남긴 뒤 지원되는 Apple Silicon Mac/빌드 환경을 검증 경로로 제안한다. 새 Xcode와 기존 Kotlin 조합도 실제 빌드로 확인하며 필요 버전 변경은 Windows가 별도 변경으로 검토한다. [Kotlin 호환 표](https://kotlinlang.org/docs/multiplatform/multiplatform-compatibility-guide.html), [Apple Xcode 요구 사항](https://developer.apple.com/xcode/system-requirements)
4. **타깃을 구분한다.** 실제 iPhone용 `iosArm64`와 Apple Silicon 시뮬레이터용 `iosSimulatorArm64`를 기본으로 둔다. 현재 Intel Mac에서 시뮬레이터를 실행하는 경로가 필요할 때만 `iosX64`를 Windows와 합의해 추가한다. Intel이라는 이유만으로 실제 iPhone의 arm64 타깃을 x64로 바꾸지 않는다. Native 타깃 컴파일과 해당 타깃 테스트 실행은 별개다. [Kotlin Native 타깃/호스트](https://kotlinlang.org/docs/native-target-support.html)

이 검사를 이유로 현재 Mac OS/Xcode를 자동 업그레이드하거나 iPhone OS를 내리거나 프로젝트 Kotlin을 임의 하향하지 않는다. 현재 환경에서 실패한 동일 명령을 원인 변화 없이 반복하지 않고, 실패한 단계만 보류한다. Windows의 기준 확보는 독립적으로 진행할 수 있다. iOS 경로가 미검증이면 공통 엔진을 기존 Android 기본 경로로 전환하지 않는다.

## 3. 담당별 작업 묶음과 완료 조건

아래 파일·산출물 이름은 구현 계획이다. 아직 존재하는 모듈/API/Gradle 작업으로 해석하지 않는다. Windows와 Mac은 각자 작업 브랜치만 쓰고, 검토한 커밋을 `codex/ios-posture-kmp`에 통합한다.

0A와 0B는 서로의 실행을 기다릴 필요가 없다. P1/P2도 JVM 결과까지만 공유할 수는 있으나 **Native 검사 없이 단계 완료로 표시하지 않는다.** iOS 정확도/장비 문제가 공통 수치 기대값을 바꾸는 근거가 되지 않게 한다.

## 4. 구현 전에 고정할 계약

| 계약 | 구체화할 내용 |
|---|---|
| 입력 경계 | 원본 MP 33관절 world/normalized 2D, 존재 마스크·visibility/presence, 회전 보정 뒤 분석 이미지 크기. 공통 변환이 `x*100, -y*100, -z*100`을 한 번 적용한다. `CVPixelBuffer`·MP SDK 타입은 엔진 밖이다. |
| 시간·수명 | `sampleTimeMs`는 단조 시간이며 0도 유효하다. `sessionId/setToken/phaseEpoch/captureEpoch`는 추론 시작 전에 붙인다. 프레임은 제출 시 복사하고 한 직렬 진입점만 상태를 바꾼다. |
| 처리·마감 | 동시 추론 1건, 대기 영상은 최신 1장. 준비/일시정지/이전 촬영의 늦은 결과는 거부한다. 마감 당시 접수된 프레임으로 한 번 확정하며 결과를 전달한 뒤 다음 운동으로 간다. 저장 성공은 별도 상태다. |
| 결과 | Snapshot과 순서 있는 효과를 반환한다. SHIP 분수의 분모는 실제 판정 수, TRACK/0판정은 점수 없음. ABSTAIN·EXCLUDE를 정상으로 채우지 않는다. 자동 횟수와 사용자가 수정한 기록 수를 분리한다. |
| 음성 | 엔진은 문구·자격·만료·이벤트 ID를 결정하고 OS가 요청/시작/완료/취소/실패를 보고한다. beta 위반·복귀는 음성 차단, TRACK은 실제 초반 대비 변화만 읽는다. 이전 모드/세트의 늦은 TTS가 새 세트로 넘어가지 않는다. |
| 자산·로그 | 같은 규칙/모델/표본 해시를 사용한다. 구형 v1 로그를 보존하고 새 플랫폼·계약/정책 버전을 구분한다. 여러 촬영 구간과 iOS 로그를 기존 Android 재보정 자료에 자동 합치지 않는다. |

Swift의 최초 API는 작은 facade와 값 중심 DTO로 제한한다. nullable/Long/배열/오류가 Swift에서 어떻게 보이는지는 생성 헤더와 실제 호출 코드로 확정한다. 제안 `create/openSession/send/accept/tick/close`의 정확한 시그니처와 테스트 작업 이름은 Windows P1/P2 커밋을 받은 후 기록한다.

`TrexPosture`는 Gradle 직접 연결, `MediaPipeTasksVision`은 Swift 앱의 CocoaPods 의존성으로 분리한다. 동일 framework를 두 경로로 링크하지 않는다. 직접 연결 작업은 `binaries.framework`가 설정돼야 생성되므로 지금 존재한다고 가정하지 않는다. [KMP 직접 연결](https://kotlinlang.org/docs/multiplatform/multiplatform-direct-integration.html), [MediaPipe iOS API](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/ios)

## 5. iOS 검증 앱의 사용자 흐름

1. **운동/모드 선택:** 처음에는 아래 5운동과 COACH/TRACK만 노출한다. 기존 프로필의 앱 이름/규칙 이름 매핑을 그대로 쓴다.
2. **촬영 준비:** 카메라 미리보기, 사용자 기준 촬영 방향, 전신/필요 부위 상태, 기존 5초 준비와 준비 건너뛰기를 제공한다. 준비 프레임·시간은 평가/기준/횟수/기록에 포함하지 않는다.
3. **운동:** 영상, 반복 또는 시간 목표, 필요한 안내와 일시정지·음성·카메라·건너뛰기 조작을 제공한다. 패널을 접거나 화면을 다시 그려도 같은 카메라 세션을 유지한다. 초기 기준 수집과 교정 판정을 분리한다.
4. **휴식/다음 세트:** 공통 진행기가 목표 도달·사용자 완료·건너뛰기를 처리한다. 권한 거부/추론 실패는 같은 운동의 타이머·직접 기록으로 이어지며 운동을 완료한 것으로 건너뛰지 않는다.
5. **완료/기록:** 관측한 범위, 유보 사유, 자동/수동 횟수, 모드별 결과와 저장 상태를 표시한다. iOS 검증 앱임을 구분하고 iPhone 연결/빌드 성공을 올바른 자세 인증으로 표시하지 않는다.

## 6. 검증 설계

**동일 관절 입력의 계산 비교와 서로 다른 카메라 영상의 비교는 별개다.** 먼저 같은 추적 픽스처를 JVM/Native에 넣어 계산을 대조한다. 같은 사람이 두 폰 앞에서 운동해도 추론 좌표는 달라질 수 있으므로 실촬영 좌표의 완전 일치를 합격 기준으로 두지 않는다.

| 검증 층 | 입력·방법 | 합격 기준 |
|---|---|---|
| 계산 | 기존 posture/floor/view/plank 픽스처, 실제 규칙 JSON | 기존 피처별 오차 유지, 유효 키/결측 동일, 규칙 선택·OK/VIOLATION/ABSTAIN 동일 |
| 세션 | 0ms·프레임 공백·명령·음성/저장 콜백을 가진 같은 재생 입력 | 횟수·앵커/종료 시각·단계·이벤트 순서·최종 결과 일치. ADR §12의 명시적 변경만 별도 목표 기대값 사용 |
| 플랫폼 | 두 단말에서 준비·가림·회전/전후면·중단·TTS·저장 관찰 | 잘못된 좌우/축, 준비 프레임 혼입, 중복 마감/저장, 이전 세트 발화가 없어야 함. 실패/미관측을 결과에 명시 |
| 성능 | 같은 Note10+에서 변경 전후 release 비교, iPhone은 독립 기준 수집 | ADR 제안: 브리지+공통 처리 p95 ≤10ms, Android 전체 처리 회귀 ≤`max(5ms, 5%)`. 추론·브리지·계산·UI·저장과 워밍업을 분리 |

기존 `PostureCoreParityTest`는 각도 0.05°, 그 밖은 `max(1e-4, abs(expected)*1e-3)`를 사용한다. 바닥/플랭크/집계는 각 기존 테스트의 기준을 유지하며 이 수치를 전역으로 덮어쓰지 않는다. 수치 오차가 허용 범위여도 판정 경계가 달라지면 실패다.

| 첫 검증 운동: 앱 이름 → 규칙 이름 | 확인할 경로 |
|---|---|
| 기본 스쿼트 → 바벨 스쿼트 | 3D 피처·반복·첫 반복/시간 앵커·마지막 복귀 |
| 플랭크 → 플랭크 | 2D·중력/종횡비·유지·정렬·TRACK 기준 |
| 푸쉬업 → 푸시업 | 바닥 반복·몸통/고개·가림·참고 항목 |
| 런지 → 스텝 포워드 다이나믹 런지 | 교대 동작·WINDOW 비교·사용자 좌우 |
| 카프 레이즈 → 규칙 없음 | 규칙 없는 프로필의 개인 비교·수동 기록·점수 없음 |

기능 경로의 최소 매트릭스는 **5운동 × 2모드 × 2단말**이다. 이는 20개 연결 시나리오의 제안이며 사람별 정확도 표본 수가 아니다. 기존 재생 입력으로 먼저 확인하고 실제 운동 촬영의 종목/횟수/시간은 사용 가능한 검증 조건에 맞춰 따로 기록한다.

필수 경계 묶음은 (1) 검출 없음/한쪽 가림/NaN/0 크기, (2) 준비와 첫 반복/4초·10초/8프레임 경계, (3) 일시정지·백그라운드·건너뛰기 취소, (4) 카메라 전환·순수 프리뷰 크기 변경·늦은 프레임, (5) 목표/완료 동시 발생·중복 명령, (6) TTS 실패/만료/콜백 누락/이전 모드 발화, (7) 자산 오류·저장 실패/재시도, (8) 0판정·beta만·부분 관측·TRACK 점수 없음이다. 준비 설명 12초 대체 진행과 `completeOnReturn=true/maxGapMs=1500`인 현재 라이브 카운터 설정도 고정한다.

P4에는 20분 준비→운동→휴식, 긴 세트, 반복 전환의 열 상태·메모리·프레임 간격·저장 큐를 포함한다. 현재 iPhone은 베타 OS 한 종류뿐이므로 그 결과를 안정 OS/최소 지원 OS 전체 검증으로 확대하지 않는다. 대표 운동 통과 후 기존 카메라 프로필 55개의 자산/분기 연결을 검사하되 새 정확도/출시 인증으로 표기하지 않는다.

## 7. 산출물 교환·기존 데이터 보존·중단 기준

Windows가 넘길 묶음에는 소스/공통 API 커밋 SHA, 공개 타입과 소비 예제, 규칙·모델·픽스처 SHA-256, 기대 결과의 정책 버전, 빌드/재생 명령과 실제 결과를 담는다. APK를 전달한다면 applicationId·version·서명 인증서 지문·APK SHA-256도 함께 기록한다. Mac은 실행한 단말 모델/OS, 동일 SHA, 명령/종료 코드, 결과 차이와 성능 요약을 돌려준다. 기기 ID와 서명키는 공유 문서에 넣지 않는다.

Android는 기존 `-PpostureReplay` 분리 패키지 경로의 적용 범위를 먼저 확인한다. 테스트가 일반 앱의 루틴/운동 기록/설정을 지우지 않게 하고, 일반 앱 업데이트가 필요하면 로컬 백업·서명 일치·바이트 보존 검사를 거친다. 서명 불일치 해결을 위해 일반 앱을 삭제하지 않는다. iOS 진단/검증 앱의 bundle ID와 저장 영역도 기존 앱과 구분한다.

새 이벤트 재생 형식은 ADR의 `trex.posture.replay/1`을 따른다. 현재 `.gitignore`가 `*.jsonl`을 제외하므로 공유 입력은 익명화·최소화한 테스트용 `.json`/텍스트 또는 결정적 생성기로 제안한다. 개인 운동 로그/AIHub 원본을 `git add -f`로 공유하지 않는다. 빌드 산출물도 소스 이력에 넣지 않고 합의한 전달 경로를 쓴다.

계산·판정 불일치, 세트 경계 혼입, beta 음성, 중복 효과, 데이터 손실, 설명할 수 없는 성능 회귀가 있으면 다음 단계 완료/기본 엔진 전환을 보류한다. 기존 Android 엔진을 유지하며 새/구형 비교에서 사용자에게 음성·횟수·저장 효과를 내는 엔진은 하나뿐이다. 엔진 선택은 세트 시작 시 고정하고 롤백은 세트 사이에서 한다. 미관측을 정상으로 채워 검사를 통과시키지 않는다.

이번 작성에서 실행한 것은 소스/문서 검토, 원격 상태 확인과 문서 검사뿐이다. 진단 앱·공통 엔진·iOS 앱·새 테스트·계측은 만들지 않았다. 구현 착수 후 첫 보고는 **현재 iPhone 개발 경로의 단계별 결과와 Windows P0 기준 확보 상태**로 한다.
