# TREX — 목표 기반 운동 진행과 엄지 중심 UX 설계

2026-09-11 · 설계 당시 기록. **구현 범위·검증 상태는 [§42 구현 문서](THUMB_FIRST_UX_IMPLEMENTATION.md)가 정본이다.**

설계 시점의 코드·이미지 자산을 확인한 결과다. 이 문서는 §41의 ‘반복 수를 시간으로 환산해 자동 종료’ 결정을 대체하는 방향을 정했다. 실제 프레임 지연은 계측하지 않았으므로 성능 원인 후보와 확인된 코드 동작을 구분한다. 아래의 제안 전체가 구현됐다는 뜻은 아니며, 좌우 개별 목표/전환 등 남은 범위는 구현 문서를 따른다.

## 1. 운동 종료: 목표를 달성하면 끝난다

시간이 흘렀다는 사실과 운동 목표를 달성했다는 사실을 분리한다. `12회 × 3초`는 예상 소요 시간이며 세트 종료 조건이 될 수 없다. 플랭크의 `45초`는 운동 목표 자체이므로 시간 완료가 맞다.

| 단계/목표 | 가장 크게 표시 | 다음 단계로 이동 | 오른쪽 아래 | 왼쪽 아래 |
|---|---|---|---|---|
| 촬영 준비 | 종목·촬영 방향 | 사용자가 시작 | 시작 | 메뉴 |
| 반복 운동·자동 측정 | `8 / 12회` | 확정된 반복이 12회에 도달 | 일시정지 / 재개 | 횟수 수정 |
| 반복 운동·직접 기록 | `목표 12회` | 실제 수행 횟수를 사용자가 기록 | 횟수 기록 | 메뉴 |
| 시간 운동 | `00:18` + `목표 45초` | 사용자가 시작한 운동 시간이 45초에 도달 | 일시정지 / 재개 | 메뉴 |
| 휴식 | 남은 시간 + 다음 종목/세트 | 0초에서 다음 세트 | 휴식 끝내기 | 일시정지 |
| 좌우 전환·종목 전환 | 다음 방향/종목 | 사용자가 준비 완료 | 시작 | 메뉴 |

준비 5초/15초 자동 시작은 없앤다. 카메라 인식 준비 완료는 시작 버튼을 돕는 정보이며, 사용자가 원치 않는 자동 시작을 일으키지 않는다. 휴식 0초는 같은 운동의 다음 세트를 시작한다. 휴식 뒤 카메라 재배치나 반대쪽 자세 준비가 필요하면 준비 화면으로 이동하고 시작을 기다린다. 중단/앱 배경 전환 중에는 운동·휴식 시간이 흐르지 않는다.

반복 운동의 경과 시간은 필요할 때만 보조 정보로 제공한다. 예상 시간을 넘겨도 운동을 끝내거나 재촉하지 않는다. `1회 소요 시간` 설정은 종료 조건에서 제거하고, 필요하면 선택적인 속도 안내에만 사용한다.

### 현재 카탈로그 57개에 적용

기준은 종목명만이 아니라 **해당 루틴에 저장된 목표 단위**다. 같은 마운틴 클라이머도 20회 루틴과 30초 루틴을 표현할 수 있다. 현재 카탈로그 기본값은 다음과 같다.

| 기본 목표 | 종목 | 개수 |
|---|---|---:|
| 유지 시간 | 월 싯, 플랭크, 사이드 플랭크, 할로우 홀드, 힙 브릿지 홀드 | 5 |
| 운동 시간 | 제자리 걷기, 하이 니, 섀도 복싱 | 3 |
| 회복 시간 | 마무리 스트레칭, 캣카우 스트레칭, 차일드 포즈, 폼롤러 마무리, 햄스트링 스트레칭, 흉추 회전 스트레칭 | 6 |
| 반복 횟수 | 나머지 카탈로그 종목. 플랭크 숄더탭·버드독·데드버그·마운틴 클라이머·점핑잭 포함 | 43 |

이는 현재 저장된 단위의 분류이며 각 운동의 적정 처방 시간이라는 주장이 아니다. 예를 들어 `전신 4분`은 올바른 자세로 4분간 유지했다는 뜻으로 기록하면 안 된다.

좌우는 별도의 계약이 필요하다. 런지의 `10회`가 양쪽 합계인지 한쪽당인지 현재 문자열에는 없다. 새 설정에는 `합계 20회` / `좌우 각각 10회`를 명시한다. 한쪽씩 하는 동작은 좌→전환 준비→우를 한 세트 안의 구간으로 표현한다. 양쪽 완료 후 세트 간 휴식에 들어간다. 기존 기록의 ‘10회’를 임의로 20회로 바꾸지 않고 기존 합계 목표를 유지한다. 사이드 플랭크도 기존 30초를 몰래 60초로 늘리지 않는다.

### 횟수 자동 종료를 바로 연결할 수 없는 이유

`RepCounter.kt:106`은 상승 뒤 **다음 하강**이 최소 폭을 넘어야 이전 반복을 확정한다. 마지막 반복 뒤 멈추면 카운트가 안 올라간다. 현재 이 값을 종료 조건에 그대로 연결하면 목표보다 한 번 더 하게 된다. 코드 주석에 남은 실기기 라벨 결과도 12회 중 9회 검출이다.

다음 구현은 순서가 중요하다.

1. 완료 자세로 복귀한 반복을 다음 반복 없이 확정하는 종료 조건을 추가한다. 종목별 시작 자세·최소 이동·복귀·짧은 안정 구간을 함께 보고, 단순 정지나 준비 자세를 한 회로 세지 않는다.
2. 마지막 반복 확정과 다음 반전 이벤트가 같은 반복을 중복 집계하지 않도록 한다. 가림·일시정지·종목 전환 전후 프레임도 한 반복으로 잇지 않는다.
3. 검증된 반복 검출 이벤트만 세션에 전달한다. 카메라 자세 관측을 지원한다고 자동 횟수 측정까지 지원하는 것은 아니다. 미지원 종목은 ‘직접 기록’으로 명시한다.
4. 반복 수와 자세 평가는 별도 값으로 보존한다. beta 규칙이나 모집단 가동 범위에 어긋났다는 이유로 수행한 반복을 지우지 않는다. 검출기의 최소 움직임 조건과 자세가 ‘좋다’는 판정도 구분한다.
5. 횟수 누락 시 하단 ‘횟수 수정’에서 보정한다. 카메라 없이 12번 화면을 누르게 하지 않고, 세트 끝에 실제 횟수를 한 번 입력한다. 목표 미달은 부분 수행으로 기록하고 완료로 부풀리지 않는다.
6. 목표 도달 이벤트는 세트 ID별 한 번만 처리한다. 리포트 확정→짧은 완료 피드백→휴식 순서로 이어지며, 화면 애니메이션 완료를 기다리느라 목표 시간이 지연되지 않는다.

횟수 자동 종료를 모든 운동에 즉시 약속하면 안 된다. 신뢰할 수 있는 카운터가 없는 종목까지 시간으로 채우거나 유사 종목의 카운터를 붙여 해결한 척하지 않는다.

### 플랭크 시간의 의미

기본 표시와 종료 조건은 **사용자가 시작한 세트의 경과 시간**이다. 자세가 흐트러졌다고 타이머를 몰래 멈추거나 목표 시간을 연장하지 않는다. 카메라가 안 보이면 ‘자세를 확인하기 어려워요’를 표시하고, 관측 공백은 평가 기록에 남긴다. `45초 운동`을 `45초 올바른 자세 유지`라고 표시하지 않는다. 개인 비교를 위한 초기 5초 수집도 사용자가 이미 시작한 운동 시간에 포함한다.

### 다음 코드 변경의 경계

- `WorkoutTarget.Repetitions(count, sidePolicy)` / `WorkoutTarget.Duration(seconds, sidePolicy)`를 명시적으로 저장한다. 문자열 해석은 기존 데이터 마이그레이션 경계로 한정한다.
- `ObservationKind.REPS/HOLD/WINDOW/GUIDE`는 자세 비교 방식이다. 운동 목표 단위로 재사용하지 않는다. `WINDOW` 동작에도 횟수 목표와 시간 목표가 모두 있다.
- `SessionProgress`는 시작·반복 확정·수동 보정·시간 도달·일시정지·건너뛰기 이벤트를 받는다. 준비와 횟수 운동에는 만료 시각을 두지 않는다.
- `TrexApp.kt:214`의 모든 단계 공통 0초 전환을 없애고 휴식/시간 목표에만 적용한다. 기존 token 중복 방지와 리포트 선확정은 유지한다.
- 권한 거부 시 `타이머로 계속`은 목표에 따라 `직접 기록으로 계속` / `시간 측정으로 계속`으로 나눈다.
- 설정은 반복 운동 `횟수·세트·휴식`, 시간 운동 `시간·세트·휴식`. 예상 소요 시간과 실제 기록 시간을 분리한다.

## 2. 화면: 상단은 읽고, 하단은 조작한다

사용자의 엄지 우선순위를 제품 전체에 일관되게 적용한다. 오른쪽 아래는 현재 화면의 가장 중요한 동작, 왼쪽 아래는 가장 자주 쓰는 보조 동작이다. 상단에는 별도 조작을 요구하지 않는다. 콘텐츠 스크롤은 허용하지만 항목 선택·편집·드래그를 상단에서 요구하지 않는다.

다만 모든 항목을 하단에서 이전/다음 버튼으로 하나씩 선택하게 만들면 긴 목록에서 조작이 늘어난다. **상단 요약 목록은 읽기 전용, 편집할 때는 선택할 목록 자체를 하단 시트로 가져오는 방식**을 권한다. 시트의 목록은 엄지로 스크롤할 수 있고 저장·닫기는 하단에 고정한다. 키보드가 뜨면 입력 구간과 완료 버튼도 키보드 위로 올라온다.

프로필/기록도 같은 원칙을 적용한다. 상세 카드 클릭을 기본 조작으로 삼지 않고 하단에서 기록/날짜를 선택한다. 단, 앱의 원칙을 강제하느라 Android 시스템 뒤로 가기·접근성 포커스·키보드 탐색을 막지 않는다.

### 운동 페이지에서 남길 것

제목 ‘오늘 운동’ → `4종목 · 12세트` → 종목명과 `12회 × 3세트` / `45초 × 3세트` → 필요한 경우 `휴식 60초` → 하단 조작부. 한 행의 이름과 목표를 같은 정렬축에 둔다. 다음 종목만 작은 표시로 구별하고, 완료는 체크와 글자로 구별한다.

기본 화면에서 제외할 것은 코드에 고정된 `비 예보·6.4 mm/h` 카드, 반복되는 실내 추천, 종목마다 다른 색 칩, 중첩 테두리·그림자, 조작 방법 상주 문장, 일반적인 부위별 코칭 문구다. 특히 모든 하체 종목에 같은 ‘무릎이 발끝을 넘지 않게’ 문구를 보여주는 현재 방식은 종목·동작을 관측한 코칭과 혼동된다.

자세 교정의 한계는 숨기지 않는다. 기본에는 ‘자세 비교 켜짐’ 정도의 상태를 두고 하단 ‘측정 안내’에 실제 평가 범위·참고 항목·못 보는 항목을 보여준다. 판단 불가일 때에는 ‘측정 어려움’을 기본 화면에도 표시한다. 설명을 줄인다는 이유로 참고 판정을 정상·교정 확정으로 승격하지 않는다.

### 시각 언어

- 목록은 여백·정렬·얇은 구분선으로 묶는다. 개별 행마다 둥근 상자와 그림자를 두지 않는다. 떠 있는 표면은 하단 조작부와 편집 시트에 집중한다.
- 제목, 주요 숫자, 본문, 보조 문구의 네 단계로 제한한다. 주요 숫자는 고정폭 숫자로 흔들림을 막는다. 긴 문장을 작은 글씨로 눌러 넣지 않는다.
- 브랜드 색은 기본 동작과 선택 상태에 집중한다. 측정 결과는 색뿐 아니라 글자로 표현한다.
- 기본 설명은 사용자가 지금 할 행동 한 문장. ‘OO를 시작합니다’, ‘AI가 정확하게 분석해요’ 같은 선언형 문장은 제거한다.
- Android 터치 영역은 48dp 이상, 주요 버튼은 56dp를 출발점으로 삼는다. 화면 끝·제스처 영역에는 여백을 둔다. 고정된 절대 화면 좌표가 아니라 하단 안전 영역에 배치한다.

Apple의 일관된 위치·명확한 피드백·사용자 주도권 원칙을 이 앱의 엄지 조작 철학과 연결한 제안이다. 특정 재질이나 효과를 모든 면에 적용하는 규칙은 아니다. [Apple Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles)

### 동작과 애니메이션

아래 수치는 TREX를 위한 초기 시안 값이며 Apple의 공식 권장 시간이 아니다.

| 동작 | 제안 | 목적 |
|---|---|---|
| 버튼 누름 | 90~120ms의 작은 눌림, 손을 떼면 복귀 | 입력이 받아들여졌음을 즉시 표시 |
| 하단 메뉴→기능 | 220~280ms, 오른쪽 주요 버튼의 위치 고정, 내부 아이콘·문구 중심 전환 | 엄지가 향하던 목표가 도망가지 않게 함 |
| 탭 콘텐츠 | 180~220ms, 짧은 이동과 투명도 전환 | 화면 전환을 알리되 넓은 화면이 오래 미끄러지지 않게 함 |
| 편집 시트 | 240~300ms, 아래에서 올라오며 손동작으로 되돌리기 가능 | 조작 공간의 출처를 설명 |
| 횟수 증가 | 숫자 영역만 100~140ms, 크기/줄 높이 유지 | 운동 중 주변 요소가 출렁이지 않게 함 |
| 세트 완료→휴식 | 짧은 체크와 햅틱/톤, 180~220ms 교체 | 완료를 알리고 다음 상태를 즉시 제공 |

화면·카드 높이·버튼 너비·글자·그림자를 동시에 크게 움직이지 않는다. 잦은 동작은 짧고 중단 가능해야 한다. 시스템 애니메이션 비활성/감소 설정을 존중하고, 움직임을 없애도 상태 변화는 읽을 수 있어야 한다. [Apple Motion](https://developer.apple.com/design/human-interface-guidelines/motion)

하단 버튼이 바뀌는 순간의 연속 탭이 다음 세트 시작이나 휴식 건너뛰기로 새어 들어가지 않도록 이벤트를 단계 ID에 결합한다. ‘애니메이션 중 전체 화면 입력 잠금’으로 해결하지 않는다.

## 3. 운동 탭 첫 진입 지연

### 코드로 확인된 동작

- `TrexApp.kt:401`: 운동/식단 탭 진입 후 260ms 기다렸다가 하단 메뉴 변형을 시작한다.
- `TrexApp.kt:569`: 그 뒤 버튼 weight를 400ms, alpha를 260ms, 높이를 300ms 동안 움직인다. 전체 하단 형태가 정착하는 설계 시간은 약 660ms다. **660ms 프레임 정지가 측정됐다는 뜻은 아니다.**
- 동시에 본문은 `AnimatedContent`에서 340ms 동안 이전/다음 화면을 이동·페이드한다.
- `MainScreens.kt:318`: 첫 미완료 운동이 처음부터 펼쳐져 있고, 카드 전체가 `animateContentSize(320)`을 사용한다. scope 비동기 결과 도착 시 내용에 영향을 줄 수 있다.
- 목록에는 이미 LazyColumn과 stable key가 있다. `PostureScopeUi.kt:58`도 이미 IO에서 규칙을 읽고 캐시한다. ‘JSON을 메인 스레드에서 읽어서 그렇다’는 진단은 현재 코드에 맞지 않는다.
- AppViewModel의 계획 로드는 앱 루트 생성 단계다. 운동 탭을 누를 때 처음 디스크에서 계획을 읽는다고 단정할 근거가 없다.

### 개선 순서

1. 260ms 지연을 없애고 본문·하단 전환을 같은 입력에 즉시 반응시킨다. 오른쪽 주요 버튼의 공간을 안정적으로 유지한다.
2. 운동 탭의 첫 프레임은 접힌 평면 목록으로 구성한다. 사용자 요청 전에는 설정·평가 범위·긴 설명을 본문에 펼치지 않는다.
3. 비동기 결과 도착으로 행 높이가 움직이지 않게 한다. 캐시 완료 전에도 종목명·목표·시작 버튼은 바로 쓸 수 있어야 한다.
4. 실제 기기의 non-debuggable/profileable 빌드에서 첫 진입과 재진입을 분리해 System Trace/Macrobenchmark로 계측한다. `frameOverrunMs`의 분포, 긴 프레임, 최초 응답, 사용 가능한 화면까지의 시간을 기록한다.
5. 초기 Compose 실행/JIT가 병목으로 확인되면 홈→운동→식단의 Baseline Profile을 추가한다. 이미지 디코딩·동기 I/O가 trace에서 확인되면 그 작업만 분리한다. 개선 전후 같은 기기·동일 루틴으로 비교한다.

목표는 즉각적인 눌림 피드백, 하나의 짧은 전환, 안정된 조작 위치다. 디버그 APK의 체감만으로 원인이나 개선률을 확정하지 않는다. [Android Compose 성능 계측](https://developer.android.com/codelabs/jetpack-compose-performance)

## 4. 가이드북: 큰 이미지와 자막

바깥 카드 제거에 찬성한다. 현재 22dp 외부 여백, 32dp 둥근 Surface, 테두리·그림자, 이미지 12dp 내부 패딩이 겹친다. 그림보다 포장이 먼저 보인다. `camera setup` 같은 영문 슬롯 라벨도 제거한다.

화면의 위·중간은 큰 이미지, 아래는 자막과 고정된 조작부로 구성한다. 이미지를 단순 확대해서 중요한 손·휴대폰·자세가 잘리지 않게 페이지별 피사체 위치를 정한다.

**전체 이미지의 alpha를 낮추는 방식은 권하지 않는다.** 아래 자막 영역 뒤에만 투명→배경색의 그라데이션을 겹친다. 밝은 화면이면 밝은 scrim+짙은 글자, 어두운 화면이면 어두운 scrim+밝은 글자로 일관시킨다. 배경이 복잡하면 하단 끝을 충분히 불투명하게 만든다. 그래도 대비가 안 나오면 자막을 이미지 아래 평면 영역에 둔다.

제목은 1~2줄, 본문은 꼭 필요한 경우 한 문장. 첫 페이지 예: `휴대폰을 놓고, 전신을 담으세요.` 페이지 이동은 같은 이미지 영역과 자막 영역 안에서 이루어지고 아래 버튼은 움직이지 않는다. 큰 글씨 모드에서는 자막을 이미지 밖으로 내려 충분한 공간을 준다.

현재 그림은 1024×1536 SVG이며 첫 파일만 약 2.5MB다. `GuideBookScreen.kt:207`이 WebView로 렌더하고 update에서 `loadDataWithBaseURL`을 호출한다. 화면 개편 때마다 재로딩될 여지가 있으므로 로드 키를 자산에 묶는다. 경로가 매우 복잡하면 출시 자산을 알맞은 크기의 이미지로 미리 변환하고 재사용한다. 벡터라는 이유만으로 더 빠르다고 가정하지 않는다. 이 코드는 **가이드북 경로이며 운동 탭 지연의 직접 원인이라고 보지 않는다.**

자막 대비는 일반 글자 4.5:1을 검수 기준으로 삼고 실제 네 이미지·밝은/어두운 테마에서 확인한다. [Apple Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

## 5. 로그인: 공룡을 상자에서 꺼내기

`AuthScreens.kt:126`은 84dp 카드 안에 `ContentScale.Crop`으로 애니메이션 프레임을 채운다. 마지막 프레임은 **720×1280 RGBA**, 실제 불투명 영역은 **x=193~507, y=198~518**이다. 즉 정사각 로고가 아니라 큰 세로 캔버스 안에 작은 공룡이 있다. 가운데 Crop까지 겹쳐 피사체가 작거나 일부 잘릴 수 있다.

권장안은 배경 없는 공룡 심볼과 읽기 쉬운 TREX 워드마크를 한 묶음으로 두는 것이다. 원본의 바깥 테두리·그림자를 없애고 **알파 영역 기준 여백부터 정리**한다. 애니메이션을 보존한다면 16장 공통 경계로 잘라 피사체 위치가 프레임마다 흔들리지 않게 한다.

로고는 화면 위쪽 중앙에 64~80dp 정도의 실제 피사체 크기를 출발점으로 검토한다. 지금의 12sp·자간 5sp 워드마크보다 글자 자체를 분명하게 읽히게 하고, ‘바로 보고, 바로 고치고’는 필수 정보가 아니므로 기본 로그인에서는 생략한다. 여백은 큰 가짜 카드가 아니라 배경 자체로 확보한다.

현재 찢어진 종이와 세밀한 그림자는 마스코트 일러스트 성격이 강하다. 당장은 기존 공룡을 깨끗이 배치하고, 후속 브랜드 정리에서는 공룡 머리의 윤곽·눈·미소를 간결하게 정돈한 로고 전용 자산을 따로 만든다. 마스코트의 존재 자체를 지울 필요는 없다.

입력은 아래쪽에 모으고 아이디→비밀번호→로그인이 짧게 이어지도록 한다. 로그인 버튼은 오른쪽 아래, 계정 찾기·회원가입·가이드는 왼쪽 아래 계정 도움에서 접근한다. 키보드가 뜨면 로고를 작게 접고 현재 입력과 완료 동작을 키보드 위에 유지한다. 실험실과 개발용 기준선 설정을 일반 로그인에서 제거한다.

애니메이션은 로그인할 때마다 시선을 붙잡는 긴 인트로가 필요하지 않다. 최초 진입의 짧은 등장 정도로 시작하고, 입력 중이나 화면 복귀 시에는 정지한다. 현재 16장×95ms의 약 1.4초 프레임 재생은 로고가 또렷해진 뒤 필요성을 다시 판단한다.

## 6. 다음 구현 순서와 완료 기준

1. **목표 단위·카운터 완료 조건·세션 전환**: 반복 목표 시간이 지나도 그대로 머묾, 준비 자동 시작 없음, 마지막 반복 뒤 추가 반복 없이 완료, 시간 목표/휴식만 자동 이동, 부분 기록 보존.
2. **하단 동작 배치와 운동 목록**: 가장 오른쪽에 주요 동작 유지, 상단 필수 탭 없음, 하단 편집에서 추가/순서/설정/자세 옵션 모두 접근, 건너뛰기와 완료 의미 구분.
3. **첫 진입 계측·전환 수정**: 지연 제거 전후 trace 비교, 최초/반복 진입 구분, 버튼 중복 입력·포커스·목록 위치 복원 확인.
4. **가이드/로그인**: 기존 자산 경계 수정→평면 배치→자막 대비→짧은 움직임. 작은 화면·큰 글씨·키보드·밝고 어두운 테마에서 확인.

전체 운동에 새 평가 규칙이나 새 모델을 추가하는 작업은 이 설계의 범위가 아니다. 현재 관측 능력을 유지하면서 운동의 목표·기록·조작을 정확하게 전달하는 데 집중한다.
