# 고정된 휴대폰 앞에서 준비하는 운동 UX — 제안

2026-09-11 당시의 설계안이다. 이후 사용자의 ‘구현해’ 요청으로 §46을 구현했다. 실제 동작·초기 감지 기준·검증 범위는 [구현 문서](CAPTURE_PREPARATION_IMPLEMENTATION.md)를 따른다. 아래 내용은 설계 당시 제안이며 구현 상태를 뜻하지 않는다.

## 현재 불편의 원인

`SessionTransitionScreen`은 카메라가 없는 준비 화면에서 `CapturePosition.placement` 문장만 보여 준다. 문장은 “오른쪽 앞에 휴대폰을 놓으세요”처럼 기기를 움직이는 관점이다. 사용자는 자기 몸의 방향을 어떻게 바꿔야 하는지 머릿속으로 변환해야 하고, 전신이 잡히는지도 확인하지 못한다. 시작을 눌러야 라이브 카메라가 생기므로 위치를 잡은 뒤 다시 휴대폰으로 돌아오는 문제가 생긴다.

## 권장 흐름

**짧은 시범 확인 → 휴대폰에서 ‘준비 시작’ 한 번 → 사용자가 자리 잡기 → 촬영 준비 확인 → 3·2·1 → 운동**

‘준비 시작’은 곧바로 운동을 기록하는 버튼이 아니라, 사용자가 자리를 잡으면 시작해도 좋다는 의사 표시다. 단순히 화면에 사람이 나타났다고 운동을 시작하지 않는다. 시작 전 대기 시간은 운동 목표 시간이나 반복 횟수에 포함하지 않는다. 반복 목표/시간 목표에 따른 기존 운동 종료 조건도 유지한다.

### 1. 휴대폰은 고정하고 사람이 움직이는 그림

- 현재의 큰 텍스트 영역을 짧게 반복되는 인물 시범으로 바꾼다. 고정된 휴대폰 표식 앞에서 **인물만 회전하거나 옆으로 이동**한다. 카메라가 인물 주변을 도는 연출은 피한다.
- ‘오른쪽 앞 30~45도’는 보조 정보다. 주요 문장은 **“오른어깨가 휴대폰에 더 가까워지도록 몸을 돌려 주세요.”** 왼쪽 앞은 왼어깨로 바꾼다. “오른쪽으로 돌아 주세요”만 쓰면 사람마다 반대로 이해할 수 있다.
- 정면은 “가슴이 휴대폰을 향하게 서 주세요”, 바닥 측면은 “휴대폰에 몸의 옆면이 보이도록 자리 잡아 주세요”처럼 사용자의 행동으로 표현한다.
- 그림과 미리보기의 좌우 반전은 일관되게 처리하되 ‘오른어깨’는 언제나 사용자 자신의 오른어깨다. 전면/후면 카메라 각각으로 확인해야 한다.
- 처음 보는 방향에서 시범을 크게 보여 주고, 같은 방향이 반복되면 작은 안내로 줄인다. 운동 종류만 바뀌었을 때 긴 설명을 매번 반복하지 않는다.

### 2. 준비 화면부터 실제 카메라 미리보기

전신이 들어가는지 즉시 보이도록 준비 단계부터 미리보기를 띄운다. 상단에는 운동명·목표, 중앙에는 미리보기와 필요한 안내 한 줄, 하단 오른쪽에는 ‘준비 시작’, 왼쪽에는 돌아가기를 둔다. 준비를 시작한 뒤에는 같은 자리에 ‘준비 취소’를 둔다.

시범 인물은 방향을 설명하는 예시이고, 사용자 몸을 정확히 그 윤곽에 맞추도록 강요하는 틀이 아니다. 사람마다 키·팔다리 비율이 다르므로 라이브에서는 필요한 관절과 화면 여백을 기준으로 촬영 범위를 안내한다. 여러 카드·정확도 퍼센트·각도 숫자를 동시에 띄우지 않는다.

예: 발이 잘리면 “한 걸음 뒤로 이동해 주세요”만, 범위가 확보된 뒤 방향이 명확히 다르면 어깨 방향만 안내한다. 서로 반대되는 음성이 연속으로 나오지 않도록 안정 구간과 안내 간격이 필요하다. 위치가 맞으면 “촬영 준비 완료”를 표시하며 “자세가 정확해요”라고 말하지 않는다.

향후 구현에서는 준비→운동을 같은 카메라 세션 안에서 전환해 미리보기가 끊기거나 다시 검게 뜨는 일을 줄인다. 준비 프레임은 자세 집계·반복 카운터·개인 기준선으로 넘기지 않는다.

### 3. 자리에서 시작하기

사용자가 ‘준비 시작’을 누른 뒤, 운동에 필요한 관절이 화면에 들어오고 관측이 안정되면 짧은 준비 카운트다운을 제공한다. 안정 대기 1~2초와 카운트다운 3초는 **초기 검토값이며 아직 검증된 값이 아니다.** 사용자의 준비 속도와 운동에 따라 충분한 여유를 검증해야 한다.

카운트다운은 큰 숫자와 원형 진행률, 음성을 함께 사용한다. 음성을 끈 경우에도 숫자와 짧은 상태 문장으로 시작 시점을 알 수 있어야 한다. 프레임 밖으로 나가거나 필요한 관절이 가려지면 운동을 시작하지 않고 자리 잡기 단계로 돌아간다. 앱이 비활성화되면 자동 시작 대기를 해제한다. 화면으로 복귀했다는 이유로 갑자기 시작하지 않는다.

음성 명령이나 손들기 제스처를 기본 입력으로 요구하지 않는다. 마이크 권한·소음에 의존하거나 바닥 운동에서 지지하는 손을 떼게 만들 수 있기 때문이다. 음성 ‘시작’은 별도 검증 후 선택 기능으로 고려할 수 있다.

인식이 어려울 때는 휴대폰에서 **‘카운트다운으로 시작’**을 직접 선택해 위치를 잡을 여유를 주는 대안이 필요하다. 이 선택은 촬영 방향 확인을 생략하는 것이지, 못 보는 자세를 평가해도 된다는 뜻이 아니다. 음성 자동 안내가 어려운 사용자에게는 준비 시간을 늘릴 수 있게 한다.

### 4. 바닥 운동에서 달라지는 점

플랭크에서는 몸 옆이 보이게 매트에서 방향을 잡는 시범을 보여 준다. 인식을 기다리는 동안 플랭크를 계속 버티도록 요구하지 않는다. 무릎을 대고 편하게 준비한 상태에서 화면 범위를 확인하고, 카운트다운에 맞춰 동작에 들어가도록 안내한다. 준비 자세에서도 운동 중 손발이 들어갈 여백이 확보되는지는 실제 기기로 확인해야 한다.

초기안에서는 **카운트다운 종료를 시간 측정 시작 시점**으로 일관되게 알린다. 이를 실제 버티기 시작을 자동 검출한 시간이라고 표시하지 않는다. 동작 진입 검출로 시계를 시작하는 방식은 별도의 검증이 필요한 후속 선택이다.

운동 중에는 사용자가 화면을 보려고 목을 들지 않도록 시작·일시정지 같은 주요 상태를 짧은 소리로 전달한다. 자세 교정 음성에는 기존 ship/beta 정책을 그대로 적용한다. 준비 음성은 촬영 범위 안내이며 몸의 정렬이 올바르다는 판정이 아니다.

서서 하는 운동에서 바닥 운동으로 넘어갈 때는 고정된 기기 높이로 전신이 안 잡힐 수 있다. 이 경우에만 첫 배치에서 낮은 받침 예시를 안내한다. **몸을 돌리는 것만으로 모든 촬영 높이 문제가 해결되지는 않는다.** 같은 높이·방향의 다음 세트는 재배치 안내를 생략하되 사용자의 루틴 순서를 자동 변경하지 않는다.

### 5. 현재 엔진을 고려한 구현 순서 — 아직 착수하지 않음

1. 먼저 프로필별 시범 그림·사용자 관점 문장·준비 미리보기·명시적 준비 시작을 만들고, 직접 선택한 카운트다운으로 휴대폰 재접근 문제를 해결한다.
2. 실제 프레임으로 준비 감지의 오작동을 확인한 뒤, 사용자가 준비 시작을 누른 경우에만 관절 범위/안정 상태에 따른 자동 카운트다운을 붙인다.
3. 방향 추정은 신뢰할 수 있는 경우에만 보조 안내로 쓴다. 처음부터 필수 통과 조건으로 만들지 않는다. SIDE/UNKNOWN과 바닥 관측의 기존 한계 때문에 정상적으로 준비해도 시작이 막힐 수 있다.

`PoseSample.detected`만으로 준비 완료를 판단할 수 없다. 유효한 관절·필요 피처·범위·안정성을 따로 확인해야 한다. 방향을 잘 못 봤다고 특정 회전 방향을 확신하여 발화하지 않는다. 촬영 가능 여부, 운동 자세의 옳고 그름, 개인 기준선 수집 여부는 각각 독립된 상태다.

## 실기기에서 확인할 경험

- 처음 쓰는 사람이 글을 길게 읽지 않고 오른어깨/왼어깨 방향을 맞추는가.
- 준비 시작 후 휴대폰을 다시 만지지 않고 정면·사선·바닥 운동을 시작하는가.
- 전신이 잘리거나 앱을 나갔다 돌아왔을 때 예고 없이 시작하지 않는가.
- 음소거·큰 글자·동작 줄이기에서도 안내와 카운트다운을 이해할 수 있는가.
- 준비 중 몸을 돌리거나 숙인 프레임이 운동 횟수·개인 기준에 섞이지 않는가.
- 바닥 운동에서 화면을 읽기 위해 고개를 들도록 만들지 않는가.

이는 UX 검증 항목이다. 기존 자세 평가 정확도가 개선됐다는 근거로 사용하지 않는다.

## 참고한 설계 원칙

상태·사용법을 설명하는 움직임이라는 [Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion) 원칙을 인물 회전 시범에 적용했다. 장식적인 카메라 회전이나 반복되는 큰 전환은 필요하지 않다. 소리만으로 상태를 전달하지 않는 [Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) 원칙을 숫자·문장·음성 조합에 적용했다. 구체적인 준비 흐름과 시간값은 TREX를 위한 설계 제안이며 Apple이 검증한 운동 UX라는 뜻은 아니다.
