## 갈림길

### A. 인식 커버리지를 더 키운다 (YOLO 보강)

- **남은 데이터**: `12_13_14_15_16`(김치·젓갈·회·떡·한과, 58클래스, 25GB)만 안 받았다. 받으면 AI Hub 400종을 거의 다 쓴다.
- **비용**: 다운로드 25GB(이더넷 40분) + 학습 1~2시간. 이미 만들어 둔 파이프라인 그대로.
- **얻는 것**: 한식 표준 메뉴 커버리지 최대.
- **걸리는 점**:
  - 클래스가 늘수록 비슷한 음식끼리 혼동이 는다(콩나물국↔계란국은 이미 관측됨). 클래스당 200장은 400클래스에는 얇다.
  - AI Hub 400종은 **식당 표준 메뉴**다. 집밥·편의점·브랜드 음식(예: 특정 프랜차이즈 버거)은 아무리 늘려도 안 나온다.
  - 한 접시에 여러 음식이 있을 때 하나만 잡는 현재 구조는 클래스를 늘려도 그대로다. 위 실측 사진이 그 예다 — 밥이 추가돼도 회·상추는 여전히 못 잡을 수 있다.

### B. 사용자가 음식을 추가하는 공용 DB

- **아이디어**: 직접 입력할 때 쌓인 음식 데이터를 서버에 모으고, 다른 사용자가 검색하면 그게 뜬다. 인식 실패의 영구적 폴백.
- **얻는 것**: 롱테일(집밥·지역 음식·브랜드 제품)을 데이터 수집 없이 커버. 쓸수록 좋아진다.
- **걸리는 점**:
  - **서버가 필요하다.** 현재 `server/`(Spring Boot)는 인증·프로필·기록 API 까지만 있고 origin 에 push 도 안 됐다. 음식 DB API·검색·중복 병합을 새로 만들어야 한다.
  - **데이터 품질**: 누구나 넣으면 "치킨 10kcal" 같은 값이 섞인다. 검수·신고·가중치 중 뭔가가 필요하다.
  - **CLAUDE.md Privacy-by-Design 확인 필요**: 지금 앱은 사진을 기기 밖으로 안 보낸다. 음식 **이름·영양값**만 올리는 건 이 원칙과 충돌하지 않지만, 사진까지 올리는 설계로 가면 원칙을 다시 봐야 한다.
  - 캡스톤 일정 안에 서버·검수까지 끝낼 수 있는지.

### C. 인식 자체를 여러 음식으로 (구조 변경)

- 지금은 클래스별 최고 점수 1개씩만 뽑는다. 박스 좌표와 NMS 를 살리면 한 사진에서 "밥 + 국 + 반찬"을 동시에 잡을 수 있다. 학습 데이터에 박스가 이미 있다(AI Hub 74번은 박스 어노테이션 포함).
- **비용**: 앱 후처리만 고치면 된다(재학습 불필요). `FoodDetector` 에 NMS 추가 + 결과를 박스 단위로.
- **위 실측 사진이 정확히 이 경우다** — 한 상에 4가지가 있는데 1개만 나왔다.

## 물어볼 것

1. A·B·C 중 **캡스톤 남은 기간에 실제로 끝낼 수 있는 것**은 무엇인가? (우선순위를 정해야 한다)
2. C 는 재학습 없이 앱 수정만으로 되는데, 왜 처음부터 안 했나? → 당시엔 "무슨 음식인지만 알면 된다"고 판단했다(`FOOD_RECOGNITION.md` 참조). 한 상에 여러 음식이 흔하다는 게 실측으로 드러났으니 재검토 대상이다.
3. B 로 간다면 **서버 API 설계**와 **데이터 품질 정책**을 누가 언제 하나? 담당 분리상 서버는 사용자 몫이었다.
4. 혼동 쌍(콩나물국↔계란국 등)을 줄이는 게 클래스 추가보다 먼저 아닌가? → 학습 후 confusion matrix 로 확인 가능하다(`runs/food/confusion_matrix.png`).
