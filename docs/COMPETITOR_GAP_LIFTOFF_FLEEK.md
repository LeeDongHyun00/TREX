# 경쟁 앱(Liftoff · 플릭) 대비 TREX 기능 격차와 개발 계획 (2026-11-05)

상태: **조사·기획 초안 — 구현 전.** 화면·시스템 프로토타입 설계는 `docs/GAP_PROTOTYPE_DESIGN.md`, 클릭 프로토타입은 `docs/prototype/competitor-gap/index.html`. 사용자 요청(2026-11-05) "Liftoff(피트니스 7위, TREX 와 유사)·플릭(지인 사용 앱)의 공통점 — 운동 보상, 기록 제한 없음, 추천 루틴, 더 많은 운동 목록, 운동 기록 페이지 — 과 그 밖에 TREX 에 없고 필요한 것을 문서화해".

조사 기준: 코드는 `main` `0c23dc8`(v1.4.0, versionCode 15). 경쟁 앱 정보는 스토어 페이지·공식 사이트·국내 언론·커뮤니티 글(2026-11-05 기준). 확인하지 못한 것은 *(미확인)*, 추정은 *(추정)* 으로 표시했다. 경쟁사가 쓴 비교 글(Gript·SensAI)은 출처에 그렇게 적었다.

## 5. 격차 목록과 제안

우선순위는 (가) 두 앱 공통이고 TREX 에 없는 것, (나) 한 앱에만 있지만 TREX 차별점과 맞물리는 것, (다) 나머지 순이다. 각 항목에 TREX 원칙(`CLAUDE.md`)과 충돌하는 지점을 적었다.

### G1. 운동 기록 보관 제한 해제 (가) — **다른 항목의 전제**

- **현재**: 7일 뒤 삭제. 2026-10-28 사용자 결정으로 운동 기록과 피로도를 같은 7일 창에 맞췄다(스펙 §111). `docs/MUSCLE_LOAD_RECOVERY_DESIGN.md` §315 가 이미 "원장 180일 보관, 화면은 7일" 을 제안하고 보관 범위 고지·삭제·내보내기를 조건으로 달았다.
- **왜 먼저인가**: 연속 일수·PR·추이 차트·달력·보상은 전부 7일 넘는 이력이 있어야 성립한다. 지금 구조에선 연속 운동이 7일에서 멈추고 서버 백업도 7일분이다.
- **제안**
  1. `RECORD_WINDOW_DAYS`(화면 조회 창)와 **보관 기간을 분리**한다. 보관은 무제한(기본) 또는 사용자 선택(90일/1년/무제한). `pruneExpiredHistory`·`MuscleLoadStore` 의 DELETE 는 보관 기간을 따르고, 피로도 계산 창은 지금처럼 7일을 유지한다(감쇠식이 24h 반감기라 7일 밖은 0 에 수렴 — 계산 결과는 바뀌지 않는다).
  2. 저장 구조: `history` 는 SharedPreferences 한 JSON 문자열이라 수년치가 쌓이면 로드·동기화 페이로드가 커진다. **월별 키(`history_YYYYMM`)로 쪼개거나 SQLite 로 옮긴다**. 동기화는 항목별 통째 방식(D5)이라 월 키가 자연스럽다(바뀐 달만 올라감). 서버 `SYNC_ITEMS` 는 키 추가에 열려 있어 스키마 변경 없음.
  3. 서버 `LogRetentionScheduler`(7일 하드 삭제)는 옛 `/api/exercise-logs` 전용이고 동기화 항목엔 안 걸린다(D7) — 그대로 둬도 되지만 혼동을 막으려면 문서에 명시.
  4. 설정에 '기록 보관 기간'·'기록 내보내기(CSV/JSON)'·'전체 삭제' 를 둔다(제안 §315 의 조건).
- **원칙 충돌**: 없음. 단 자세 판정 요약(`PostureCorrection`)이 장기 보관되면 **당시 규칙 버전(`rules_version`)을 기록에 같이 남겨야** 뒤에 규칙이 바뀌어도 "그때 beta 였던 판정" 을 구분할 수 있다(원칙 #2).
- **마이그레이션**: 이미 삭제된 과거는 복원 불가. 설치 시점부터 쌓인다.

### G2. 중량·RPE 입력과 이전 기록 자동 채움 (가)

- **현재**: 세트당 횟수/초만. 무게는 체중뿐. 이전 세션 값은 루틴(plan)에서 온다.
- **경쟁**: 둘 다 세트별 무게·횟수(·시간)가 기본, Liftoff 는 RPE·워밍업·드롭 세트, 플릭은 드롭·슈퍼·실패 세트와 종목별 메모, '이전 기록으로 시작'.
- **제안**
  - `Workout` 과 `LoadSet` 에 **선택적 `loadKg`**(기구 무게, null = 맨몸) 와 세트별 배열(`sets: List<SetEntry(reps, seconds, loadKg, rpe?)>`)을 추가. 지금의 "12회 × 3세트" 문자열은 요약으로만 남긴다.
  - 세션 준비·휴식 화면에 **같은 종목의 최근 세트를 인라인으로 보여 주고 한 번에 채우기**. `TimerSessionScreen` 의 '횟수 기록' 에 무게 휠 추가(`WorkoutNumberWheel` 재사용, 0.5 kg 단위).
  - 종목별 메모(플릭에서 가장 칭찬받는 기능 중 하나).
  - **근육 부하 추정에 무게 반영**: `MuscleLoadEngine` dose 식이 체중×역할 가중치뿐이라 지금은 덤벨 5 kg 와 20 kg 가 같은 부하다. `docs/MUSCLE_LOAD_RECOVERY_DESIGN.md` §202 의 중량 입력 설계를 그대로 쓴다.
- **원칙 충돌**: 카메라 세션의 횟수는 beta(마지막 렙을 구조적으로 놓침) — 자동 카운트 위에 무게를 곱해 볼륨을 내면 오차가 kg 단위로 커진다. **볼륨·1RM 은 사용자가 확정한 횟수(자가 라벨 `actualReps` 또는 수동 입력)로만 계산**하고 자동 카운트만 있는 세트는 '추정' 표시.

### G3. 운동 기록 페이지 확장 (가)

- **현재**: 7일 막대 + 날짜 카드.
- **경쟁**: 달력, 종목별 추이(무게·1RM·볼륨), PR 목록, 기간 비교, 부위별 균형(Bodygraph/자극 맵), 신체 측정 이력.
- **제안**(G1·G2 뒤)
  1. **달력 월 뷰** — 운동한 날 점, 날짜 탭 → 그날 카드. 미사용 `WorkoutNavigationTab.History/Schedule`(`TrexData.kt:24-27`) 자리.
  2. **종목 상세 페이지** — 종목별 세트 이력, 최고 무게·최고 횟수·추정 1RM 추이(Epley, 횟수 ≤ 10 에서만 — 맨몸 종목은 횟수 추이만), 마지막 수행일. 카탈로그 행에서 진입.
  3. **주간·월간 요약** — 운동 일수, 세트 수, 볼륨, 부위 비중(이미 `routineOverview` 의 분류를 재사용), 피로도 맵은 그대로.
  4. **PR 감지** — 세트 저장 시 종목별 최고 기록 갱신이면 완료 화면·기록 카드에 'PR' 표시(G5 의 보상 트리거).
  5. **체중·신체 측정 이력** — 프로필 `weightKg` 를 날짜별 이력으로(동기화 키 `body`). 체지방·둘레는 선택 입력. 영양 목표 계산(`WorkoutMath.kt:103-114`)이 최신 체중을 쓴다.
- **원칙 충돌**: 자세 점수를 추이 차트로 그리지 않는다 — 점수는 분수이고 판정 0건이면 점수가 없으며(원칙 #1), ship 규칙 0~3개라 1건 위반이 그래프를 크게 흔든다. 기록 페이지의 자세 항목은 지금처럼 **문장**("무릎 안쪽 모임 2회 뺌")으로.

### G4. 운동 목록 확대와 커스텀 종목 (가)

- **현재**: 26개, 커스텀 없음. 게이트는 `postureExerciseMap` + `Workout.postureSupported()` (`CLAUDE.md` 구조 절).
- **경쟁**: 400~600개, 부위·기구 분류, GIF/영상, 커스텀.
- **제안**
  1. **카탈로그를 두 층으로**: ① 자세 교정 26종목(지금, AIHub) ② **기록 전용 종목** 수백 개(부위·기구·동작 유형 메타, 근육 매핑 `trainingload/MuscleLoad.kt:7-12` 확장). 기록 전용 종목은 자세 토글이 꺼진 채 타이머 세션으로 가고 "이 종목은 자세 비교를 지원하지 않아요" 문구를 유지한다(원칙 #5 — 못 보는 것을 밝힘).
  2. 종목 데이터는 **공개 라이선스 데이터셋**(예: wger, free-exercise-db — 라이선스 확인 필요)에서 가져와 한국어 이름·별칭을 붙인다. GIF 가 없는 종목은 정지 그림·텍스트 설명만.
  3. **커스텀 종목**: 이름·부위·기구·근육(선택) 입력, 동기화 키 `custom_workouts`(커스텀 음식과 같은 꼴). 커스텀은 자세·근육 추정 없음을 명시.
  4. `WorkoutNames.canonical` 과 `workoutCatalog` 의 26개 앱 이름 불변 — 새 종목은 별도 id 공간.
- **원칙 충돌**: "AIHub 에 없어서 못 한다는 답은 하지 않는다"(원칙 #2) 는 **자세 규칙**에 관한 말이다. 기록 전용 종목은 자세 판정을 약속하지 않으므로 충돌 없음. 단 자세 교정 종목 수를 늘리는 일은 `docs/EXERCISE_TIERS.md` 절차(계열·등급 → 모집단 재생 → 폰 세트)를 지키며 별도 트랙으로.

### G5. 운동 보상 (가)

- **현재**: 연속 운동 일수(7일 상한)뿐.
- **경쟁**: Liftoff 는 근력 등급·LP·연속·퀘스트·알·시즌 리더보드가 앱의 중심. 플릭은 레벨·PR 알림 정도. **둘 다 현금·쿠폰·제휴 보상은 없다.**
- **제안 — 1차(기록 기반, 서버 없이 가능)**
  1. **연속 일수**를 G1 뒤 무제한으로. 휴식일 개념(주 N일 목표를 온보딩 `dayMask` 에서 읽어 목표 요일만 세는 방식 — 미사용 데이터 활용).
  2. **배지·업적**: 첫 운동, 7·30·100일, 종목별 100회, PR 갱신, 자세 교정 모드로 N세트, 가이드 전 종목 열람 등. 로컬 계산, 동기화 키 `achievements`.
  3. **PR 축하**: 완료 화면에 '개인 기록 갱신'(플릭의 갱신 알림).
  4. **레벨/XP**: 세트 완료·운동 일수·기록 작성에 XP. 간단하고 무게 없는 종목에도 공평.
- **2차(서버·커뮤니티 결합)**: 주간 챌린지("이번 주 3일"), 친구 리더보드(커뮤니티 팔로우가 비목표라 1차 범위 밖), 시즌.
- **Liftoff 식 근력 등급은 권하지 않는다** — 모집단 1RM 분포(종목당 10만 건)가 필요하고 TREX 사용자 규모로는 만들 수 없으며, Liftoff 리뷰의 불만("무게에 치우침", 종목 간 등급 불일치)이 바로 그 설계의 비용이다.
- **원칙 충돌 — 가장 주의할 항목**
  - **보상 트리거를 자세 점수·자동 카운트에 걸지 않는다.** 점수는 보지 못한 세트일수록 오르는 신호를 만들면 안 되고(원칙 #1), 카운트는 beta 다. 보상은 **"세트를 수행하고 기록했다"**(완료 화면 도달, 자가 라벨 포함) 에만 건다.
  - **COACH 모드에서 '정확 횟수' 를 보상에 넣지 않는다** — 오탐 1건이 1회를 지우는 게이트(§62b)라 보상이 걸리면 사용자가 TRACK 으로 도망가거나 카메라를 끈다. 자세 관련 업적은 "교정 모드로 N세트 **시도**" 처럼 결과가 아니라 참여에 건다.
  - 연속 일수 복구를 돈·화폐로 파는 Liftoff 모델은 체험판 단계에서 비목표.

## 6. 지키는 것 — 격차를 메우면서 깨지 말아야 할 TREX 전제

1. **보상·통계는 자세 판정과 자동 카운트 위에 세우지 않는다.** 둘 다 "검증 중" 이고 세트를 덜 본 쪽이 유리해지는 구조를 만들면 안 된다(원칙 #1·#2). 트리거는 수행·기록·참여.
2. **기록 전용 종목은 "자세 비교 미지원" 을 그대로 말한다**(원칙 #5). 종목 수를 늘리는 것과 자세 교정 종목을 늘리는 것은 다른 트랙이다.
3. **장기 보관되는 자세 요약에는 규칙 버전을 남긴다.** 규칙은 ship/beta 가 바뀐다.
4. **`PostureLiveSessionScreen` 에 지역 변수를 늘리지 않는다**(dex 레지스터 함정). 무게 입력·PR 표시를 세션 화면에 넣을 때는 `LiveSessionRefs` 홀더나 별도 클래스로.
5. **공유 파일(`ios-ui/android-sources.txt`)에 `java.*`·`android.*` 금지.** 새 화면·저장소는 `AppPlatform`·`KeyValueStore` 경계로. 알림·Health Connect 는 플랫폼 짝 파일.
6. 커뮤니티·루틴 공유 서버 API 는 `docs/SERVER_SYNC_HANDOFF.md` 트랙(서버는 사용자 담당). 새 동기화 키는 `SyncRules.KEYS` 에만 더하면 서버 변경이 없다(D5).

## 8. 사용자가 정할 것

1. **G1 — 7일 삭제를 되돌릴지.** 2026-10-28 의 결정(7일 창)을 바꾸는 일이라 사용자 확인이 필요하다. 되돌리면 보관 기간 선택·내보내기·전체 삭제를 같이 넣는다(§315 조건).
2. **G5 — 보상의 톤.** 배지·연속·XP(조용함) 까지인지, Liftoff 식 화폐·상점·리더보드(시끄러움) 까지인지. 이 문서는 전자를 권한다.
3. **G4 — 종목 데이터 출처와 라이선스**(wger 등 공개 DB vs 직접 작성), 한국어 이름 작업량.
4. **G6 — 프리셋 루틴의 저자.** 팀이 직접 쓰는지(분할 템플릿 10여 개), 외부 콘텐츠를 들이는지.
5. **마감과의 관계.** 커뮤니티 설계 문서에 2026-11-11 수정 마감이 적혀 있다. 이 문서의 항목은 그 뒤의 일로 보는 것이 맞는지.
