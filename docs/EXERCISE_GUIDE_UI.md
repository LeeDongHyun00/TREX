# 기존 화면을 유지하는 운동 시범 (2026-09-27)

## 범위와 근거

사용자 요청: 로컬 main에서 구현하되 기존 레이아웃을 최대한 유지한다.
홈·내비게이션·카메라 영역·목표 계기판·편집·정렬·스와이프 삭제는 유지하고,
운동 목록/종목 선택/준비/운동/휴식에 `운동 방법` 진입점만 추가한다.
전체 화면을 재설계했던 브라우저 시안은 앱에 이식하지 않았다.

## 동작

- 준비된 시범은 기본 스쿼트·런지·덤벨 컬 3종목이다. 다른 종목에는 버튼을 표시하지 않는다.
- 목록 및 종목 선택 화면에서는 선택·수정 대신 별도 하단 시트로 안내를 연다.
- 각 종목의 첫 준비에서 같은 시트를 한 번 자동으로 연다. 확인 여부는 전용 `exercise_guides` 설정에 저장한다.
- 첫 안내가 보이는 초기 구성부터 준비·측정·타이머·자동 전환을 멈춘다.
- 첫 안내에서 `준비 계속하기`를 누르면 기존 준비 화면으로 돌아온다.
- 운동/휴식/준비에서 수동으로 안내를 열면 명시적으로 일시정지한다. 닫기·뒤로가기·스와이프는 자동 재개하지 않는다.
- 카메라 준비에서도 기존 `재개` 조작으로 다시 진행한다. 안내는 세트를 마감하거나 카메라 화면을 교체하지 않는다.
- GIF는 로컬 자산으로 재생하며 일시정지·재생을 제공한다. 앱이 배경으로 가면 멈춘다.
- 작은 화면에서는 시범·설명을 스크롤하고 닫기/계속 버튼을 하단에 유지한다.

## 자산 한계

Gym Visual의 실제 자산은 사용하지 않았다. 기존 로컬 ImageGen GIF 3개를 패키지에 복사했다.
현재 시범은 두 자세를 번갈아 보여주는 로컬 시안이며, 연속 운동을 촬영한 교육 자료는 아니다.
새 종목 자산 없이 비슷한 운동의 시범을 대신 표시하지 않는다.
정본 매핑은 `ExerciseGuides.kt`, 자산 출처는 `app/src/main/assets/exercise_guides/README.md`.

## 후속 수정 (2026-09-27, §65)

- 준비 화면에서 제목 아래 긴 준비 대사, 프레임 상태 설명, 몸만 움직이라는 문구와 재시작 안내를 제거했다.
  촬영 방향 그림과 `capture.placement`를 남기고 내부 스크롤을 없앴다. 카운트다운·촬영 오류·기존 조작은 유지한다.
- 운동 수정은 세트 / 횟수(또는 시간) / 세트 간 휴식의 세 열로 바꿨다. 제목 아래 숫자 휠을 두고
  아래 드래그로 증가, 위 드래그로 감소한다. 손을 떼면 중앙 줄로 정렬한다. 시간·휴식은 초 단위다.
  범위는 세트 1–20, 횟수 1–999, 시간 1–3600초, 휴식 0–600초다. 저장 전까지만 초안에 반영한다.
- GIF 아래에 코치의 코멘트 / 운동 가이드 / 주의사항 탭을 넣었다. 기본 탭은 운동 가이드이며
  시작 자세·운동 동작·호흡법을 나눠 보여 준다. 안내의 본문만 스크롤하고 닫기는 하단에 유지한다.
- 첨부 이미지는 정보 구조 참고용이다. 이미지 속 시티드 케이블 로우의 설명을 다른 종목에 복사하지 않았다.

## §66 — 고정 운동 안내와 숫자 휠 저장 일치 (2026-09-27)

- 운동 가이드의 시트 드래그와 핸들을 제거했다. 패널 높이를 고정하고 본문 영역만 스크롤하며,
  운동 가이드 / 주의사항 두 탭과 닫기 버튼을 유지한다.
- GIF의 수동 재생·정지 버튼과 코치의 코멘트, 참고 링크, 운동 수정의 드래그 방향 설명을 제거했다.
  GIF는 열린 화면에서 자동 반복 재생하며 백그라운드에서는 기존 수명주기 정책에 따라 멈춘다.
- 사용자 확인: 런지 문제는 세트 사이 휴식 진입이 아니라 수정 화면에서 휴식 값이 저장되지 않는 현상이다.
  `TrexStore`는 명시적 휴식 값을 쓰고 읽고 있었으므로 저장 포맷·휴식 단계 생성 정책은 변경하지 않았다.
- 숫자 휠 선택값을 `snapshotFlow` 콜백으로 초안에 복제하는 경로를 제거했다. 이제 표시와 저장은 같은
  `WorkoutNumberWheelState.value`를 읽고, 저장 순간 세트·목표·휴식을 함께 확정한다. 모드 전환에도 선택한 휴식을 보존한다.
  운동 수정 중 시트 드래그로 저장 없이 닫히는 경로도 차단했다.
- 실기기에서 원래 현상을 재현하지 않았으므로 발생 원인을 확정한 것은 아니다. 비동기 값 복제·드래그 닫기의
  유실 가능성을 코드에서 제거하고 런지 95초/125초/0초의 저장 결과와 휴식 단계 반영을 JVM으로 확인했다.
