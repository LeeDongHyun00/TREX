## 1. 먼저 내린 결정

네 종목을 기존 세트 평균 규칙에 더 붙이는 방식으로 확장하지 않는다. **동작 사이클 검출 → 동작·쪽 식별 → 반복 창 자세 평가 → 표시/목표 정책**을 분리한다. 같은 자세 판정과 임계값을 COACH/TRACK에서 공유하고, 모드에 따라 표시·발화·진행 정책만 바꾼다.

핵심 이유는 다음과 같다.

1. 교대 운동의 좌우 평균은 한쪽 움직임을 약화시키고, 부호가 있는 평균은 좌우를 상쇄할 수 있다.
2. 크로스 런지의 다리 교차와 사이드 크런치의 옆 굽힘은 정상 동작이다. 스쿼트의 무릎 모임 검사나 몸통 기울기 검사를 그대로 가져오면 정상 동작을 교정한다.
3. 준비 동작과 휴식이 들어간 `range/std/mean`은 실제 반복의 자세를 대표하지 않는다. 이전 §31a·§62a의 실패를 반복하지 않는다.
4. 현재 런지류의 두 사이클 묶기는 좌우 수행을 확인하지 않는다. 동일 다리 두 번과 반대 다리 한 번씩을 구분해야 한다.
5. 기존 `ship`은 이 네 종목의 새 반복 검사에 대한 실기기 검증을 뜻하지 않는다. 피처·창·촬영 방향이 바뀐 규칙은 새 후보로 검증한다.

## 3. 정상 동작과 필요한 관절

### 3.1 동작 정의

**크로스 런지**는 우선 로컬 AIHub의 뒤로 교차하는 변형(curtsy)으로 범위를 고정한다. 정상 라벨 대표 클립 `D02-1-177`의 GT 좌표는 오른발이 왼발 뒤·반대쪽으로 이동하고 복귀한 뒤 반대 다리가 움직인다. 1개 대표 클립의 확인이므로 전체 정상 클립에서도 같은 변형인지 P0에서 검토한다. 앞으로 교차하는 crossover를 같은 분포에 섞지 않는다.

준비 → 이동 다리가 뒤쪽 대각으로 교차 → 앞 지지 다리와 골반이 내려감 → 올라오고 교차를 풀어 준비 위치 복귀. 뒤 다리의 뒤꿈치가 들리는 것은 이 동작에서 자연스럽다. 앞 지지 무릎이 해당 앞발 방향에서 무너지는 것과 두 다리가 교차하는 것은 다른 관측이다.

**사이드 런지**는 옆으로 한 발 디디고 그쪽 무릎과 고관절을 굽히며 엉덩이를 뒤로 보내고, 반대 다리는 비교적 편 채 복귀한다. 넓은 고정 스탠스에서 좌우로 옮기는 변형은 별도 프로필이다. 이를 같은 발 닫기 복귀 조건으로 처리하면 매번 놓친다. 첫 구현은 스텝 후 복귀형으로 고정하고, 원본 정상 클립에 고정 스탠스형이 있으면 데이터·검출 상태를 분리한다.

**니업**은 한쪽 허벅지/무릎을 들어 올리고 같은 발이 내려온 사이클이다. 무릎을 굽히기만 해서 뒤꿈치를 엉덩이로 보내는 동작과 구분한다. 지지 무릎을 약간 굽히는 것은 정상이다. 몸통을 곧게 유지한 작은 범위는 동작 사이클로 관측하고, 높이가 목표 범위에 들었는지는 별도 자세/가동범위 질문으로 평가한다.

**사이드 크런치**는 한쪽 무릎을 옆으로 들며 같은 쪽 팔꿈치/옆 몸통이 접근하고 중립으로 복귀하는 동작이다. 측굴 자체를 오류로 삼지 않는다. 실제 복근 활성이나 손으로 목을 당기는 힘은 알 수 없다. AIHub의 양손 머리 뒤 변형을 첫 프로필로 삼되, GatorCare의 팔을 든 변형을 ‘손 위치 오류’로 학습하지 않는다. 그 변형은 별도 프로필/지원 범위로 다룬다.

주의할 좌표계 문제:

- MP 월드의 원점은 매 프레임 골반 중심이다. 월드 발목의 프레임 차이를 지면에서 발이 미끄러진 거리로 해석하지 않는다. 실제 이동은 고정된 이미지/보정 카메라 좌표와 함께 본다.
- 동작 중에 골반 축이 돌면 그 축을 매 프레임 기준으로 삼은 피처가 회전을 지워 버린다. 교차 발 경로는 준비 축 기준, 상대 관절 자세는 현재 몸 축 기준을 구분한다.
- 분모는 hip→knee + knee→ankle 마디 길이의 준비 중앙값이다. 굽힌 hip→ankle 현이나 사선에서 줄어든 어깨 가로폭을 분모로 쓰지 않는다.
- 같은 쪽이 L인지 R인지와 화면 왼쪽/오른쪽은 별개다. 미러는 UI 좌표에만 적용하고 엔진의 해부학 이름을 뒤집지 않는다.

## 4. 횟수 검출 설계

### 4.1 공통 상태와 사건

`WAIT_VISIBLE → READY → DEPARTURE → EXTREME → RETURN → COMPLETE`를 timestamp 기준으로 구현한다. `EXTREME`는 무릎이 가장 굽은 런지/무릎이 가장 올라온 니업/수축한 크런치라는 **동작 극점**이지, 올바른 자세 합격선이 아니다.

READY는 준비 카운트다운에서 측정 가능한 안정 자세를 모아 잡는다. 한 프레임을 기준선으로 쓰거나, 처음부터 잘못된 폼을 정상 기준으로 채택하지 않는다. 기준선은 카운트 출발/복귀의 기준과 모집단 자세 평가의 기준을 분리한다.

DEPARTURE는 잡음보다 충분한 변화와 해당 동작의 넓은 경로 증거가 있어야 한다. EXTREME 후 변화가 되돌아오고 RETURN의 기준 띠를 충족하면 1사이클을 한 번 발표한다. 진폭/시간 조건·가시성 띠는 개발 자료로 선택하고 고정한다. 다음 반복 하강을 기다리지 않으므로 마지막 반복도 복귀 시점에 발표한다. ✓/세트 종료 호출만으로 미복귀 후보를 강제로 세지 않는다.

긴 가림·일시정지·카메라 변경·배치 변화는 **진행 중 후보**를 끊는다. 양 끝점 사이를 보간해 본 적 없는 극점을 만들지 않는다. 이미 완료한 사이클과 쪽별 횟수는 유지한다. 종료/종목 변경 시 미완료 후보는 남은 부분 움직임으로 기록하고 다음 세트로 넘기지 않는다.

발표 사건은 `cycle_id,start_ms,extreme_ms,return_ms,exercise,working_side,moving_side,side_state,identity_state,quality,placement`를 가진다. `side_state=KNOWN/UNKNOWN/CONFLICT`를 별도로 둔다. 동일 사건의 재발표를 ID로 막는다.

단순 진폭 검출은 자세 합격 판정이 아니다. 얕거나 팔 위치가 틀린 **식별 가능한 운동 반복**도 원시 반복 원장에 남기고 자세 결과를 따로 붙인다. 반면 명백한 걷기/자리 잡기/다른 동작은 반복 원장 대신 기각 사건에 기록한다. 같은 좌표열을 ‘서로 다른 운동’과 ‘틀린 폼의 해당 운동’ 둘 다로 해석할 수 있으면 `identity=UNKNOWN`으로 기록한다. 이 모호성은 독립 주석자의 합의로 정의하고 목표 진행으로 승격하지 않는다.

### 4.2 종목별 주요 신호

| 종목 | 첫 비교 후보 | 동작 확인·반증 | 복귀 |
|---|---|---|---|
| 크로스 런지 | 지지 쪽 `knee_L/R`의 굽힘 + 골반 하강 | 이동 발의 뒤·반대쪽 경로. 두 발의 단순 교차 부호만 쓰면 가림/이름 바뀜을 진짜 교차로 셈 | 지지 무릎과 골반 높이가 돌아오고 교차 발이 준비 배치로 돌아옴 |
| 사이드 런지 | 좌우 개별 무릎 굽힘 + 옆 이동 | 어느 쪽으로 딛는지와 골반 이동. `knee_minside`가 가장 굽은 다리를 바꾸며 만드는 가짜 사이클 반증 | 해당 무릎 폄·골반 복귀·스텝형의 발 복귀 |
| 니업 | 좌우 개별 허벅지 들림 / `knee_h2d_L/R` | 같은 쪽 발목 들림, 지지 다리 유지. 뒤꿈치만 뒤로 올리기·몸통만 숙이기 반증 | **그 다리**의 무릎/발이 낮은 기준으로 돌아옴. 반대쪽은 이미 출발해도 됨 |
| 사이드 크런치 | 좌우 개별 무릎 들림을 넓은 후보 신호로 사용 | 같은 쪽 lateral knee path·`knee_elbow_L/R` 감소·정상 방향 측굴을 병렬 기록. 팔꿈치 접근 합격을 카운트 필수로 걸면 팔 위치/수축 오류 반복 자체를 잃음 | **그 쪽** 다리 복귀와 측굴 해제. 다른 쪽 접근으로 앞쪽 후보를 마감하지 않음 |

니업·크런치는 다리 두 개의 독립 상태가 필요하다. 기존 컬의 `pairedFeatures` 경로는 두 팔 합침·한 팔 가림 폴백·ROM·극점 정책을 포함하므로 이름만 바꾸어 재사용하지 않는다. 공통 사이클 검출부를 추출하되, 동시/교대·단위·가림 정책은 운동별로 명시한다.

카운트하려고 ‘팔꿈치에 무릎이 닿아야 한다’, ‘무릎이 정확히 90도여야 한다’를 요구하지 않는다. 그런 조건은 폼/목표 범위 질문이다. 동작 정체성의 잡음 하한과 자세의 정상 범위는 다른 파라미터다.

### 4.3 좌우와 쌍

시작 자세에서 안정된 두 다리의 이름을 확인하고, 출발 구간부터 발목·무릎·골반의 연속성을 따라 쪽을 유지한다. 교차 극점의 화면 x 순서로 쪽을 다시 이름 붙이지 않는다. 2D와 3D가 충돌하거나 MP 이름 바뀜·길이 급변·가림이 있으면 UNKNOWN이다. 확신 있는 MP 이름 오분류가 기존 런지 연구에 있었으므로 confidence 점수 하나로 해결됐다고 가정하지 않는다.

크로스의 `working_side`는 앞 지지 다리, 사이드는 옆으로 딛는 다리다. 이동 발 이름을 앞 다리 이름으로 저장하면 사용자에게 반대쪽을 안내하므로 둘 다 로그에 남긴다.

쌍 단위에서는 **확인된** `N_L`, `N_R`를 따로 저장하고 표시 완료 쌍은 `min(N_L,N_R)`이다. 왼쪽 10번만 하면 0쌍, 왼10+오10이면 10쌍이다. 번갈아 하기와 한쪽씩 몰아서 하기 모두 같은 계산이다. 양쪽이 목표에 닿기 전에 자동 진행하지 않는다.

쪽 미확인 사이클은 `N_unknown`이다. 런지 쌍 단위에서는 ‘최근 순서상 반대쪽 같음’을 실제 확인 횟수로 채우지 않는다. 화면은 미확인 수와 수동 확인 경로를 제공하고, 미확인을 근거로 반대쪽 음성/쌍 완료/자동 종료를 하지 않는다. 한쪽이 1회인 니업·크런치는 해부학 이름만 모르는 완전한 궤적을 총수에 남길 수 있지만, 궤적 자체가 뒤섞였거나 미완료면 완료 수에 넣지 않는다. 기존 `SideStepCounter`의 추정 채우기는 이 설계에서 그대로 사용하지 않는다. 이 정책은 기존 런지의 동작을 바꾸는 요청으로 확대하지 않고 네 종목의 새 경로에 한정한다.

### 4.4 자세와 목표 진행

반복 원장은 모드와 무관하게 동일하다. 폼 원장은 검사별 `OK/VIOLATION/ABSTAIN`, 측정값·필요 뷰·관측률·상태·근거 버전을 가진다.

- ship 차단 검사에 위반이 있으면 해당 반복의 폼은 FAIL이다.
- 위반이 없고, 선언한 정확 판정 필수 ship 검사들이 **모두 판정 가능하고 OK**면 `PASS_IN_SCOPE`다.
- 필수 ship 검사가 없거나 하나라도 유보돼 합격을 확정할 수 없으면 UNJUDGED다. beta가 정상이라는 이유로 합격하지 않는다.
- FAIL·UNJUDGED도 원시 운동 반복 횟수는 보존한다. COACH 목표 진행에서 제외할지, TRACK에서 원시 반복을 표시할지는 정책이다.
- 새 규칙이 beta인 개발 단계에서는 정확 횟수/점수/자세 음성으로 승격하지 않는다. 횟수도 검증 전엔 참고이고 자동 진행은 검증 모드에서 꺼 둔다.
- 개인 시작 자세/처음 몇 반복은 같은 사람의 동작 변화 기록에 쓸 수 있지만 정상 폼의 정답으로 쓰지 않는다. COACH/TRACK 및 특정 체형별로 모집단 문턱을 달리하지 않는다.

## 5. 오류 카탈로그

여기서 ‘모든 경우’는 무한한 몸 동작을 완전 탐지한다는 약속이 아니라 **이 네 프로필의 준비·수행·복귀·좌우·템포·비관측 오류 범주**를 빠짐없이 관리한다는 의미다. 좌우 반전, 심한 정도, 처음부터/후반만, 둘 이상 동시에 발생하는 조합은 각 항목의 검증 축으로 둔다. 한 사례마다 새 규칙을 계속 만드는 방식은 피한다.

표의 ‘후보’는 아직 검출 가능성과 폰 오탐률을 검증해야 한다. ‘부분’은 보이는 동반 움직임만 기록하며 원인을 진단하지 않는다. 모든 신규 규칙은 beta로 시작한다. C=정면, B/D=앞 사선이며 구체적인 허용 각도는 데이터로 확정한다. SIDE는 현재 미검증이라 허용하지 않는다.

## 6. 구현 순서와 파일 경계

먼저 니업 → 사이드 런지 → 크로스 런지 → 사이드 크런치 순서로 한 종목씩 검증한다. 니업의 좌우 들림/복귀가 크런치와 공유되고, 사이드의 다리 역할/발 경로를 먼저 검증한 다음 교차 가림 문제를 추가한다. 크런치는 무릎·팔꿈치·정상 측굴의 복합 상태라 마지막에 조합한다.

| 단계 | 구현/산출물 | 완료 조건 |
|---|---|---|
| P0 동작·데이터 확정 | ZIP에서 필요한 라벨만 읽는 manifest, 원본/캐시 경로와 해시·종목/변형/수행자/클립/뷰, 오류 ID 목록·라벨 양식 | 뒤 교차/앞 교차·스텝/고정 스탠스·팔 위치 변형 혼합 제거. 분할과 검증 지표 사전 등록 |
| P1 관절→피처 | 계획 파일 `LowerLimbGeometry.kt`, `StandingCrunchGeometry.kt` 또는 같은 책임의 작은 순수 모듈. Python 후보 계산과 Kotlin 파리티 fixture | 동일 입력의 관절/단위/부호·결측 처리 일치, 카메라·체형 스트레스 확인 |
| P2 사이클·쪽 | 운동별 후보 신호와 READY/복귀 상태, 쪽 원장·unknown, 단위 표시 | 마지막 반복·동일 쪽 반복·가림·빠른 교대·세트 종료에서 과다/미완료 카운트 없음 |
| P3 반복 자세 | `RepForm`의 START/진행/EXTREME/RETURN과 `working_side` 기반 창. `RepFormSpecs` 네 프로필의 후보 등록 | 스쿼트 하단 찾기 등 기존 무릎 신호 전제가 니업/크런치에 남지 않음. 신규 규칙 beta·중복 의미 합침 |
| P4 앱 연결 | `ExerciseProfiles.kt`, `PostureSupport.kt`의 map/`Workout.postureSupported()`, `PostureLive.kt`, HUD/세트 로그/리포트/자가 라벨·replay-jvm 목록 | 준비·번호·기록·단위가 동일 사건 사용. 재생기와 실시간의 카운트/폼/쪽/유보 파리티 |
| P5 폰 Gate A/B | 고정 빌드·다중 사람/날짜/배치, 전문 라벨·오탐/관측률/진행 검증 | 종목·규칙·뷰별 통과 범위만 ship. 통과하지 않은 것은 beta/exclude 유지 |

실시간 순서는 `raw frame → quality/placement → geometry → phase candidate → counter event → 해당 사이클 form 창 확정 → 정책/음성/로그`다. 평가기는 카운터 완료 처리 **전부터** 원본 프레임을 받아야 완료 프레임이 다음 창으로 넘어가지 않는다. 같은 이벤트를 여러 처리기가 재검출하지 않고, 하나의 사이클 ID를 공유한다.

기존 `RepFormEvaluator`의 단일 `signalFeature`, 전방 런지용 `Lunge2d.stepSide`, 스쿼트 STANDING/EXTREME, 컬 팔 가림 폴백을 감사한다. 일반화가 필요하면 공통 코어와 운동별 phase/role 전략을 분리하고 기존 스쿼트·컬·런지는 회귀 fixture로 잠근다. 새 운동을 위해 기존 임계값을 바꾸지 않는다.

`posture` 순수 엔진은 앱 최상위·Android·`org.json`에 의존하지 않는다. 로그 직렬화는 기존 직접 문자열 방식을 유지한다. `PostureScope`가 exclude와 유보를 보여줄 수 있도록 규칙 배열을 보존한다.

로그는 사이클 수·쪽별 수·표시 단위·목표 인정 수를 별도로 가진다. 관찰하지 않은 쪽과 폼을 0/정상으로 저장하지 않는다. 규칙 버전·파라미터 버전·seed/placement·원시 프레임·유보/기각/부분 사유도 남긴다. 세트 시작의 종목·뷰·단위를 마감 람다 인자로 고정해 다음 종목 값이 섞이지 않게 한다.

beta 자세는 화면 ‘참고’만, 음성·헤드라인·점수/정확 분모에 넣지 않는다. ship 후 발화도 측정한 현상만 말한다. 예: ‘몸통이 앞으로 기울어졌어요’는 가능하지만 ‘척추 중립이 깨졌어요’로 확대하지 않는다. 한 반복에 여러 오류가 있으면 원인이라고 단정하지 않고 검증된 우선순위의 한 문장만 발화한다. 발화율/정상 오발화도 검증 지표다.

## 7. 실검증 설계

### 7.1 정답 만들기

정답은 앱 카운트·판정 화면을 보지 않고 원본 연속 영상에서 만든다. 앱에 보내는 카메라와 별도의 정답 영상은 시작의 시간 표지로 동기화하고, 정면/사선 등 추가 각도를 통해 숨은 오류를 확인한다. 정답의 반대쪽 카메라가 있어도 앱에게 그 입력을 주지 않는다.

라벨 파일의 최소 열은 다음과 같다.

`subject_id,day_id,session_id,set_id,exercise,variant,working_side,moving_side,start_ms,extreme_ms,return_ms,complete,partial,other_motion,fault_id,severity,fault_start_ms,fault_end_ms,truth_visible,annotator,agreement,source_video`

반복 정답과 각 오류의 정답은 다른 열/원장이다. 전문 코치/운동 지도자 두 명의 독립 주석을 권장한다. 경계 사례는 합의하거나 UNKNOWN으로 남기고, 앱이 맞힌 쪽으로 정답을 고치지 않는다. ‘본인이 일부러 오류를 했다’는 의도 라벨만으로 발이 들렸다고 확정하지 않는다.

기존 자가 라벨의 확인/수정한 총 횟수는 총수 검증에 쓰되, 사이클 시각·좌우·개별 오류 검증의 정답으로 승격하지 않는다. 새 파서는 `side_pair`의 1회와 원시 다리 사이클 두 번을 혼동하지 않아야 한다.

### 7.2 오프라인 개발 검증

1. AIHub를 수행자 기준으로 분할한다. 같은 사람의 다른 클립/뷰/날짜를 개발·평가에 섞지 않는다. 이미 기존 규칙을 고르는 데 사용한 MP 60클립/종목은 **개발 자료**다. 새 봉인 검증이라고 부르지 않는다.
2. GT 3D로 후보 기하를 확인하고, MP 캐시·가용 JPEG로 실제 앱 피처의 측정 오차·유보율·뷰 차이를 확인한다. GT 성적을 MP 성적으로 쓰지 않는다.
3. 클립 오류와 피처의 상관/분류를 후보 선택에 사용하되, 반복 오류는 재주석 후 평가한다. 데이터셋의 라벨 오류가 있으면 원본과 수정 라벨의 차이를 남긴다.
4. 준비→운동→휴식의 **전체** 연속 영상에서 카운트한다. 정답 반복 창으로 입력을 잘라 준비 헛카운트와 마지막 누락을 숨기지 않는다. AIHub의 드문 16시점은 신호 연구용이며 이를 30fps로 보간한 영상은 횟수 정답이 아니다.
5. 공통 코어를 바꾼 경우 기존 스쿼트/컬/전방 런지의 저장 fixture와 재생 결과를 비교한다.

### 7.3 폰 Gate A: 개발 자료

사용자가 실휴대폰 촬영·검증을 직접 한다는 기존 지침을 따른다. 에이전트의 역할은 검증 APK/라벨 양식·계획표·회수/재생/채점 도구를 준비하고, 사용자가 제공한 로그/영상을 분석하는 것이다. 이번 조사에서는 설치도 하지 않았다.

최소 시작안: 개발 피험자 3명, 종목별 6개 짧은 세트(총 72세트) + 규칙별 부족한 오류 세트 보충. 72세트는 신호와 측정 실패를 찾는 파일럿 규모이며 출시 검증 수가 아니다. 정상 범위가 다양한 사람을 포함하고 사람별로 동일 모집단 정책을 적용한다.

| 세트 | 구성/목적 |
|---|---|
| A1 | 정상, 느린·보통 속도, 실제 다리 사이클 5/7/9처럼 목표 10에 편중되지 않은 수 |
| A2 | 정상, 빠른 교대·짧은 극점·긴 정지, 지원 가능한 속도 경계 확인 |
| A3 | 한쪽만 5번, 같은 쪽 2번→다른 쪽 1번, 왼 몰아서→오른 몰아서 |
| A4 | 정상 3 → 오류 한 종류 2 → 정상 3. 반복별 검출·회복 창 확인 |
| A5 | 준비 중 몸 숙이기/발 정리·헛움직임, 마지막 정상 복귀 후 즉시 종료, 극점에서 종료 |
| A6 | 다른 날짜/폰 배치·일시 가림·방향 전환. 같은 폼이 판정을 바꾸는지 확인 |

A4는 한 종류로 전 오류를 대표하지 않는다. §5의 각 후보 오류에 대해 좌/우·약함/명확함·초반/후반·복합 오류를 추가로 수집한다. 판정 불가한 생리/힘 상태를 시연으로 ‘정답화’하지 않는다.

촬영 배치 행렬:

- C와 B/D(좌우 사선), SIDE/후면을 유보 시험으로 별도 포함.
- 정면이 유리한 무릎/측굴과 사선이 유리한 전후 동작을 각각 채점한다. 두 뷰의 결과를 합쳐 ‘한 뷰에서 모두 본다’고 하지 않는다.
- 바닥/무릎 안팎/허리 안팎의 폰 높이, 서로 다른 거리·폰 피치/롤·빛·배경·옷·신발. 먼저 실제로 허용할 범위를 정하고 범위 밖 유보를 평가한다.
- 한 기기의 여러 날짜와 최소 두 성능의 기기/렌즈에서 확인한다. 렌즈·배치가 성능에 미치는 영향은 `placement` 지문과 줄자 실측을 함께 남긴다.
- 카메라 30fps와 실제 추론 3Hz를 혼동하지 않는다. 로그 timestamp로 실효 Hz/간격/추론 지연을 계산하고, 더 빠른/느린 입력 재생은 사전 정의된 스트레스 시험으로만 사용한다.

### 7.4 Gate B: 고정 빌드의 새 사람 평가

Gate A가 끝나면 피처·필터·문턱·ROM·뷰·발화/목표 정책·모델 버전·빌드 해시를 고정한다. **새 사람 최소 5명**, 최소 두 날짜에서 사람·종목·배치에 균형을 둔 평가를 한다. 고정 이후 실패 자료로 값을 바꾸면 그 평가 자료는 개발 자료가 되고 새 봉인 자료가 필요하다.

최초 평가 계획은 종목당 100세트 정도로 시작하되, 이 수로 2%의 드문 과다 카운트 위험까지 입증할 수 있다고 쓰지 않는다. 독립 세트라는 가정에서 0/100의 과다 카운트도 단측 95% 상한은 약 2.95%다. 0/149일 때 약 1.99%다. 사람별 반복 세트는 독립이 아니므로 이 계산은 표본 규모의 참고이며, 최종 보고는 사람별 성적과 사람 군집을 반영한 불확실성을 병기한다. 필요한 새 사람/세트를 늘리거나 통과 범위를 제한한다.

종목·허용 뷰별로 다음을 평가하며 다른 종목의 좋은 결과로 나쁜 종목을 평균 통과시키지 않는다.

| 대상 | 기존 기준 또는 이번 제안 | 반드시 함께 보고할 것 |
|---|---|---|
| 횟수 | 기존 `REP_ENGINE_DESIGN` 기준: 세트 정확 일치 ≥90%, ±1 ≥98%, 세트 안 과다 ≤2%, 시작 헛카운트 ≤0.05/세트 | 원시 사이클·표시 단위·좌우·전체 세트 창별 성적, 항상 목표치/기존 카운터 기준선, 사람별 값·95% 구간 |
| 마지막 반복 | 다음 하강 없이 복귀 시 확정 | 마지막 1회만 있는 세트·즉시 종료·미복귀 종료를 분리 |
| 좌우 | **제안**: 확정 쪽 정확도 ≥99%, unknown 비율 ≤5%를 초기 연구 목표로 둠 | 확신 오분류와 유보를 따로. 좌우 목표 전 조기 종료 시험 사례에서 0건이어야 함. 목표는 검증 결과가 아님 |
| 자세 | 기존 §9의 정상 FPR ≤10%, 균형정확도 ≥80%를 최소 기준으로 계승 | 오류별/방향별 TPR, 정상 FPR, 위반 방향 혼동, 관측률·ABSTAIN, 사람별 구간 |
| 음성 | **제안**: 정상 세트의 잘못된 교정 발화 ≤5%를 별도 목표로 검증 | 발화 단위 정확도·세트당 오발화, 지연, 과한 반복 발화. 베타 침묵·오류 의미와 실제 문장의 일치 |
| 가시성/유보 | **제안**: 지원 배치에서 필수 검사 반복 관측률 ≥90% | 유보가 많아져 FPR만 좋아지는 후보 금지. 뷰/관절별 실패 원인·폼 합격 가능 범위 |
| 사용자 진행 | 두 쪽 실제 목표 충족 전에 넘어가지 않음 | unknown/가림·한쪽만·같은 쪽 중복·모드 전환·종목 전환·수동 종료·재진입 |

새 좌우/음성/관측률 수치는 제품 연구의 초기 목표이며 의학적으로 검증된 상수나 이미 달성한 성능이 아니다. 규칙/뷰 단위로 표본이 부족하면 ship를 보류한다. 균형정확도 하나가 높아도 정상 오발화나 특정 사람의 반복적인 오탐이 있으면 수정·범위 제한 후 새 평가를 한다.

## 8. 필요한 테스트와 남은 결정

엔진을 실제로 구현할 때 다음 의미 있는 테스트를 추가한다. 현재 문서만을 위해 Gradle 테스트를 반복하지 않았다.

- 같은 쪽 두 번이 런지 1쌍이 되지 않음, 왼10/오0은 미완료, 왼10/오10은 완료, unknown을 반대쪽 확정 수로 채우지 않음.
- 크로스 정상 발 교차가 무릎 모임 위반이 되지 않음, 뒷뒤꿈치 들림이 앞 지지 발 오류가 되지 않음.
- 사이드 정상 반대 다리 폄·hip hinge가 오류가 되지 않음, 고정 스탠스형을 스텝 복귀형과 혼합하지 않음.

### 9.2 고정한 개발값과 정책

**카운트용 초기값**: 준비 무릎/허벅지각 145° 이상, 3프레임·400 ms 안정; 이탈 25°; 복귀 10° 띠·120 ms; 후보 최대 15 s; 최대 관측 공백 750 ms. 발 이동/복귀는 준비 다리 길이와 준비 이미지 몸통 길이로 정규화한다. 미완료 종료나 ✓ 버튼으로 후보를 강제 완료하지 않는다. 가림·급격한 마디 길이/이름 반전·큰 방향 변경·일시정지는 후보를 버리고 완료 기록을 유지한다. 준비 countdown에서 얻은 안정 기준은 세트 로그와 재생기에 그대로 전달한다.

두 다리를 같은 시점에 동시에 올리는 동작은 현재 한쪽 들기 프로필의 식별 근거로 삼지 않는다. 서로 다른 시점에 출발한 좌우 후보는 겹쳐도 독립적으로 마감한다. 상체만 숙이기·뒤꿈치만 접기·발이 고정된 측방 이동·스쿼트·앞쪽 교차에 대한 반증을 넣었다. 그 반증의 사람별 민감도/특이도는 아직 모른다.

**자세용 초기값**(모두 beta): 런지 활동 무릎각 125° 초과, 반대 무릎 145° 미만, 들기 허벅지각 115° 초과, 지지 무릎 140° 미만, 비크런치 몸통 측방각 20° 초과, 전후 기울기 −20°~35°(사이드 런지는 정상 힌지를 고려해 상한 55°), 어깨/골반 상대 요 30° 초과, 크런치 같은 쪽 팔꿈치 거리/현재 몸통 길이 1 초과, 무릎 측방 성분/다리 길이 .12 미만, 각 손목/귀 거리/몸통 길이 .65 초과다. **이는 개발 후보 문턱이며 모집단 정상 띠로 보정·승인된 값이 아니다.** 신체 분절/관절 힘을 뜻하지 않는다. 개인 시작 자세를 정상 폼 정답으로 사용하지 않는다.

검사는 종목별 C/B/D 허용 뷰에서만 수행한다. UNKNOWN/SIDE, 쪽 미확인, 극점 표본 2개 미만 또는 해당 피처 관측률 60% 미만은 ABSTAIN이다. 옆으로 굽히는 크런치에 측방각 상한 오류를 적용하지 않았다. 손은 평균이 아닌 좌우 각각 검사한다. 현재 몸통 길이로 정규화한 거리 피처는 원근/분절 오차의 영향을 받으며, 준비 길이 대비 실제 복근 수축률로 해석하지 않는다.

기존 네 종목의 창 규칙은 런타임 `plusRepForm()`에서 EXCLUDE로 남긴다. JSON 원자료는 보존한다. 신규 폼은 음성·점수·횟수 차감에 들어가지 않는다. 원시 반복의 gate 통과와 자세의 정확을 분리해 **폼 정확 수 0, 로그 `correct:false, form_state:UNJUDGED`**를 기록한다. TRACK/COACH는 같은 기하/문턱을 사용한다. 일반 모드의 기존 목표 진행을 유지하되, 검증 모드는 기존 정책대로 자동 진행을 끈다. 카운트 또한 검증 중임을 화면에 밝힌다.

### 9.5 사용자가 진행할 실검증과 재현 도구

`four_exercise_validation.py plan --people 3 --out outputs/four-exercise-validation`으로 **3명×4종목×11상황=132세트** 계획과 빈 `rep-truth.csv`를 만들었다. 이는 촬영 완료 자료가 아니다. 권장 뷰 C/B/D를 나누고 동일 빌드에서 정상 교대, 한쪽 몰아서 수행, 같은 쪽만, 마지막 복귀, 미복귀, 가림, 일시정지, 방향 변경, 서 있기/걷기, 유사 운동, 편안한 작은 범위를 기록한다. 통증이나 무리한 잘못된 자세를 재현하지 않는다.

검증 모드에서 사용자가 직접 촬영한다. 기록된 원시 관절/피처 로그를 회수하고 기존 `setlog_captures.py`로 `.fcap`/manifest를 만든 뒤 `replay-jvm`으로 현재 빌드를 재생한다. 이 변환기는 새 준비 기준도 복원한다. 외부 관찰자/별도 영상의 정답을 보면서 CSV에 **한쪽 완료 사건마다** `id,subject,exercise,return_ms,side`를 적는다. `id`는 replay manifest의 id와 맞추고 시각은 해당 세트 시작 기준 ms다. 런지는 L/R 필수이며 크로스는 앞 지지 다리로 적는다. 실제 반복이 없는 비운동 대조 세트도 한 줄 남기되 `return_ms,side`를 비운다. 앱 숫자를 정답으로 복사하지 않는다.

```powershell
python research/aihub_fitness/four_exercise_validation.py score --truth outputs/four-exercise-validation/rep-truth.csv --predictions outputs/phone-replay/results.jsonl --out outputs/four-exercise-validation/scores.json
```

채점기는 기본 ±750 ms에서 시간 순서를 보존하며 일대일 대응한다. 과다/누락·사건 일치·알려진 쪽의 정확도와 커버리지·표시 단위 정확 일치/MAE를 내며, 누락 예측이나 빈 정답을 성공으로 만들지 않는다. 허용 시간은 촬영 전에 고정한다. 자세 22검사는 별도로 검사/뷰/반복 단위 전문가 정답을 수집하고 ABSTAIN/정상 오탐/오류 검출을 보고해야 한다. 촬영 계획에 쓰지 않은 새로운 사람의 고정 빌드 Gate B는 §7 기준을 따른다. 위 숫자 하나만으로 출시하거나 음성 코칭으로 승격하지 않는다.
