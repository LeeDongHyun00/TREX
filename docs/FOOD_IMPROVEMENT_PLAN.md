### 검토에서 확인한 사실과 아직 모르는 것

- **현재 앱은 342종 모델이다.** 이름 모델은 YOLO 탐지 출력의 좌표를 버리고 클래스별 최고 점수만 쓴다(`food/FoodDetector.kt: classScores`). 위치 모델이 자른 음식은 회색 캔버스의 긴 변 기준 정사각 면적 30%로 배치한다(`FoodRegions.cropPlacement`). 머지 학습은 전체 사진·박스로 학습했으므로, 이 음식 조각 입력과 학습 작업 사이의 차이를 확인해야 한다.
- **머지 3차가 완전한 실패라는 결론은 과하다.** 16장 기록에서 기존 25개 정답은 342종 13개 vs 414종 11개, 새 음식을 포함하면 414종이 15/31개를 맞히고 오검출은 기존과 같은 24개다. 새 음식 이득과 기존 음식 손실이 함께 있다. 서로 다른 분모의 13/25와 15/31을 성능 순위로 바로 비교하지 않는다. 이 수치는 기존 기록이며 이번에 다시 추론한 결과가 아니다.
- **평가 단위가 현재 UI와 다르다.** `training/two_stage_eval/compare_models.py`는 사진 전체의 이름 집합을 비교하고, Top-3도 사진의 어느 박스에서든 정답이 나오면 센다. 다른 음식 박스에 붙은 이름이 맞은 것으로 처리될 수 있다. 기억·이름 없는 사진의 전체 추론 폴백까지 포함한 앱 전체 흐름과도 다르다. 모델 자체 비교와 앱 전체 비교를 따로 보고한다.
- **원인을 확정한 실험이 부족하다.** '실사처럼 보이면 서양 음식으로 판단한다'는 가설이다. 평균 mAP 유지가 음식별 망각 없음을 증명하지도 않는다. 원본 `.pt`와 앱 INT8 모델의 같은 입력 비교가 필요하다. 병렬/앙상블 실험의 구체적인 설정·로그는 이번 저장소 검토에서 찾지 못했으므로 실패 원인을 단정하지 않는다.
- **라벨 품질 문제 후보:** `merge_food101.py`는 가장 큰 박스, 없으면 가운데 90%를 음식 위치 정답으로 삼으며 검증 박스도 자동 생성한다. `aihub242_map.py`에는 김치찌개→돼지고기김치찌개, 냉면→물냉면, 무김치→깍두기처럼 원본보다 구체적인 이름으로 바꾸는 규칙이 있다. 사진 검수 없이 동일 음식이라고 확정하지 않는다.
- **즉시 개선 가능한 기억 경로:** `PhotoFoodSheet.rememberUserNamed`는 사용자가 음식 이름을 붙여도 `looksEmpty`이면 저장하지 않고, `FoodPipeline.withMemory`도 같은 자리를 비교하지 않는다. 미등록 음식·작은 반찬을 빈 그릇으로 오인하면 사용자가 가르쳐도 기억하지 못한다. 저장과 조회 양쪽을 함께 다뤄야 한다.

### 1. 사진별 이름 평가를 음식 자리별 평가로 바꾸기

**파일 제안:** 새 `training/food_eval_v2/README.md`, `evaluate.py`, `test_evaluate.py`. 원본 사진·정답표·추론 결과의 로컬 경로는 인자로 받고 Git 제외를 확인한다. 기존 평가 스크립트는 비교 근거로 보존한다.

- [ ] 정답 형식을 먼저 고정한다: `image_id`, `meal_group_id`, `split`, `regions[{id, box_xyxy_normalized, kind, canonical_name, acceptable_names}]`. `kind`는 `food`/`empty`/`nonfood`. 사람도 세부 이름을 확정 못 하는 음식은 넓은 이름과 허용 답을 사전에 명시한다. 모델 결과를 보고 정답을 추가하지 않는다.

**완료물:** 위치/이름/입력 배치/변환 중 어느 구간에서 손실이 생기는지 보여주는 표와 대표 실패 사진. 차이가 불명확하면 데이터 추가 학습을 성공 해법으로 확정하지 않는다.

### 3. 이름이 병목일 때: 음식 조각 전용 분류기 소규모 실험

**파일 제안:** 새 `training/food_crop_classifier/build_crops.py`, `train_linear.py`, `README.md`. 산출물·특징값 캐시는 Git 제외 로컬 폴더에 둔다.

- [ ] 기존 AI Hub·UEC의 검수된 박스를 이용해 음식 조각을 만든다. Food-101은 자동 박스를 정답으로 무조건 믿지 않고 학습용 일부를 검수하며, 평가용 위치·음식 이름은 사람이 확인한 것을 사용한다. 데이터셋 전체 파일을 다시 대량 다운로드하기 전에 현재 로컬 자료를 재사용한다.
- [ ] 잘못 좁혀진 이름 매핑을 검수한다. 김치찌개처럼 재료를 모르면 넓은 이름으로 보존하고, 기존 세부 클래스에 억지로 합치지 않는다. 음식 ID·표시 이름·영양 DB 항목의 대응표를 별도로 유지한다. 출처 간 중복·근접 중복과 같은 끼니가 학습/검증을 넘지 않게 한다.
- [ ] **첫 비교 후보는 앱에 이미 있는 DINOv2의 384차원 특징 + 선형 분류기.** 특징 추출기는 고정하고 기존 음식과 추가 음식을 함께 학습한다. 음식별·출처별 샘플 수를 보고 한쪽이 학습을 지배하지 않게 배치를 조절한다. 폰에서 쓰는 특징 추출 전처리·모델과 학습용 특징이 같은지 먼저 확인한다.
- [ ] 기존 YOLO 이름 모델, 414종 머지 모델, 새 분류기를 같은 자리·같은 정답표로 비교한다. 첫 목적은 Top-3 후보 개선이다. 후보가 좋아졌다고 자동 이름 기준까지 바로 완화하지 않는다. 미등록 음식·빈 그릇으로 오명명도 따로 확인한다.
- [ ] 선형 분류기에서 신호가 있을 때만 더 큰 분류기/미세조정/경량화 실험으로 넓힌다. 신호가 없으면 매핑·음식 조각·특징 구분력을 먼저 점검한다. 여러 모델의 raw score 중 가장 큰 값을 고르는 앙상블을 기본안으로 삼지 않는다.

**완료물:** 현재 방식과 새 방식의 같은 입력 비교. DINOv2 재사용은 유망한 실험 제안이며 정확도·속도 개선을 보장하지 않는다. 특징 추출을 모든 박스에 실행하면 현재보다 느려질 수 있으므로 폰 측정이 필요하다.

### 4. 별도 작은 개선: 사용자가 확인한 음식은 기억할 수 있게

**대상:** `app/src/main/java/com/example/trex_kotlin/PhotoFoodSheet.kt`, `food/FoodPipeline.kt`, `food/FoodRegions.kt`, 필요 시 새 순수 정책 파일 `food/FoodMemoryPolicy.kt`; 검증은 `food/FoodPipelineTest.kt`, `FoodRegionsTest.kt`, `FoodMemoryTest.kt` 및 새 `FoodMemoryPolicyTest.kt`.

- [ ] 먼저 실패 사례를 고정한다: 이름 점수 0.02 미만인 실제 반찬 → 숨김 펼치기 → 사용자가 이름 선택 → 기록 → 다음 인식. 현재 저장/조회에서 제외되는 것을 확인한다. 이름이 같은 여러 박스가 한 줄로 합쳐지는 경우도 넣는다.
- [ ] 사용자가 확인한 자리의 `regionId`와 선택한 이름을 줄 병합 이후에도 추적한다. 저장 후보를 고르는 순수 정책을 분리해 **직접 확인한 실제 음식은 낮은 모델 점수만으로 제외하지 않게** 한다. 자동 이름·단순 기록 버튼·취소한 선택을 사용자 교정으로 오인해 저장하지 않는다.
- [ ] 기억이 있을 때 낮은 점수의 자리도 비교할 수 있도록 조회를 함께 바꾼다. 초기안은 그 자리의 기억 결과를 **후보로만** 보여주고 자동으로 이름 붙이거나 기본 숨김을 해제하지 않는다. 이를 위해 `FoodRegion`에 `memorySuggestionOnly: Boolean = false`를 두고 저점수 자리의 기억 비교에서 true로 설정한다. 이때 `rememberedName`은 null, `remembered` 후보 목록은 유지한다(0.77을 넘어도 자동 이름이 되지 않음). 숨김을 펼쳐 선택할 수 있어야 한다. 빈 그릇 자동 오명명과 전 박스 임베딩 비용을 측정한 뒤 자동 표시 확대 여부를 정한다.
- [ ] 회귀 확인: 직접 확인한 저점수 음식은 저장되고 다음에 후보로 나옴, 실제 빈 그릇은 자동 기록되지 않음, 취소/자동 이름은 학습하지 않음, 같은 이름으로 합친 다른 자리에는 사용자 확인이 전파되지 않음, 기존 고침 기억·저장 한도·백업 제외 유지. 기억 평가는 같은 사진 재입력과 다른 날 사진을 분리한다.

**완료물:** 모델 학습과 독립적으로 검토 가능한 작은 변경. 결과가 예측 가능해질 때까지 저장만 고치거나 자동 기억 문턱을 일괄 낮추지 않는다. 1단계 평가 준비와 독립적으로 진행할 수 있으나, 이번 계획 작성에서 구현한 것은 아니다.

### 5. 채택 기준과 앱 반영 순서

- [ ] 실행 전에 비교 대상·평가 세트·자동 이름 기준을 고정한다. **예비 목표(검증된 기준 아님):** 자리별 Top-3가 기존 대비 5%p 이상 개선, 기존 공통 음식 Top-1 저하 2%p 이내, 잘못 자동으로 이름 붙인 수/사진 증가 없음. 개선 수·퇴보 수와 음식별 표본 수를 함께 보고한다. 표본이 작거나 끼니 단위 paired bootstrap의 차이 구간이 0을 포함하면 개선 확정 대신 추가 측정으로 남긴다.
- [ ] 조건을 통과한 후보만 새 최종 평가 세트로 한 번 확인한다. 최종 평가를 보고 다시 튜닝하면 그 세트는 개발용으로 전환하고 새 평가 세트를 확보한다. 자동 이름이 나쁘고 후보만 좋아지면 후보 기능으로 한정하는 선택이 가능하다.
- [ ] 실제 폰에서 모델 로드, 음식 많은 사진의 전체 처리 시간(전처리 포함) 중앙값/p95, 메모리·오류를 기준선과 비교한다. **예비 시간 예산은 p95가 기준선의 1.2배 이내**로 두되 사용자 체감과 함께 판단한다. 폰이 없으면 PC 결과와 미검증 항목을 기록하고 모델 교체를 완료 처리하지 않는다.
- [ ] 앱 변경 시 `:app:testDebugUnitTest`, `:app:assembleDebug`와 해당 공유/iOS 검증을 수행한다. 모델·라벨·DB 대응은 `FoodLabelDatabaseTest`, 입력 배치는 `FoodInputsTest`, 흐름은 `FoodPipelineTest`로 확인한다. 기존 파일을 보관해 되돌릴 수 있게 한 뒤 후보 기능/모델 교체/기억 수정은 각각 설명 가능한 변경으로 정리한다.

### 내일 먼저 할 일과 추가 메모

1. **0단계 파일 목록 확인 → 1단계 정답표·평가기 설계부터 시작한다.** 기존 사진·모델만으로 할 수 있는 작업을 먼저 끝내고 새 사진 확보량을 정한다. 새 학습을 바로 밤새 돌리는 순서는 권하지 않는다.
2. 사용자가 나중에 도와줄 부분은 사진 속 실제 메뉴 확인과 다른 날 같은 음식 사진 제공이다. 지금 잠들기 전에 준비할 필수 절차는 없다. 0~3단계 준비에는 휴대폰 연결이 필요하지 않다.
3. 식약처 DB 확대는 검색 선택지·영양값 개선으로 별도 진행할 수 있다. DB 추가만으로 사진 모델이 새 음식을 알아보지는 않는다. 기존 문서의 '33%'는 당시 소수 사진의 커버리지 결과이지 전체 사용자의 고정 비율이 아니다.
4. 기존 '확신 NN%'는 보정되지 않은 모델 점수다. 새 후보/기억 유사도와 같은 확률처럼 비교하지 말고, 화면 문구도 실제 의미에 맞는지 앱 반영 단계에서 검토한다.
5. 단계별 결과에는 측정한 사실·가설·아직 실행하지 못한 비교를 나눠 적는다. 오래된 §10의 '망각 없음'·'스타일 지름길' 단정은 새 평가 문서에서 근거 수준을 정정하고, 기존 수치는 이력으로 남긴다.
6. 참고: [DINOv2 공식 분류 활용](https://github.com/facebookresearch/dinov2), [LiteRT 양자화 전후 비교](https://developers.google.com/edge/litert/conversion/tensorflow/quantization/post_training_integer_quant). 이 자료는 실험 방법의 근거이며 TREX에서의 성능 증거는 아니다.
