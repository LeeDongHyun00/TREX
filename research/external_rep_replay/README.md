# 외부 코퍼스 렙 카운터 재생 — 현재 앱 `RepCounter`

반복 정답이 있는 외부 데이터(MM-Fit, REHAB24-6)에 **지금 앱이 세션에서 쓰는 카운터**를 그대로 돌려,
"AIHub 에서 뽑은 렙 로직이 연속 동작·휴대폰 조건에서도 통하는가"를 스쿼트·런지·덤벨 컬 세 종목에서 잰다.

## 0. 상태 (2026-09-23)

| 실험 | 상태 |
|---|---|
| **본 실험** — 영상 → MediaPipe(앱 모델) → 현재 카운터 | **미실행.** MM-Fit 영상과 REHAB24-6 은 zenodo.org 에 있는데 이 작업 환경의 네트워크 정책이 그 호스트를 거부했다. 코드는 준비·검증돼 있어 호스트가 허용되면 §6 명령으로 바로 돈다 |
| **보조 실험** — MM-Fit 데이터셋 자체 3D 포즈 → 현재 카운터 | 실행함(§4). MediaPipe 결과를 대신하지 않는다 |

`docs/mmfit-rep-counting.v1.md`·`docs/rehab-rep-f1.v1.md` 의 숫자는 **다른 계열 엔진**(`HeuristicFormCheckSession`,
`app/src/testDebug.other-lineage`)의 측정이다. 지금 앱의 `RepCounter`(복귀형)와는 알고리즘이 다르다.

## 1. 구성

| 파일 | 역할 |
|---|---|
| `replay-jvm/` | 앱 소스 `PostureCore.kt`·`RepCounter.kt`·`ReturnRepTracker.kt` 를 **복사 없이 그 자리에서** 컴파일하는 Kotlin/JVM 재생기 |
| `extract_mediapipe.py` | 영상 → MediaPipe 캡처 (MM-Fit 세트 / REHAB24-6 녹화) |
| `mmfit_pose3d_captures.py` | MM-Fit `pose_3d.npy` → 같은 형식의 캡처 (보조 실험) |
| `capture_format.py` | 캡처 형식, 앱 추론 주기 |
| `run_replay.py` | 매니페스트 생성 → 재생 → 채점 (세트 반복 수, 반복 경계 F1) |
| `results/` | 요약 수치 (원본 캡처는 `data/` — git 제외) |

## 2. 앱과 맞춘 것, 다른 것

**맞춘 것**
- 카운터 구성: `PostureLive` 의 서서 하는 종목 경로 그대로 — `RepCounter(signal, maxGapMs = 1500, completeOnReturn = true)`.
  `rules_mp_v0.json` 에 `kind=rep` 규칙이 없어 신호·ROM 기준은 `RepSignals` 등록부 값이다.
- 신호: 스쿼트 `knee_mean`(35°), 런지(앱 '런지' = 스텝 포워드 다이나믹 런지) `knee_out_mean`(0.10), 덤벨 컬 `elbow_mean`(35°).
- 추론 후처리: `PostureAnalyzer.analyzeBitmap` 과 같은 순서(visibility·presence 최솟값, 0.5 미만 관절 제외,
  m→cm·y·z 반전, `checkUpSanity`, `PoseFrame.features()`). 이 부분만 Android 타입 때문에 절차를 옮겨 적었다(`Replay.kt` 머리 주석).
- MediaPipe: 앱 번들 모델(`posture/pose_landmarker_full.task`, SHA `4eaa5eb7…` — 다른 계열 측정과 같은 파일),
  VIDEO 모드, `num_poses=1`, 신뢰도 0.5, `mediapipe==0.10.14`(앱 tasks-vision 과 같은 버전).
- 추론 주기: 직전 추론 이후 300ms 이상인 프레임만. 건너뛴 프레임은 랜드마커에도 넣지 않는다.
- 사람이 검출된 프레임에서만 `onFrame` 을 부른다(앱과 같다).

**다른 것 — 결과를 읽을 때 따라가야 한다**
- 카메라: 휴대폰이 아니다. MM-Fit 은 고정 정면 한 대(Orbbec). REHAB24-6 은 같은 자리의 두 대로 가로(cam17)·세로(cam18) 화면비만 다르다
  (`docs/rehab-rep-f1.v1.md` §3.4) — 같은 반복을 다른 **각도**에서 본 자료가 아니다.
- 중력: 영상에 IMU 가 없어 up = 화면 세로축(앱의 센서 없는 폴백).
- 델리게이트 CPU(앱은 GPU 우선), 발열 감속 없음.
- 30fps 영상 시각이 정수 ms 라 추론 간격이 정확히 300ms 다(실기기는 지터로 300~333ms).

## 3. 검증

- 앱 저장소의 카운터 유닛 테스트 19개(`RepCounterTest` 12, `ReturnRepTrackerTest` 7)를 이 재생기가 컴파일한
  카운터로 돌려 전부 통과했다 — 재생기의 카운터가 앱 테스트가 기대하는 그 카운터다.
- MediaPipe 공개 테스트 이미지(`mediapipe-assets/pose.jpg`)로 만든 합성 영상으로 추출 → 재생 → 채점을 끝까지 돌렸다
  (11샘플 전부 검출, 피처 정상). **실제 반복 영상으로는 아직 검증하지 않았다.**
- 경계 채점 함수는 손으로 계산한 예제와 일치한다.

## 4. 보조 실험 결과 — MM-Fit 자체 3D 포즈 (MediaPipe 아님)

데이터: MM-Fit (Strömbäck, Huang, Radu, IMWUT 2020, doi:10.1145/3432701, **CC BY 4.0**) 21개 워크아웃,
세 종목 185세트(스쿼트 64, 런지 62, 컬 59). 포즈는 데이터셋이 제공한 H36M 17관절 3D(연속 30fps 영상에서 추정).
세트 정답은 반복 수뿐이라 경계 F1 은 계산할 수 없다. 앞뒤 여유는 다른 계열과 같은 0.5초, 민감도로 2초.

**앱 구성(live)** — 과다 카운트는 모든 구성에서 0건(정밀도 1.000)

|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 스쿼트 `knee_mean` (여유 0.5s) | 64 | 639 | 576 | 161 | 0.98 | 0.81 | 0.53 | 1 | 0.901 | 0.948 |
| 스쿼트 (여유 2s) | 64 | 639 | 604 | 171 | 0.55 | 0.88 | 0.75 | 1 | 0.945 | 0.972 |
| 런지 `knee_out_mean` (0.5s) | 62 | 624 | 62 | 62 | 9.06 | 0.00 | 0.00 | 39 | 0.099 | 0.181 |
| 런지 (2s) | 62 | 624 | 62 | 62 | 9.06 | 0.00 | 0.00 | 41 | 0.099 | 0.181 |

**진단 — 앱 동작이 아니다.** 같은 복귀형 구성에 신호만 바꿨다. 앱의 다른 종목이 이미 쓰는 신호만 골랐고 ROM 기준은 뗐다.

|---|---|---|
| 런지 `knee_mean` (앱 '크로스 런지' 신호) | 0.838 / 0.912 | 0.875 / 0.933 |
| 런지 `knee_minside` (앱 '바벨 런지' 신호) | 0.689 / 0.816 | 0.766 / 0.868 |
| 덤벨 컬 `elbow_minside` | 0.873 / 0.932 | 0.851 / 0.920 |
| 반전형(`RepCounter` 기본 구성, 앱 세션은 안 씀) — 스쿼트·런지·컬 재현율 | 0.886 · 0.077 · 0.751, 정확 일치 0 | 0.887 · 0.077 · 0.755, 정확 일치 0~0.02 |

### 해석

1. **런지 — 신호 선택 자체가 연속 동작에서 무너진다.** `knee_out_mean` 은 62세트 중 39세트를 0회로 셌다.
   세트별 흔들림(p95−p5) 중앙값이 0.090 으로 최소 스윙 0.10 에 못 미친다. 앞으로 딛는 런지에서 무릎은 앞으로 나가지
   옆으로 벌어지지 않으므로, 옆 이탈 신호에는 반복이 담기지 않는다. 이 신호는 AIHub 0.6초 간격 조사(`REP_SIGNALS.md`)에서
   일관성 1등이었다 — 성긴 데이터에서 고른 신호가 조밀한 연속 데이터에서 통하지 않은 직접 사례다. MediaPipe 이전의 문제다.
2. **스쿼트 — 세기는 대체로 된다. 놓치는 원인은 두 가지다.**
   - 기준 자세: 복귀형 추적기는 한 자세에 3샘플 연속(300ms 간격이라 최소 600ms) ±7.7° 안에 머물러야 기준을 잡는다.
     쉬지 않고 연속으로 하면 세트 전체가 0회다. w00 첫 세트는 무릎각이 70°↔165° 로 10번 뚜렷한데 0회였다.
     여유를 2초로 늘리면(준비 자세가 보이면) 재현율 0.901 → 0.945.
   - 템포: 반복당 1.6초 미만 세트는 재현율 0.50(3세트), 1.6~2.0초 0.88(34세트), 2초 이상 0.97(27세트).
   - ROM: 검출된 반복의 28%(161/576)만 유효다. 코치 모드였다면 대부분을 "무효"로 말했다. 원인은 둘로 갈린다.
     (a) 정의 불일치 — 카운터는 300ms 간격이면 3점 중앙값으로 평활하고, ROM 은 **평활된** 사이클 최저값을 본다. 바닥은 보통
     한 샘플에만 찍히므로 평활이 그것을 지운다(세트 하위 2% 무릎각: 원값 92.3° → 평활 101.1°). 기준 97.9° 는 평활하지 않은
     AIHub 값에서 뽑았다. 반복 사이 구간의 원값 최저를 쓰면 유효가 346/576(60%)으로 는다(근사 추정).
     (b) 동작 차이 — 나머지는 MM-Fit 맨몸 스쿼트가 AIHub 기준보다 얕아서다. 이 3D 포즈의 무릎각이 MediaPipe 와 다를 수 있어
     두 몫의 크기는 본 실험으로 다시 봐야 한다.
3. **덤벨 컬 — 교대 동작에서 세기는 되지만 ROM 이 거의 전부 무효다.** MM-Fit 컬은 좌우 교대다. 한쪽 팔을 굽힐 때마다
   양팔 평균이 약 50° 움직여 35° 게이트를 넘으므로 센다(재현율 0.82~0.86, 1.6초 미만 템포 7세트는 0.59).
   그러나 평균은 81.3°(ROM 기준) 아래로 내려갈 수 없어 유효 판정이 14/512(3%)다.
   여유를 2초로 늘리자 2세트(w00·w05 마지막 컬 세트)가 0회로 바뀌었다. 복귀형 추적기는 **처음 안정된 자세**(3샘플 ±7.7°)를
   세트 내내 기준으로 고정하는데, 이 두 세트는 덤벨을 든 채 팔꿈치가 122~129° 로 굽은 준비 구간에서 기준을 잡았다.
   이후 컬은 그 기준에서 35° 이상 벗어나지 못해 한 번도 "움직임"으로 시작되지 않았다.
4. **반전형은 정확 일치가 0이다** — 다음 하강이 있어야 상단을 확정하므로 세트의 마지막 반복을 구조적으로 놓친다(`CLAUDE.md` 함정과 같다).
   앱 세션은 복귀형을 쓰므로 이 결함은 세션 카운트에는 해당하지 않는다.

가설과 연결하면: 카운트 **메커니즘**(복귀형)은 깨끗한 연속 골격에서 대체로 작동한다. 반면 AIHub 에서 온 **선택과 기준**
(런지 신호, ROM 임계값)은 연속 데이터에서 무너졌다. 휴대폰·MediaPipe 조건이 여기에 무엇을 더하는지는 본 실험이 답한다.

## 5. 한계

- 보조 실험의 포즈는 MediaPipe 가 아니다(2D→3D 추정). 여기서 잘 센다고 휴대폰에서 잘 센다는 뜻이 아니다.
- MM-Fit: 고정 정면 카메라, 맨몸 스쿼트·런지, 세트 단위 정답(경계 없음). 여유 길이에 따라 결과가 달라진다(§4 두 줄).
- 이 결과로 임계값·신호를 적합하지 않았다. REHAB24-6 은 CC BY-NC 4.0 이라 측정에만 쓸 수 있다.

## 7. "촬영기기·각도 때문에 MM-Fit 에서 안 된다" 가설 검토 (2026-09-23)

주장: 현재 엔진은 AIHub 로 배운 것이고, MM-Fit 에서 제대로 안 되는 이유는 촬영기기·각도이므로, MM-Fit 도 정답 기준으로 삼는다.
실험 4개(시점 변환, 실제 코드 상태 계측, 문서 감사, MM-Fit 라벨 감사)와 찬반 논증, 독립 판정 2개로 검토했다.
작업 산출물은 `data/mm-fit/exp_*`(git 제외).

| 고리 | 판정 | 결정적 근거 |
|---|---|---|
| 엔진은 AIHub 로 배웠다 | 절반만 맞다 | AIHub 에는 반복 정답이 없어 횟수를 학습한 부품이 없다. AIHub 에서 온 것은 런지 신호 선택과 ROM 기준뿐이고, 복귀형 추적기·35° 게이트·평활은 설계와 폰 데이터에서 왔다(spec §27·§42, `RepCounter.kt` 주석) |
| MM-Fit 에서 안 된다 | 맞다 (대리 입력 기준) | 세트 정확 일치 스쿼트 0.53 · 런지 0.00 · 컬 0.42. 185세트 중 174세트가 10회라 "항상 10" 이 엔진보다 낫다(MAE 0.08·0.10·0.15 대 0.98·9.06·1.47) |
| 원인은 촬영기기·각도다 | 반증 (측정된 실패에 대해) | ① 폰·MediaPipe 가 없는 입력에서 같은 실패가 난다 ② 같은 300ms 신호에 평활·기준자세 없는 단순 인과 카운터(35°)를 돌리면 스쿼트 0.997 · 런지(`knee_mean`) 0.990 · 컬 0.998 — 반복은 신호 안에 있고 엔진이 잃는다 ③ 스쿼트·컬 신호는 세 관절 각이라 회전 불변: 시점 변환 26개에서 123세트 중 0세트 변화 ④ 놓친 712회 중 기기·각도에 민감한 원인은 최대 4회 ⑤ 스쿼트는 MM-Fit 정면이 앱 권장 방향과 같다 |
| 그래서 MM-Fit 도 정답으로 | 결론만 맞다, 이유는 틀렸다 | 라벨은 실제 센 값이다(3D 포즈 오프라인 계수와 180/185 세트 일치). 이유는 각도가 아니라 "AIHub 가 줄 수 없는 연속 세트 횟수 정답"이라서다. 원인이 정말 기기·각도라면 필요한 기준은 앱 권장 방향의 폰 데이터이지 MM-Fit 이 아니다 |

놓친 반복의 원인(실제 코드의 내부 상태를 매 프레임 읽어 배정): 런지는 신호 폭 부족(562회 중 513회, `knee_out_mean` 반복당 이동 중앙값
0.052 < 게이트 0.10, 두 반복마다 되풀이되는 보폭 신호). 스쿼트·컬은 상단 체류 부족으로 복귀 조건 미충족(26·29), 3점 중앙값 평활(7·40),
0.5s 여유에서 마지막 반복 잘림(20·14 — 평가 인공물), 준비 자세에 잘못 잡힌 기준. 불응기 1.2s 와 1.5s 끊김 초기화는 영향 0.
시점 변환 중 결과를 움직인 것은 IMU 가 없을 때의 카메라 기울기가 런지 `knee_out_mean` 에 들어가는 경로 하나다(재현율 0.06~0.35).
앱은 중력 센서가 있으면 이 경로를 닫고, 최선의 경우도 `knee_mean` 0.84 에 못 미친다.

**MM-Fit 을 쓰는 규칙.** 세트 단위 반복 수와 휴식 중 오카운트(현재 컬 1.53회/분)의 정답으로만 쓴다. 참여자 10명 중 P0·P1 이 반복의 56% 라
피험자 단위로 나눠 보고한다(처음 보는 피험자 재현율: 스쿼트 0.833, 컬 0.729). "항상 10" 기준선을 같은 표에 싣는다.
ROM·깊이 기준은 맞추지 않는다 — 스쿼트 바닥 중앙값이 사람마다 64.9°~108.2° 인 스타일 차이라 원칙 #3·#4 에 걸린다.
교대 컬은 양팔 평균 81.33° 에 구조적으로 닿지 못한다(한 팔 기준 601/604 통과) — 기준값이 아니라 판정 정의의 문제다.

**아직 답이 없는 것.** MediaPipe 가 시점에 따라 더하는 추정 오차(특히 정면에서 카메라 쪽으로 굽는 팔꿈치), 폰 조건(IMU·GPU·지터).
MM-Fit 영상으로 같은 185세트를 재생해 대리 입력과 세트별로 짝지으면 MediaPipe 의 몫이 나온다. 각도 자체는 같은 반복을 두 방향에서
찍은 자료로만 판정된다(MM-Fit 두 번째 시점 영상이 있으면 그것, 없으면 폰 두 대 동시 촬영).
