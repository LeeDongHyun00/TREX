# 바닥 규칙 판정 기준 감사 (rules_floor_v0.1, 14규칙 / 8종목)

규칙은 '충실도 게이트 통과 피처 중 CV AUC 최대'로 **자동 선택**됐다. AUC 는 좋은데 **조건명이 말하는 것과 실제로 재는 것이 다른** 규칙들이 있다. 성능 지표만으로는 이걸 못 잡는다(§21 요건: 한 조건 = 한 메커니즘, 방향 특이성).

## 1. 채택 피처 vs 조건명에 맞는 피처

조건명이 문자 그대로 가리키는 '자연 피처'를 직접 지정해 비교했다. **14건 모두 채택 피처가 같거나 우세** — 즉 성능만 보면 교체할 이유가 없다.

## 2. 성능이 아니라 '판정이 말이 되는가' — 심화 검증

### 🔴 A. 크런치 '견갑골' — 사실상 판정 불가
- 조건은 **견갑골(어깨)** 이 지면에서 뜨는지인데, 규칙은 **머리 높이**(`head_ground__max`)를 잰다.
- 조건명에 맞는 `shoulder_ground` 의 **MP 충실도 ρ = −0.002**(max) / 0.216(mean) — MediaPipe 로는 어깨의 지면 대비 높이를 **아예 못 잰다**. 그래서 게이트에서 탈락하고 머리가 대신 뽑혔다.
- 대신 쓰는 머리 지표도 **ρ = 0.38** 로 낮다(전 규칙 중 최저).
- 실측: **'머리는 기준을 통과했는데 어깨는 하위 25% 미만'인 클립 42개 중 24개가 실제 위반.** 크런치의 대표 오류인 **목만 당기고 상체는 안 올라오는 자세를 규칙이 통과시킨다.**
- → 이 규칙은 조건명이 약속하는 것을 이행하지 못한다. **제거하거나, 판정 대신 '측정 불가'로 표시**하는 것이 정직하다.

### 🔴 B. 플랭크 '몸통-엉덩이 정렬' — 정반대 오류를 한 경고로 뭉갠다
- 채택 피처 `trunk_ankle_ang`(어깨-골반-발목 각)은 **꺾인 정도만** 재고 **방향이 없다**.
- 실측: 위반 클립 104개가 **엉덩이 솟음 69% / 처짐 31%** 로 **양방향으로 갈린다**.
- 두 오류는 처방이 정반대(내려라 / 올려라)인데 같은 경고가 나간다. 실제로 코치 문구가 `"엉덩이가 처지거나 솟아 있어요"` 로 **양쪽을 다 말하며 얼버무리고 있다** — 이게 증거다.
- 부호 있는 `hip_dev_ankle` 을 쓰면 방향을 구분할 수 있으나 AUC 0.794 → 0.732 로 떨어진다. **정확도와 실행 가능성의 교환**이다.

### 🟠 C. 힙쓰러스트 '고개 들지 않기' — 흔들림으로 판정하는데 문구는 '들려 있다'
- 채택은 `head_trunk_ang__std`(**흔들림**) 0.874, 평균 각도는 0.770.
- 실측 방향이 어긋난다: 위반 클립의 **평균 고개각이 71.0° 로 정상 78.6° 보다 오히려 작다**(각도가 클수록 젖힘). 즉 라벨상 '고개 듦' 위반인데 데이터는 '덜 젖혀지고 더 흔들림'을 보인다.
- 코치 문구는 `"처음부터 고개가 들려 있어요"` 인데 실제 판정 근거는 **움직임의 크기**다. 설명과 근거가 불일치한다.
- 다만 '평균은 높은데 흔들림은 작은'(계속 든 채) 클립 26개 중 **실제 위반은 0개** — 연기 데이터에는 그런 케이스가 없어, 놓침이 실측으로 확인되지는 않았다. 실사용자에게서 나타날 수 있는 위험이다.

### 🟠 D. Y-Exercise '경추 중립/후인' — 목을 잰다면서 골반을 잰다
- 채택 `hip_dev_knee__min`(골반이 어깨→무릎 선에서 벗어난 정도) 0.759 vs 머리 각도 0.669.
- 골반 위치가 '경추 중립' 라벨을 머리보다 잘 예측한다 = **라벨이 실제로는 경추가 아니라 전신 자세의 변화를 담고 있다**(§21 에서 본 '라벨 ≠ 연기된 편차' 패턴).
- ρ=0.447 로 측정 신뢰도도 낮다. 사용자에게 "목을 중립으로"라고 말하지만 근거는 골반이다.

### 🟡 E. 구조적 편중
| 관찰 | 수치 |
|---|---|
| 고개 각도(`head_trunk_ang`)에 의존하는 규칙 | **5/14 (36%)** |
| MP 충실도 ρ<0.5 인 규칙 | 4/14 (크런치 0.38, 푸시업·니푸쉬업 가슴이동 0.44/0.45, Y-Ex 0.45) |
| AUC<0.80 인 규칙 | 6/14 |
| 개인 기준선(personal_baseline) 적용 규칙 | **0/14** — 임계값이 절대값이라 체형·목 길이 차이를 흡수하지 못한다 |

'자세 교정'이라고 부르지만 **판정의 3분의 1이 고개 위치**다. 측정이 잘 되는 쪽(머리)으로 규칙이 쏠린 결과이며, 정작 각 종목의 핵심 오류(견갑골, 허리 처짐 방향)는 못 잡거나 뭉개고 있다.

### 🟡 F. 같은 조건, 다른 피처
'손의 위치 가슴 중앙 여부'가 푸시업은 `shoulder_dev__mean`, 니푸쉬업은 `shoulder_arm_ang__mean` 이다. **푸시업에서 두 피처의 AUC 가 0.783 로 완전히 동일**하므로, 성능 손실 없이 통일할 수 있다. 통일하면 사용자에게 같은 설명을 할 수 있다.

## 2-2. 🔴 실기기 대조 — 플랭크는 처짐을 사실상 못 잡는다

**감사 1차에서 빠뜨린 검증이다.** 조건-피처 정합성만 보고, 이미 확보한 실기기 로그에 임계값을 대조하지 않았다. 사용자가 "엉덩이가 내려갔는데 100% 로 나왔다"고 지적해 확인한 결과:

| | 값 |
|---|---|
| 실기기 플랭크 세트 평균 `trunk_ankle_ang` | **152.1°** |
| 규칙 임계값 | 133.35° 미만이면 위반 |
| 여유 | **+18.8°** — 평균이 19° 나 꺾여야 위반. 15° 처져도 통과 |
| AIHub 정상 분포에서의 위치 | 상위 51 퍼센타일 = **'정상 중에서도 평범~좋은 편'** |

원인은 넷이 겹친다.

1. **위반의 69% 가 '솟음'이라 임계값이 솟음 쪽에 맞춰졌다.** 부호 있는 `hip_dev_ankle__mean` 으로 보면 정상 중앙값 **+0.105** vs 위반 중앙값 **+0.177** — 위반이 오히려 **더 큰 양수(엉덩이 솟음)** 다. 위반 중 정상보다 더 처진 것은 **20%** 뿐. 즉 이 규칙은 애초에 **처짐을 잡도록 학습되지 않았다.**
2. **연기 위반이 과장돼 있다.** 위반 분포 하위 25% 가 112° — 실사용자의 자연스러운 처짐과는 스케일이 다르다. 그 과장된 분포에 맞춰 임계값이 잡혔다.
3. **민감도가 원래 낮다.** 임계값 133.35° 는 AIHub **연기 위반조차 60.6% 만 검출**한다(특이도 91.3%). AUC 0.794 가 이 낮은 민감도를 가리고 있었다.
4. **평균이 순간을 묻는다.** 그 세트에는 임계값 아래로 내려간 프레임이 **11개**, 최소 50.0° 까지 간 프레임도 있었지만 평균 152.1° 로 전부 통과했다.

여기에 **자세 점수 자체의 구조적 결함**이 겹친다. 점수는 `OK 규칙 수 ÷ 전체 규칙 수` 인데 **플랭크는 규칙이 1개뿐이라 0% 아니면 100% 밖에 나올 수 없다.** 중간값이 존재하지 않는다.

> **감사 1차가 이걸 놓친 이유**: 검증 범위를 'AIHub 데이터 내부의 타당성'(라벨-피처 일치·방향성·충실도)으로 한정하고, 임계값의 실사용 감도는 "전 규칙 beta, 미보정"이라는 **일반 경고로 대체**했다. 방향 미구분은 지적했지만 "그래서 처짐이 실제로는 거의 안 걸린다"는 결론까지 가지 않았다. 규칙 감사에는 **실측 대조가 반드시 포함돼야 한다.**

### 즉시 손볼 것 (실사용에서 이미 오작동 확인)
1. **플랭크** — 처짐 전용 규칙을 부호 있는 `hip_dev_ankle` 로 분리하고, 임계값을 연기 위반이 아닌 **정상 분포 기준**(예: 정상 하위 10~25 퍼센타일)으로 잡는다. 방향별로 문구도 분리("엉덩이를 올리세요" / "내리세요").
2. **자세 점수** — 규칙 개수 비율이 아니라 **프레임 단위 위반 비율**로 바꾼다. 지금은 규칙 1개 종목에서 0%/100% 만 나온다.
3. **`mean` 편중** — 순간 처짐을 잡으려면 `min`(또는 하위 퍼센타일)을 병용해야 한다. 현재 14규칙 중 8개가 mean.

**전제**: 위 AUC 는 전부 AIHub **연기 위반** 기준이고, 임계값은 **바닥 높이 카메라가 아닌** 촬영에서 나왔다(전 규칙 beta). 실사용 신뢰도는 세트 로그 재보정 후에야 말할 수 있다.
