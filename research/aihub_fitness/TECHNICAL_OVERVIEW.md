# TREX 자세 교정 — 기술 설명서

휴대폰 카메라 한 대로 운동 자세를 판정하고 실시간으로 교정 안내를 하는 기능을, **'올바른 자세'의 정의부터 앱 동작·측정 결과·한계까지** 처음부터 끝까지 설명한다.

---

## 0. 이 문서에 대하여

### 0.1 대상 독자와 문서의 역할

이 분야를 처음 보는 사람이 읽고 **"무엇을, 왜 그렇게 만들었는지"**를 이해할 수 있게 쓰되, 숫자와 근거는 생략하지 않는다.

기술 문서는 목적에 따라 네 가지로 나뉜다([Diátaxis](https://diataxis.fr/) 분류). 이 저장소의 문서도 그렇게 나뉘어 있으니, 필요한 것을 골라 읽으면 된다.

| 유형 | 목적 | 이 프로젝트의 문서 |
|---|---|---|
| 튜토리얼 | 처음 배우기 | (없음 — 연구 코드라 불필요) |
| **How-to** | 작업 수행 | [`README.md`](README.md) — 파서·실험·재보정 실행 명령 |
| **레퍼런스** | 사실 조회 | [`KOTLIN_PORTING_SPEC.md`](KOTLIN_PORTING_SPEC.md) — 좌표 변환·피처 공식·규칙 스키마 / [`rules/rules_mp_v0.md`](rules/rules_mp_v0.md) — 규칙 표 |
| **설명 ← 이 문서** | 이해하기 | 왜 이 설계인가, 무엇이 검증됐고 무엇이 안 됐나 |

가장 흔한 문서 실패는 이 넷을 한 페이지에 섞는 것이다. 그래서 이 문서에는 **실행 명령을 넣지 않고**(→ README), **전체 규칙 표를 넣지 않는다**(→ 레퍼런스). 대신 판단의 근거와 그 근거가 된 수치를 담는다.

### 0.2 최소 용어 사전

읽기 전에 이 여덟 개만 알면 된다. 나머지는 [부록 A](#부록-a-용어집)에 있다.

| 용어 | 뜻 |
|---|---|
| **랜드마크(landmark)** | 영상에서 추정한 관절 위치 점. MediaPipe는 33개를 낸다 |
| **피처(feature)** | 관절 좌표에서 계산한 측정값. 예: 무릎 각도, 어깨 높이차 |
| **조건(condition)** | 종목마다 코치가 정한 자세 체크 항목. 예: "발과 무릎의 방향 일치" |
| **규칙(rule)** | "이 피처가 이 임계값을 넘으면 위반" 형태의 판정식 |
| **AUC** | 판별력 지표. 0.5 = 동전 던지기, 1.0 = 완벽. 0.85 이상이면 실용 가능으로 봤다 |
| **GroupKFold(수행자 홀드아웃)** | 같은 사람이 학습·평가에 동시에 들어가지 않도록 나누는 교차검증. 이걸 안 하면 성능이 부풀려진다 |
| **유보(ABSTAIN)** | "판정하지 않음". 관절이 안 보이거나 프레임이 모자랄 때 정상/위반 대신 내는 세 번째 답 |
| **valgus(무릎 모임)** | 스쿼트에서 무릎이 발끝보다 안쪽으로 무너지는 것. 대표적 부상 위험 신호 |

## 2. '올바른 자세'란 무엇인가

### 2.1 정의는 셋 중 하나를 골라야 한다

"올바른 자세"는 생각보다 정의하기 어렵다. 세 가지 접근이 가능하다.

1. **생체역학적 정의** — 관절 부하·모멘트암이 안전 범위인 상태. 가장 근본적이지만 **힘을 측정해야 한다.** 카메라는 힘을 못 본다.
2. **해부학적 규범** — "무릎 각도 90도", "척추 중립". 명확해 보이지만 **사람마다 뼈 길이와 가동범위가 달라** 같은 각도가 누구에겐 정상, 누구에겐 무리다.
3. **코치 합의 정의** — 숙련 코치가 종목별로 "이건 맞고 이건 틀리다"라고 판정한 항목의 집합.

이 프로젝트는 **3번을 채택**했다. 이유는 단순하다. 우리가 가진 정답지(AIHub 데이터)가 코치 감수로 만들어졌고, 앱이 사용자에게 하려는 말도 결국 코치의 말이기 때문이다.

그래서 이 시스템에서 **"올바른 자세" = 종목별로 정의된 조건 3~5개를 모두 충족한 상태**다. 예를 들어 바벨 스쿼트는 `척추의 중립`, `발과 무릎의 방향 일치`, `고개 정면`, `발바닥 지면 고정`, `무릎과 골반이 동시에 펴짐` 같은 항목이 각각 참/거짓으로 판정된다. **하나의 종합 점수가 아니라 항목별 판정**이라는 점이 중요하다 — 사용자에게 "70점입니다"보다 "무릎이 안쪽으로 모입니다"가 훨씬 쓸모 있다.

### 2.2 좋은 정의가 갖춰야 할 4요건

작업 중에 정의가 깨지는 지점을 여러 번 만났고, 거기서 요건을 역산했다. 새 종목을 추가할 때의 체크리스트이기도 하다. (근거 스크립트: `definition_quality.py`, 상세: [DEFINITION_QUALITY.md](DEFINITION_QUALITY.md))

| 요건 | 왜 필요한가 | 실측 근거 |
|---|---|---|
| **① 한 조건 = 한 메커니즘** | 한 항목에 여러 실패 방식을 묶으면, 규칙은 가장 흔한 방식만 배운다 | 여러 방향이 섞인 조건 6개를 방향별로 쪼개니 AUC 중앙값 **+0.132**(런지 0.765→0.978). 더 중요한 건 검출률 — 통합 규칙은 다수 방향은 90~98% 잡지만 **소수 방향은 중앙값 8%**만 잡았다(스티프 데드리프트 '신전' 3%). **AUC 0.86이 "흔한 방향만 잡는 상태"를 가린다** |
| **② 관측 가능** | 좌표로 표현 못 하는 것은 카메라로 판정 불가 | 완벽한 3D 정답 좌표로도 AUC 0.75 미만인 조건이 **62개 중 26개**. 대부분 "긴장 유지", "숄더패킹" 같은 **힘·의도** 항목 |
| **③ 라벨명 = 실제 편차** | 항목 이름과 실제로 연기된 오류가 다르면, 피드백 문구가 엉뚱해진다 | 행잉 레그레이즈의 '어깨-귀 거리' 위반은 실제로는 **좁은 그립**, OHP '전완 수직'은 **팔꿈치 내밀기**, 페이스풀 '외회전'은 **팔꿈치 모으기**였다 |
| **④ 방향 특정** | 양방향 오류를 부호 없는 절대값으로 재면 한쪽만 잡힌다 | 부호 없는 `torso_incl`은 체형 의존 초과분 +0.046, 부호 있는 `torso_pitch`는 −0.009. **AUC로는 이 실패를 못 잡는다** — 데이터가 한 방향만 담고 있으면 오히려 AUC가 높게 나온다 |

### 2.3 그래서 이 앱이 말하는 '올바른 자세'의 정확한 의미

정직하게 범위를 좁혀 말하면 이렇다.

> **숙련 코치가 종목별로 정의한 관찰 가능한 조건 중, 관절 좌표의 각도·비율로 표현되고, 수행자를 분리한 교차검증에서 판별력이 확인된 항목에 한해** — 카메라에 보이는 자세가 그 조건을 벗어났는지 판정한다.

여기 포함되지 **않는** 것: 근육 긴장·부하·통증, 척추 곡률의 절대 측정, 축(회전) 방향 오류, 심각도(얼마나 위험한가). [7.4](#74-무엇이-보이고-무엇이-안-보이나)에서 하나씩 다룬다.

## 3. 왜 휴대폰 카메라 한 대로 가능한가 — 네 가지 반론과 답

이 기능을 시작할 때 나온 반론 넷이 사실상 프로젝트의 설계도가 됐다.

### 3.1 "사람마다 체형이 다른데 같은 각도 기준을 쓸 수 있나"

**답: 각도와 비율로만 재면 상당 부분 통한다. 그리고 실제로 측정해서 확인했다.**

키가 180cm든 160cm든 무릎이 굽은 **각도**는 같은 의미를 갖는다. 길이가 필요한 값(손 간격, 발 간격)은 어깨너비·몸통 길이 같은 **본인 신체 치수로 나눠** 비율로 만든다. 이러면 절대 크기가 사라진다.

검증 방법이 중요하다. 수행자를 체형 지표(키·대퇴/경골 비·몸통/다리 비)로 4분위로 나눠, **다른 체형 집단에서 학습한 임계값으로 남은 집단을 판정**했다. 그냥 하면 안 된다 — 집단을 무작위로 나눠도 표본 오차 때문에 성능은 떨어지기 때문이다. 그래서 **무작위 4분할을 20회 반복한 귀무 대조군**을 만들고, 그 이상으로 떨어진 몫만 체형 효과로 봤다.

| 측정 | 값 |
|---|---|
| 체형 분위 이식 시 성능 저하 | 0.083 |
| 무작위 분위 이식 시 저하 (귀무) | 0.079 |
| **체형 때문에 추가로 잃은 몫** | **+0.004** |
| 체형 효과가 사실상 없는 규칙 | **62개 중 48개 (77%)** |

**결론: 임계값은 체형을 넘어 이식된다.** 그런데 사람마다 값이 다른 건 분명한 사실이다(정상 자세 값 분산의 45%가 사람 차이). 그 차이는 체형이 아니라 **습관·수행 스타일**이었다. 이 발견이 나중에 개인화 설계를 바꿨다([9장](#9-개인화--무엇이-되고-무엇이-안-되는가)).

체형 차이를 아예 지워버리는 알고리즘(정준 골격 리타게팅 — 뼈 길이를 인구 중앙값으로 바꿔 재조립)도 구현해 검증했는데, **전체 이득은 0**이었다(+0.002). 피처가 이미 각도·비율이라 지울 체형 효과가 남아있지 않았던 것이다. 다만 팔 길이에 의존하던 규칙 몇 개는 실제로 고쳐졌다(행잉 레그레이즈 `grip_w` 체형 초과분 +0.062 → **+0.001**). 넓은 체형 인구 데이터가 생기면 켤 옵션으로 보관했다. (`canonical_retarget.py`)

### 3.2 "카메라 한 대로는 깊이(z)를 모르지 않나"

**답: 절반만 맞다. MediaPipe는 학습된 3D를 내놓고, 그게 얼마나 쓸 만한지 직접 쟀다.**

MediaPipe Pose Landmarker는 2D 픽셀 좌표뿐 아니라 **world 좌표(미터 단위 3D, 골반 중점 원점)**를 낸다. 카메라가 실제로 깊이를 측정한 게 아니라 모델이 추정한 값이므로, "얼마나 믿을 수 있나"는 실험으로만 답할 수 있다.

그래서 AIHub 데이터의 이미지를 MediaPipe에 그대로 넣고, 같은 프레임의 정답 3D와 비교했다(실험 A, 이미지 166,923장). 결과:

- 검출률 96.4%, 2D 위치 오차는 몸통 길이 대비 어깨 0.035~0.041, 골반 0.055~0.060 (몸통길이=1 기준, 0.1이 대략 5~6cm)
- **정답 3D 대신 MediaPipe를 쓸 때 판별력 비용: AUC −0.025** (같은 표본·같은 피처로 통제 비교)
- 단, **깊이가 핵심인 조건은 무너진다.** 축회전(어깨 내회전 등) 0.647, 발 접지 0.761

**설계 결론: 깊이에 의존하는 조건은 규칙에서 제외하고, 뷰(촬영 방향)에 따라 유보한다.** 무릎 모임(valgus)은 정면에서 AUC 0.993이지만 사선에서 0.79~0.82로 떨어지므로, 사선 촬영이면 **틀린 판정보다 유보가 낫다**.

### 3.3 "실제로 찍으면 각도·왜곡 때문에 다 틀어질 텐데"

**답: 휴대폰에는 중력 센서가 있다. 그걸 '위쪽'의 정의로 쓰면 폰이 기울어도 값이 유지된다.**

모든 "높이" 피처(어깨가 얼마나 올라갔나 등)를 **화면의 세로축** 기준으로 재면, 폰을 조금만 기울여도 전부 틀어진다. 대신 IMU(`TYPE_GRAVITY`)에서 중력 방향을 읽어 그 반대를 `up`으로 삼고, 골반에서 시작하는 **신체좌표계**를 매 프레임 세운다.

```
y_b = up (중력 반대)
x_b = 골반 좌우축에서 up 성분을 뺀 방향  (사람의 왼쪽 +)
z_b = x_b × y_b                          (사람의 정면 +)
```

이러면 **장면 전체를 회전시켜도 피처 값이 변하지 않는다.** 이건 주장이 아니라 테스트로 고정했다 — 관절과 up을 같은 회전(롤 30°/피치 20°/복합 47°)으로 돌렸을 때 모든 피처가 불변임을 유닛 테스트가 검사한다.

> **실제로 겪은 버그**: Android 중력 센서는 정지 상태에서 **위쪽 반작용 벡터**를 보고한다(화면을 위로 놓으면 z=+9.81). 이걸 아래 방향으로 가정해 `up`이 180° 뒤집혔고, 높이 피처 부호가 전부 반대가 됐다(귀-어깨 간격 −0.34 vs 정답 +0.36). 실기기 로그로 발견해 수정하고, **자가검증 안전장치**를 넣었다 — 서 있는 자세에서 골반이 발목보다 아래로 계산되면 뒤집힘으로 보고 `up`을 반전하고, 판단이 불가능한 자세(누움 등)에서는 보정하지 않고 `upVerified=false`로만 표시한다.

### 3.4 "애초에 정답 데이터가 있나"

**답: 있다. AIHub 013 피트니스자세 데이터셋.** 다음 장 전체가 이 이야기다.

## 4. 데이터 — 정답지의 구조와 함정

### 4.1 무엇이 들어 있나

AIHub `013.피트니스자세` 학습 데이터를 파싱했다(`parse_labels.py`).

| 항목 | 값 |
|---|---|
| 클립 | 34,468개 (3D 좌표 보유 33,349개) |
| 종목 | 41개 (바벨 스쿼트, 데드리프트, OHP, 런지류, 푸시업, 크런치 …) |
| 조건 조합 | 816개 타입 — 종목별 조건 3~5개의 **완전요인설계**(2^k 전 조합) |
| 클립 구조 | 16프레임 × **5개 뷰 동시 촬영** |
| 관절 | 24개, 2D 픽셀 + **3D(cm)** |
| 수행자 | 약 112명 (익명 Z코드) |
| 부가 정보 | 조건별 참/거짓 라벨 + `description`(실제로 어떤 편차를 연기했는지 서술) |

뷰 5개의 기하는 데이터에 안 적혀 있어 직접 판별했다(정답 2D의 어깨 투영비 이용): **C=정면, B/D=전방 사선 ±40°, A/E=후방 사선 ±40°**. 순수 측면(옆모습) 뷰는 **없다** — 그래서 측면 촬영은 이 데이터로 검증 불가이며, 앱도 정면~전방 45°를 안내한다.

### 4.2 라벨의 성격 — "연기된 오류"

이 데이터의 위반 클립은 **피험자가 의도적으로 잘못된 자세를 연기한 것**이다. 자연스럽게 무너진 자세가 아니다. 이 사실은 프로젝트 내내 따라다니는 제약이며, 정직하게 다뤄야 한다.

- **장점**: 라벨이 깨끗하고, 완전요인설계라 조건별로 균형 잡힌 표본이 나온다.
- **한계**: 무·경부하로 연기했으므로 **실제 중량에서 피로로 무너지는 오류와 분포가 다를 수 있다.** [8.5](#85-실시간-음성-코칭)에서 이 한계를 정면으로 다룬다.

### 4.3 품질검사 — 정답지도 틀린다

정답 3D를 그대로 믿고 시작했다면 결과가 오염됐을 것이다. 실제로 값이 폭주하는 프레임들이 있었다(정규화 분모가 무너져 피처가 1e5~1e8이 되는 경우).

검사 두 가지를 만들었다(`qc_kp3d.py`):
1. **뼈 길이 검사** — 몸통·어깨폭·골반폭·허벅지·정강이·상완·전완 길이가 해부학적 범위를 벗어나거나 클립 중앙값 대비 ±30% 이탈하는 프레임
2. **좌우 일관성 검사** — 골반 좌우축 기준으로 어깨·귀 쌍이 반대편에 있는 프레임(좌우 스왑 → 전방축 반전)

| 결과 | 값 |
|---|---|
| 전체 불량 프레임 | **18%** |
| 서 있는 종목 | 1~6% (양호) |
| **바닥/누운 종목** (크런치·푸시업·플랭크·레그레이즈·힙쓰러스트 등) | **73~92% 불량** — 리그가 선 자세용이라 3D를 신뢰 불가 |
| 벤트오버 계열 (굿모닝 27%, 바벨 로우 19%) | 중간 |
| 특정 촬영일(Day28) | 전량 불량 — 리그 캘리브레이션 실패일 |

**바닥 종목 8개는 3D 기반 분석에서 제외**했다. QC 후 남은 28,673클립으로 이후 실험을 진행한다.

> **못 쓴 검사도 기록해 둔다.** 처음엔 "프레임 간 점프(시간 평활도) 검사"를 넣으려 했는데, 이 데이터에는 쓸 수 없다. 클립의 16프레임은 연속 프레임이 아니라 **여러 렙에 걸친 성긴 샘플**이라(스쿼트 골반 높이 95→38→96→37cm) 정상 동작도 프레임 간 수십 cm 튄다. 대신 좌우 일관성 검사로 대체했다.

### 4.4 라벨명이 실제 편차와 다르다 — 척추 하위유형의 발견

"척추의 중립" 조건은 15개 종목에 나오는데, **종목마다 다른 오류를 연기했다.** `description` 필드를 읽고서야 알았다.

| 연기된 편차 | 종목 |
|---|---|
| 등이 말림(flexion) | 스쿼트·데드리프트·로우·컬·OHP |
| 옆으로 갸우뚱(lateral, 측굴) | 굿모닝·런지류 |
| 좌/우 기울기 | 스티프 데드리프트 |
| 허리 반동(lumbar swing) | 라잉 트라이셉스 |
| 상체 앞숙임(forward lean) | 런지류 일부 |

이걸 모르고 한 덩어리로 학습시키면 [2.2 요건 ①](#22-좋은-정의가-갖춰야-할-4요건)의 실패가 그대로 일어난다. `description`을 정규식으로 파싱해 하위유형을 파생시켰고(98% 특정, `spine_subtypes.py`), 규칙도 하위유형별로 따로 만든다.

> **내가 틀렸던 지점**: 굿모닝의 '어깨 비대칭' 신호를 처음엔 데이터 아티팩트로 판단했다. `description`을 읽어보니 실제로 "옆으로 갸우뚱"을 연기한 것이었고, 그 정정이 하위유형 발견으로 이어졌다.

## 5. 자세를 숫자로 바꾸기 — 피처 설계

### 5.1 프레임 하나에서 481개의 값

각 프레임마다 신체좌표계([3.3](#33-실제로-찍으면-각도왜곡-때문에-다-틀어질-텐데))를 세우고 다음을 계산한다(`features.py`).

| 종류 | 예시 |
|---|---|
| **3점 관절각** | 무릎 ∠(엉덩이,무릎,발목), 팔꿈치 ∠(어깨,팔꿈치,손목), 고관절, 어깨 |
| **몸통 방향** | `torso_incl`(수직 대비 기울기, 부호 없음), `torso_pitch`(앞/뒤 부호 있음) |
| **머리·시선** | `head_pitch`(고개 고도각), `face_vs_torso`(얼굴과 몸통이 이루는 각) |
| **정규화 거리** | `grip_w`=손 간격/어깨너비, `stance_w`=발 간격/골반너비, `palm_head_dist`=손-머리 거리/몸통길이 |
| **좌우 비대칭** | `shoulder_asym`=(왼어깨−오른어깨 높이)/어깨너비, `hand_h_asym` |
| **valgus** | `knee_out` — 아래 설명 |

`knee_out`은 이 프로젝트에서 가장 많이 쓰이는 피처라 계산법을 밝혀 둔다.

```
엉덩이와 발목을 잇는 직선 위에서, 무릎과 같은 높이인 지점의 좌우 좌표를 구한다.
knee_out = (실제 무릎 좌우 좌표 − 그 기준점) / 다리 길이     ← 오른쪽은 부호 반전
  음수 = 무릎이 안쪽으로 모임(valgus)   양수 = 바깥으로 벌어짐
```

다리 길이로 나누기 때문에 체형 무관이고, 부호가 있어서 **양방향을 구분**한다([2.2 요건 ④](#22-좋은-정의가-갖춰야-할-4요건)). 이 설계가 나중에 [8.6 양방향 검출](#86-양방향-검출--반대-방향-오류도-잡기)을 가능하게 했다.

### 5.2 세트 단위로 모으기 — 다섯 통계

프레임 값 하나로는 판정하지 않는다. 세트 전체(또는 최소 3~4렙)에서 모은 뒤 다섯 통계를 낸다.

| 통계 | 무엇을 잡나 |
|---|---|
| `mean` | 평균적인 자세 수준 — "전반적으로 상체가 숙여져 있다" |
| `min` / `max` | 최악의 순간 — "가장 깊은 지점에서 무릎이 모였다" |
| `std` / `range` | **흔들림·반동** — "무릎 반동을 쓴다", "발바닥이 뜬다" |

출시 규칙 59개의 통계 분포: mean 26 · min 14 · std 10 · range 5 · max 4. **반동 계열 조건은 std/range가 아니면 못 잡는다**는 게 실험에서 확인됐다.

> **창(window) 정의가 임계값의 전제다.** AIHub 클립은 ~4렙에 걸친 16프레임 성긴 샘플이다. 앱도 **2~4 fps로 세트 전체를 샘플링**해야 std/range가 같은 스케일이 된다. 30fps 전 프레임을 쓰면 min/max가 극단값에 더 민감해져 임계값이 어긋난다.

### 5.3 관절이 안 보이면 — 유보

MediaPipe가 주는 `visibility`/`presence`가 0.5 미만인 관절은 그 프레임에서 NaN 처리하고, 집계에서 제외한다. **유효 프레임이 8개 미만이면 그 세트는 판정 유보**다. 틀린 판정보다 "모르겠다"가 낫다는 원칙이 시스템 전체에 일관되게 적용돼 있다.

## 6. 판정 규칙을 만드는 법

### 6.1 왜 딥러닝으로 바로 분류하지 않았나

조건 라벨이 있으니 신경망으로 바로 학습시킬 수도 있다. 그러지 않은 이유는 셋이다.

1. **설명 가능해야 한다.** 사용자에게 "무릎이 안쪽으로 모입니다"라고 말하려면 어떤 양이 얼마나 벗어났는지 알아야 한다.
2. **재보정이 가능해야 한다.** 자체 데이터로 다시 맞출 때, 임계값 하나만 옮기면 되는 구조와 모델 전체를 재학습해야 하는 구조는 비용이 다르다.
3. **성능 차이가 생각보다 작다.** 아래에서 실제로 쟀다.

### 6.2 물리 화이트리스트 — 아무 피처나 못 쓰게 막기

481개 피처 중 가장 AUC가 높은 걸 고르면, "런지 조건을 손목 각도로 판정"하는 규칙이 나올 수 있다. 데이터에서는 잘 맞지만 **물리적으로 무의미하고, 새 데이터에서 무너진다.**

그래서 조건 이름의 키워드에서 **허용 피처 패밀리를 미리 정해** 그 안에서만 고른다(`rule_engine_v0.py`의 `COND_RULES`/`FAMILIES`). 예: "발과 무릎의 방향" → `knee_out`, `knee_lat`, `stance_w` 계열만. 척추 조건은 하위유형별로 다른 패밀리를 쓴다.

### 6.3 단일 피처 + Youden 임계값 + 수행자 GroupKFold

규칙 하나는 **피처 하나와 임계값 하나**다. 임계값은 Youden J 통계(민감도+특이도−1의 최댓값)로 정한다. 검증은 반드시 **수행자 GroupKFold** — 같은 사람이 학습·평가에 동시에 들어가면 성능이 부풀려진다(같은 표본을 섞으면 AUC 0.894, 사람 단위로 분리하면 0.858).

### 6.4 복잡한 모델은 얼마나 나은가 — 실제로 쟀다

| 모델 | AUC 중앙값 (정답 3D, 162개 조건) |
|---|---|
| **단일 피처 규칙** | **0.861** |
| 로지스틱 회귀(선형 결합) | 0.891 |
| GBM(비선형 상한) | 0.923 |

GBM이 0.06 높다. 그런데 규칙을 **2피처(깊이-2 트리)로 늘려봤더니 오히려 나빠졌다**(0.860 → 0.842, 개선 3개 vs 악화 24개). GBM의 우위는 두 피처의 상호작용이 아니라 **여러 피처의 완만한 조합**에서 나오는 것이고, 그건 설명 가능성과 재보정 용이성을 포기해야 얻는 0.06이다.

**결정: 단일 피처 규칙 유지.** 대신 상한(0.923)을 알고 있으니, 특정 조건이 0.7에 머물면 "규칙 방식의 한계"인지 "이 조건 자체가 관측 불가"인지 구분할 수 있다.

## 7. 실험 — 어디까지 되는지 재기

### 7.1 실험 B — 완벽한 3D라면 어디까지 되나 (상한선)

먼저 **정답 3D 좌표**로 상한을 쟀다. 포즈 추정이 완벽해져도 넘을 수 없는 선이다.

- 조건 162개 평가, 단일 규칙 AUC 중앙값 **0.861**
- AUC ≥0.90: 37개 / 0.80~0.90: 54개 / **0.70 미만: 22개**

마지막 22개가 중요하다. **정답 좌표로도 안 되는 조건**은 포즈 추정을 개선해도 안 된다. 대부분 "긴장 유지", "숄더패킹" 같은 힘·의도 항목이었다. 이걸 먼저 알았기 때문에, 이후 작업에서 헛수고를 줄일 수 있었다.

조건별로 보면 편차가 크다: `앞다리 무릎 각도 90도` 0.968, `무릎 반동 없음` 0.915, `척추의 중립` 0.830, `손목의 중립` 0.826.

### 7.2 실험 A — MediaPipe로 갈아타면 얼마나 잃나

앱은 정답 3D가 아니라 MediaPipe 추정을 쓴다. 그 비용을 **통제 실험**으로 분리했다.

같은 60클립 표본 · 같은 MediaPipe-계산가능 피처만 쓴 정답 3D 결과를 **통제군**으로 두고 비교했다. 이렇게 해야 "표본이 작아서 떨어진 몫"과 "랜드마크 노이즈 때문에 떨어진 몫"이 섞이지 않는다.

| 조건 | AUC 중앙값 |
|---|---|
| 정답 3D, 전체 표본 | 0.861 |
| 정답 3D, 통제군(같은 표본·같은 피처) | 0.843 |
| **MediaPipe 재적합, 규칙별 최적 뷰** | **0.818** |
| → **랜드마크 노이즈의 순수 비용** | **−0.025** |

뷰 고정 시(정면만, 사선만) 성능은 더 떨어지며, **후방 사선은 −0.135**로 뚜렷하게 나쁘다. 그래서 앱은 정면~전방 45° 촬영을 안내한다.

> **가장 중요한 발견 — 임계값은 전이되지 않는다.** 정답 3D에서 구한 임계값을 MediaPipe 값에 그대로 쓰면 균형정확도가 0.55~0.59로 무너진다(동전 던지기 수준). **피처와 방향은 유지되지만 임계값은 반드시 다시 맞춰야 한다.** 이 사실이 재보정 툴체인([11.2](#112-출시-전-필수-절차-재보정))을 만든 이유다.

### 7.3 규칙셋 확정 — rules_mp_v0.1

MediaPipe 값 위에서 재적합한 규칙에 등급을 매겼다(`export_rules_mp.py` → `rules/rules_mp_v0.json`).

| 등급 | 기준 | 개수 |
|---|---|---|
| **ship** | 최적 뷰 MediaPipe 재적합 AUC ≥ 0.85 | **59** |
| beta | 0.75~0.85 — 플래그 뒤에서 수집만 | 12 |
| exclude | 그 미만 또는 계산 불가 — 사유 기록 | 70 |

ship 규칙의 AUC 중앙값은 0.938, 규칙당 표본 중앙값 60클립·30명이다.

**미러 안전(mirror-safe)**: MediaPipe의 좌/우는 해부학적 기준이라 값 자체는 카메라 위치와 무관하지만, 카메라 반대편 관절은 가려져 정밀도가 떨어진다. `*_L`/`*_R`을 직접 쓰는 규칙은 촬영 방향에 취약하므로, **좌우 대칭 변형(mean/min/max)으로 재적합**해 대체했다. 그 결과 미러 안전 ship 규칙이 38 → **53개**로 늘었고, 교체된 규칙은 `alt_rule`로 보존했다.

### 7.4 무엇이 보이고 무엇이 안 보이나

조건 132개를 해부학적 자유도로 분류해, 정답 3D 상한과 MediaPipe 전이 후를 비교했다(`observability_inventory.py`, [OBSERVABILITY.md](OBSERVABILITY.md)).

| 자유도 | 조건 수 | 정답 3D | MediaPipe | 판정 |
|---|---|---|---|---|
| 굴곡·신전(관절각) | 39 | 0.873 | 0.877 | ✅ 잘 된다 |
| 외전·내전(무릎 내/외, 손 위치) | 24 | 0.873 | 0.901 | ✅ |
| 머리·시선 | 6 | 0.882 | 0.880 | ✅ |
| 몸통 정렬 | 5 | 0.900 | 0.820 | ✅ |
| 척추 중립(조건 판정) | 20 | 0.865 | 0.938 | ✅ **프록시로** |
| 발·접지 | 2 | 0.924 | 0.761 | △ 깊이 의존 |
| 견갑·골반 | 9 | 0.821 | 0.731 | ⚠ MediaPipe에서 붕괴 |
| **축회전** | 10 | 0.826 | 0.647 | ⚠ ship 0개 |
| **긴장·부하** | 13 | 0.670 | 0.756 | ❌ 원리적 불가 |

**척추는 두 가지를 구분해야 한다.** MediaPipe 33점에는 척추 중간 랜드마크가 없어 **곡률을 각도로 측정하는 것은 불가능**하다(정답 3D 기반 `spine_*` 피처를 쓴 규칙 6개는 전부 제외). 그런데 **척추 중립 여부의 판정은 잘 된다** — 측굴은 어깨 높이차로, 굴곡은 고개 각도·상체 전방 이동으로, 앞숙임은 몸통 기울기로, **동반 증상 프록시**를 통해 잡기 때문이다. 실제로 프록시(AUC 0.73~0.90)가 정답 곡률 지표(0.64~0.76)보다 판별력이 높았고, 둘의 상관은 |r|<0.35로 약하다 — **서로 다른 것을 재고 있다.** 잔여 위험은 "곡률은 큰데 프록시는 정상"인 3~14%다.

**설계 함의**: 카메라로 판정 가능한 건 결국 넷이다 — **관절이 얼마나 굽었나 · 사지가 어디에 있나 · 몸통이 어디를 향하나 · 얼마나 흔들리나.** "힘주세요", "견갑 고정" 같은 지시는 검증 불가이므로 조건에서 빼거나, 그 결과로 나타나는 위치 변화로 재정의해야 한다.

## 8. 앱은 어떻게 동작하나

### 8.1 파이프라인

```
CameraX (ImageAnalysis, 최신 프레임만)
  → MediaPipe Pose Landmarker (VIDEO 모드, full 모델)
  → world 좌표 33점 → cm 변환·축 보정 → 24관절 매핑
  → IMU 중력축으로 신체좌표계 구성
  → 프레임 피처 계산 (규칙이 필요로 하는 것만)
  → 세트 창 집계 (mean/min/max/std/range)
  → 규칙 평가 → 정상 / 위반 / 유보
  → ① 실시간 음성 코칭   ② 세트 종료 리포트   ③ 세트 로그 저장(재보정용)
```

구현은 `app/src/main/java/com/example/trex_kotlin/posture/` 11개 파일, 3,601줄이다. 역할 분담은 [부록 B](#부록-b-파일-지도)에 있다.

### 8.2 연구 코드와 앱 코드가 같은 값을 내는가 — 파리티 테스트

Python으로 검증한 규칙을 Kotlin으로 옮길 때 가장 큰 위험은 **미묘한 계산 차이**다. 그래서 연구 코드로 계산한 **40프레임 × 129피처**를 픽스처로 내보내고, 같은 입력에 대해 Kotlin 결과가 일치하는지(각도 0.05° / 상대오차 1e-3 이내) 유닛 테스트로 검사한다.

유닛 테스트 30개: 파리티 6 · 회전 불변성/중력 매핑 6 · 실시간 코칭 8 · 기준선 4 · 세트 로그 3 · 추론 스케줄러 3.

### 8.3 발열 — 실측하고 고쳤다

실험실 화면을 2분 쓰면 기기가 뜨거워졌다. 측정하니 **앱 CPU 140~173%**, AP 온도 39.8→41.8°C였다.

원인은 넷이었다: ① 분석기가 즉시 재진입해 **추론이 쉬지 않고 돌았다**(판정에 필요한 건 300ms당 1회인데 듀티 ≈100%) ② CPU 델리게이트 ③ 모든 프레임을 RGBA로 변환 + 프레임마다 비트맵 2장 할당 ④ 분석 스트림 해상도 과다(720×960, 모델 입력은 256px).

수정: **추론 스케줄러**(`InferencePolicy`)가 상태별로 간격을 정하고(기록 중 1:1, 대기 400ms, 리포트 1500ms), OS 열 상태에 따라 ×1.5/×2/×3으로 감속하되 **심한 발열에서도 10초 세트에 16프레임 이상은 확보**한다. 여기에 GPU 델리게이트 우선, YUV 입력 + 추론 프레임만 변환, 해상도 축소를 더했다.

### 8.4 판정 — 정상 / 위반 / 유보

```
값 = 집계(통계, 피처)
위반 = (연산자가 '<' 이면 값 < 임계값, 아니면 값 > 임계값)
값이 없거나 유효 프레임 < 8 → 유보
```

출시 등급 규칙만 활성화되고, 베타는 플래그 뒤에서 수집만, 제외는 UI에 노출하지 않는다. 척추는 하위유형 규칙이 있으면 그것이 정본이다.

### 8.5 실시간 음성 코칭

**질문**: 사용자가 처음부터 잘못했는지, 하다가 무너졌는지 어떻게 구분하나?

**원리**: 세트의 **초반 8프레임**과 **최근 8프레임**을 같은 규칙으로 따로 평가한다.

| 초반 | 최근 | 분류 | 안내 |
|---|---|---|---|
| 위반 | 위반 | **HABIT** | "처음부터 무릎이 안쪽으로 모여 있어요" |
| 정상 | 위반 | **DRIFT** | "무릎이 점점 안쪽으로 모여요" |
| 위반 | 정상 | **RECOVERED** | "좋아요, 무릎 자세가 교정됐어요" |

8프레임 창으로도 판별력이 유지되는지 먼저 확인했다: **8프레임 AUC 0.912 ≈ 전체 16프레임 0.903**(첫 5프레임은 0.889). 300ms 샘플링에서 8프레임은 약 2.4초, 대략 1렙이다.

**발화 억제**가 없으면 음성이 쉴 새 없이 나온다. 규칙별 연속 2회 위반일 때만, 같은 규칙은 12초 쿨다운, 전체 최소 간격 4초, **한 번에 한 문장**(가장 오래 지속된 위반, 동률이면 AUC가 높은 규칙)으로 제한했다.

문구는 43개 활성 조건을 커버하며, **조건 이름이 아니라 실제로 연기된 편차 기준**으로 썼다([2.2 요건 ③](#22-좋은-정의가-갖춰야-할-4요건)) — OHP의 '전완 지면과 수직' 위반은 "팔꿈치가 앞으로 벌어져 있어요"라고 말한다.

> **오류가 생기는 방식 3유형을 먼저 분석했다**(`error_onset_analysis.py`, [ERROR_ONSET.md](ERROR_ONSET.md)). AIHub의 연기 위반은 **처음부터 끝까지 일정한 오프셋**(습관형)뿐이었다 — 초반/중반/후반 차이 비율 0.78/1.00/0.35, 동작 중 변동계수 0.19. 피로형·순간형은 데이터에 없으므로, **같은 총 오류량을 시간축에만 다르게 배치한 합성 신호**로 평가했다. 결과: 피로형은 `drift`(후반⅓−전반⅓) 0.889·`late_mean` 0.927로 잡히고, 순간형은 `spike_dir` 0.926·`ext_dir` 0.995로 잡힌다. 반면 **습관형 신호로는 피로형 판별이 0.481**로 무너진다 — 유형이 다르면 봐야 할 통계가 다르다는 뜻이고, 이것이 초반/최근 창 비교 설계의 근거다.
>
> **정직한 한계**: 현재 임계값은 습관형(AIHub)으로 맞춰진 값이라 DRIFT도 같은 임계값을 쓴다. 피로형 전용 임계값은 실사용 로그를 모은 뒤의 일이다. 순간 붕괴(삐끗)는 2~4fps 샘플링에서 놓칠 수 있어 이번 범위에서 제외했다.

### 8.6 양방향 검출 — 반대 방향 오류도 잡기

**문제**: AIHub는 종목마다 **한 방향만** 연기했다. 스쿼트에는 "무릎이 바깥으로 벌어진" 클립이 0개다. 그래서 기존 규칙은 단방향이었다 — 무릎이 과하게 벌어져도 "정상"으로 판정한다.

**근거 세 단계로 해결했다**(`bidirectional_analysis.py`, [BIDIRECTIONAL.md](BIDIRECTIONAL.md)):

1. **부호가 방향을 가르는가** — 양방향 라벨이 존재하는 다른 종목들에서 확인. `knee_out` 평균이 안쪽 위반 −0.030 < 정자세 < 바깥 위반 +0.044로 단조 분리됐다. 고개 좌/우는 `head_yaw`로 90%, 상/하는 78%, 몸 기울기는 69~76% 판별.
2. **"정상 분포의 반대쪽 경계" 방식이 통하는가** — 정상 클립 분포에서 중앙값 ± 2.5·MAD 밖을 반대측 위반으로 보는 방식을 수행자 홀드아웃으로 검증. 좌우 손 높이 96/93%, 고개 좌/우 97/98% 검출(오탐 6.5~8%). 반면 **발끝 각도는 5/25%로 실패** — 정상인의 발 벌림 편차가 너무 커서 이 방식으로는 못 잡는다.
3. **주입** — 검증된 피처를 쓰는 활성 규칙 7개에 반대측 가드를 넣었다. 음성 안내는 오탐 비용이 크므로 앱용 경계는 검증(2.5)보다 보수적인 **3.0·MAD**로 설정했다.

이제 스쿼트에서 무릎이 과하게 벌어지면 `위반(반대측)`으로 판정되고 "무릎이 발끝보다 바깥으로 벌어져 있어요"라고 안내한다. 그 방향의 라벨이 아예 없는 2건(런지 상체 앞숙임, 딥스 고개 숙임)은 `validated=false`로 표시해 **오탐률만 통제되고 검출률은 미보증**임을 명시했다.

## 9. 개인화 — 무엇이 되고 무엇이 안 되는가

"사용자마다 임계값을 맞춘다"는 아이디어는 직관적으로 옳아 보인다. 네 가지 실험으로 결판냈다(`personalization_experiments.py`).

| 실험 | 결과 | 결정 |
|---|---|---|
| **① 개인별 임계값 재적합** | 인구 임계값 균형정확도 0.778 = **정직한 개인 분할 0.778 (Δ +0.002)**. 인샘플로 재면 0.886으로 보이지만 그건 과적합 | **기각.** 개인차는 실재하지만 사용자 1명이 낼 수 있는 라벨 규모(클래스당 5~10세트)로는 노이즈를 못 이긴다 |
| **② 임계값 분산 분해** | ICC 중앙값 **0.66** — 개인 간 임계값 편차(0.53σ)가 측정 노이즈(0.28σ)보다 크다. 개인차가 큰 건 **수준(level) 피처** | 개인차는 실재 → 라벨 없이 잡을 방법을 찾자 |
| **③ 체형 조건화** | 피처~체형 회귀 R² 중앙값 **0.08**. 균형정확도 raw 0.780 vs 체형 조건화 0.769 | **기각.** (내가 앞서 제안했던 방식을 스스로 철회했다) |
| **④ 기준선 오염 내성** | 기준선 세트에 잘못된 자세가 1개 섞여도 중앙값이 흡수(+0.001), 2개면 −0.014 | 중앙값 기반 + 수집 UX로 방어 |

**최종 설계**: 기본은 인구 임계값. **정자세 세트의 값을 빼는 개인 기준선은 검증된 12개 규칙(7종목)에만** 적용한다. 대상은 수준 피처(mean/min/max)뿐이고, **변동성 피처(std/range)에는 금지**한다 — 거기서는 오히려 성능이 나빠졌다(−0.03~−0.06).

기준선 세트 수도 곡선으로 정했다: 없음 0.761 → 1세트 0.792 → **3세트 0.809**에서 포화. 그래서 `k=3`이다.

### 9.1 이 개인화가 앱에서 얼마나 들을까 — 격차 분석

AIHub에서 잰 이득이 앱에서 그대로 나올 리 없다. 어디서 격차가 생기는지 분해했다(`personalization_gap.py`).

| 계층 | 측정 | 앱에서의 함의 |
|---|---|---|
| **① 세션(같은 사람, 다른 날)** | 같은 날 기준선 이득 **+0.009** → **다른 날 −0.009** | 앱은 **항상 다른 날**이다. AIHub 이득의 상당분이 "같은 날 같은 세팅" 효과일 수 있다 |
| **② 측정(정답 3D → MediaPipe)** | MediaPipe 오차 / 임계값 크기 비율 **1.12** | **잡음이 판정 경계와 맞먹는다.** MediaPipe 스케일 재보정 전에는 이득을 기대하면 안 된다 |
| **③ 모집단·프로토콜** | 연기 오류·좁은 체형 범위·통제 조명·고정 리그 | 실사용은 실중량·자연 오류·단일 뷰·일반 인구 |

**그래서 앱은 절대 판정과 상대 판정을 둘 다 로그에 남긴다.** 기준선 기능이 실제로 도움이 되는지 실사용 데이터로 A/B 판정하기 위해서다. 기준선 세트는 그 자체가 "다른 날 실험"이 된다.

## 11. 한계와 다음 단계

### 11.1 알려진 한계 (정직하게)

1. **임계값이 스튜디오 기준이다.** AIHub는 통제 조명·타이트 복장·고정 리그·무부하 연기 환경이다. 실사용 분포와 다르며, 이것이 현재 실험실 화면에만 노출하는 이유다.
2. **연기된 오류 ≠ 자연 오류.** 특히 피로로 무너지는 패턴은 데이터에 없어 합성으로만 평가했다.
3. **판정에 심각도가 없다.** 이진 판정이라 "약간 모임"과 "심하게 무너짐"을 구분하지 못한다.
4. **'올바름'은 코치 합의물이다.** 라벨러 간 일치도(κ)는 측정되지 않았다.
5. **측면 촬영 미검증.** 데이터에 순수 측면 뷰가 없다.
6. **바닥/누운 종목 제외.** 3D 정답 자체가 신뢰 불가였다(73~92% 불량).
7. **힘·긴장·부하는 원리적으로 관측 불가.** 카메라로는 못 본다.
8. **음성 코칭은 오탐이 사용자를 잘못 교정시킨다.** 재보정 전까지 개발용에 한정한다.

### 11.2 출시 전 필수 절차 — 재보정

임계값을 자체 데이터로 다시 맞추는 절차를 **설계하고 도구까지 구현**해 두었다.

**얼마나 찍어야 하는가**(`calibration_protocol.py`, 표본 크기 곡선 기반):

| 목적 | 필요량 | 근거 |
|---|---|---|
| 임계값 재보정 | 종목당 **30세트**(최소 12, 권장 40) × **3~6명 이상** | 상한 대비 회복률 12세트 95.5% → 30세트 97.9% → 40세트 98.2%. 세트를 늘리는 주 효과는 평균보다 **재보정 안정성**(반복 SD 0.060→0.039) |
| 개인 기준선 | 대상 7종목, 사용자당 **정자세 3세트** | k 곡선 포화점 |

설계 요령 둘: 세트마다 조건별로 **정상/위반을 무작위 절반씩 배정**한다(한 세트가 그 종목의 모든 조건에 라벨을 준다 — 한 번에 한 조건만 틀리게 하면 세트 수가 조건 수만큼 곱해진다). 그리고 **인원 > 세트** — 개인 임계값의 정직한 이득이 +0.002이므로, 같은 총량이면 1명×90세트보다 **6명×15세트**가 낫다.

**도구는 이미 있다**: 앱이 세트마다 프레임 피처 원본을 JSON Lines로 기록하고(`PostureSetLog`), 공유 시트로 내보내면, 연구 쪽 `calibrate_from_logs.py`가 코치 라벨과 합쳐 **피처·방향은 고정하고 임계값만 Youden으로 재적합**한다. AIHub MediaPipe 결과를 같은 스키마로 변환해 **236세트/14규칙 재보정까지 엔드투엔드로 검증**했다.

**합격 기준**: 조건별 균형정확도 ≥ 0.80, 오탐률 ≤ 10%. 미달이면 ship에서 beta로 강등한다.

### 11.3 다음 단계

1. 자체 촬영 → 재보정 → 규칙 JSON 갱신 (위 절차)
2. 기준선 세트(`note=baseline`)로 `threshold_rel`을 MediaPipe 스케일로 재보정
3. 실사용 로그로 피로형 임계값 도출 (현재는 습관형 기준)
4. 재보정 통과 후 실험실 → 일반 사용자 화면으로 승격
5. 넓은 체형 인구 데이터 확보 시 정준 리타게팅 활성화 검토

## 부록 A. 용어집

| 용어 | 설명 |
|---|---|
| **AUC** | ROC 곡선 아래 면적. 무작위로 뽑은 위반 사례가 정상 사례보다 높은 점수를 받을 확률 |
| **균형정확도** | (민감도+특이도)/2. 클래스 불균형에 강한 정확도 |
| **Youden J** | 민감도+특이도−1. 이 값이 최대가 되는 지점을 임계값으로 삼는다 |
| **GroupKFold** | 그룹(여기선 수행자)이 학습·평가에 나뉘어 들어가지 않도록 하는 교차검증 |
| **ICC** | 급내상관계수. 전체 분산 중 개인 간 분산의 비율 |
| **MAD** | 중앙값 절대편차. 이상치에 강한 산포도 |
| **랜드마크** | 포즈 추정 모델이 내놓는 관절 위치 점 |
| **world 좌표** | MediaPipe가 내는 미터 단위 3D 좌표(골반 중점 원점) |
| **신체좌표계** | 골반을 원점으로, 중력 반대 방향을 위쪽으로 삼아 세운 사람 기준 좌표계 |
| **valgus** | 무릎이 안쪽으로 무너지는 것 |
| **연기된 편차** | 데이터 제작 시 피험자가 의도적으로 만든 잘못된 자세 |
| **완전요인설계** | 조건들의 참/거짓 전 조합을 모두 촬영하는 설계(2^k) |
| **미러 안전** | 카메라가 좌/우 어느 쪽에 있어도 값이 유지되는 성질 |
| **델리게이트** | 추론 연산을 어느 하드웨어(CPU/GPU)에 맡길지 지정하는 설정 |
